## 1. 背景与问题本质

### 1.1 现状：四环在三粒度上复用度极不平衡

| 环 \ 粒度 | 大盘                     | 板块                  | 个股                   | 复用度                                       |
| ------ | ---------------------- | ------------------- | -------------------- | ----------------------------------------- |
| **溯源** | ✓ review（归因到板块层）       | ◷ sector\_trace 设计稿 | ✓ stock\_trace（异动归因） | 低：三独立 agent，但归因链已复用 `ChainStage`          |
| **预判** | ✓ predict\_from\_trace | ✗ 无入口               | △ chat + 轻量预判        | 中：统一 `PredictionResult`，产出方分散             |
| **验证** | ✓ index                | ✓ sector            | ✗ 数据源未接              | **最高**：`classify_target` 已三粒度分类           |
| **迭代** | ✓ review 已注册           | ◷ 规划中               | ✗ 无                  | 中：`IterableAgentAdapter` 通用，evaluator 单归因 |

### 1.2 问题本质

复用地基已存在（统一 `PredictionResult` schema、统一归因链 `ChainStage`、统一 `IterableAgentAdapter` 注册表、统一 `classify_target` 分类、事件链模式），但**缺一个统一的** **`Target`** **维度贯穿四环**，导致：

1. 预判产出方散落（大盘 `predict_from_trace`、个股 `run_chat_prediction`、板块无），没有 `predict(target, snapshot)` 统一入口。
2. 验证器 `classify_target` 到 stock 断（"个股源未接"），三粒度没打通。
3. 迭代闭环只挂归因类（review/event\_analyst），预判/验证类没挂。
4. 板块四环断裂：溯源有设计稿，预判/验证/迭代全缺。

### 1.3 用户确认的闭环逻辑（✅）

- **溯源 → 预判 → 验证 → 迭代** 四环。

- **溯源**只能走**历史切片监督式迭代**（产出无未来锚点，靠标准答案对照）。

- **预判**必须走**验证驱动迭代**（产出有 `due_dates` 到期锚点，验证结果 = 标准答案）。

- **验证**是预判的伴随动作，与预判不可分割。

- **大改可接受**：以逻辑完善且闭环为主。

## 2. 核心抽象：统一 Target 维度（地基）

### 2.1 Target 模型

四环全部用 `Target` 通行，替代散落的 `target` 字符串 + `classify_target` 临时归类：

```python
class Target(BaseModel):
    kind: Literal["index", "sector", "stock"]
    internal_id: str           # 稳定标识（画像 key / 缓存 key / 日志 一律用它，不用 name）
    code: str | None = None    # ts_code 带交易所后缀：000001.SH / 000001.SZ（区分指数与个股码空间冲突）
    name: str                  # 展示名（"上证指数"/"半导体板块"/"贵州茅台"，可改名不影响 internal_id）
```

**数据卫生约束（✅ P0 定稿时修，事后迁移成本翻倍）**：

1. **码空间冲突**：`000001` 既是上证指数又是平安银行。`kind` 能区分，但任何只落裸码的缓存 key / 日志 / 画像维度会撞。**内部统一存带交易所后缀的** **`ts_code`（`000001.SH`** **/** **`000001.SZ`），6 位裸码只做展示层。**
2. **板块改名脆弱性**：`resolve_sector_target(name)` 按名解析，同花顺概念板块会改名/合并，改名即断历史画像。**Target 必须带稳定** **`internal_id`，画像 key 强制用** **`internal_id`（或 code）而非 name**，改名只更新 `name` 字段。

### 2.2 Target 的三粒度映射（复用现有 classify\_target）

| kind   | internal\_id 来源       | ts\_code      | name 来源 | 验证数据源                        |
| ------ | --------------------- | ------------- | ------- | ---------------------------- |
| index  | `INDEX_TARGETS[name]` | `000001.SH` 等 | 已知指数别名  | 指数日 K（`get_index_kline`）     |
| sector | 板块稳定 code             | 板块 ts\_code   | 板块名     | 板块日 K（`get_ths_daily_range`） |
| stock  | 个股稳定 code             | `000001.SZ` 等 | 个股名     | **待接入**（个股日 K + 成交量）         |

> `classify_target`（`prediction_targets.py`）已实现 index/sector/stock/unknown 四类，本架构将它提升为**首类 Target 对象**，而非仅在验证时临时归类。

### 2.3 TargetProfile 配置层（✅ P0 新增，粒度差异集中一处）

`Target` 只承载"分析谁"（标识），不承载"这类怎么分析"（粒度差异）。粒度差异若散落在四环的 `if target.kind == ...`，会复制到至少 5 处（预判入口、验证数据源、迭代产片源、归因 prompt、验证指标）。**用一张轻量数据化注册表收拢**：

```python
class TargetProfile(BaseModel):
    kind: Literal["index", "sector", "stock"]
    # 溯源
    trace_prompt_template: str        # 归因 prompt 分粒度
    evidence_sources: list[str]       # 数据源列表（北向/宏观 vs ETF/龙头 vs 龙虎榜/主力）
    # 预判
    snapshot_builder: str             # 输入快照构造器名
    default_horizons: list[str]       # 各粒度默认预测周期（默认 ["short","mid","long"]）
    # 验证
    kline_fetcher: str                # 数据获取函数名（get_index_kline / get_ths_daily_range / get_stock_kline）
    benchmark: str | None             # 超额收益基准（个股用；index/sector 为 None）
    # 迭代
    case_sourcer: str                 # 产片源函数名
    score_threshold: float | dict     # 触发迭代的命中率阈值：默认 float；或按 horizon×场景 分层 dict（见 §5.3）
```

四环统一读 `get_profile(target)`，所有 `if target.kind == ...` 变为 `profile = get_profile(target)`，差异集中一处。加第五粒度（如 ETF/行业指数）只改这张表。**这是数据，不是框架（YAGNI）**。

**阈值分层取值（✅ 统一入口，见 §5.3；Spec C §4.4 必须引用，不读裸字段）**：迭代触发阈值按"粒度 × horizon × 场景"三层分层。粒度由 `TargetProfile.kind` 隐含；horizon/场景 用统一取值函数 `get_iterate_threshold(target, horizon, scenario)`：先查 `score_threshold` 的分层 dict（如 `{"short": {"up": 0.5, "down": 0.4}, "mid": {...}, "_default": 0.4}`），按 horizon→scenario 逐层命中，未命中回落 `_default`（或 float 默认值）。`score_threshold` 保持单字段，仅类型扩展为 `float | dict`，不新增配置层。

## 3. 四环统一抽象 + 三粒度适配

### 3.1 溯源环：`trace(target, snapshot) -> TraceResult`

| 层         | 抽象                                                                                | 三粒度适配                                                                                                                           |
| --------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 归因链结构     | **统一** **`CausalChain`** **/** **`ChainStage`**（`trace/chain.py`，已复用）             | 三粒度共用"现象确认 → 触发 trigger → 传导 transmission → 定价 repricing"链                                                                      |
| 归因 prompt | 分粒度                                                                               | 大盘 4 类（`global_risk_liquidity`/`domestic_macro_policy`/`industry_technology_supply`/`market_positioning_liquidity`）；板块事件级；个股异动级 |
| 产出        | 统一落 `TraceResult`（MarketTraceResult / SectorTraceResult / StockTraceResult 同源链结构） | 三粒度归因结果都含 `CausalChain`                                                                                                         |

**落地支撑**：

- 大盘 review：已实现，不改（归因到板块层是终点）。

- 板块 sector\_trace：Spec D 落地（设计稿 `2026-08-28-sector-trace-design.md` 已规划溯源 + 迭代，补预判 + 验证）。

- 个股 stock\_trace：已实现，schema 已复用 `ChainStage`。

### 3.2 预判环：`predict(target, trace_or_snapshot) -> PredictionResult`

| 层       | 抽象                                                                    | 三粒度适配                               |
| ------- | --------------------------------------------------------------------- | ----------------------------------- |
| 输出结构    | **统一** **`PredictionResult`** **+** **`conditions[]`**（Spec A 定义）     | 三粒度共用                               |
| 统一入口    | `predict(target, snapshot)`，**内部 fast/slow 路由**（见下）                   | index→市场快照；sector→板块快照；stock→个股快照   |
| 现有产出方收敛 | from\_trace / run\_chat\_prediction / morning\_forecast / 轻量预判 → 统一入口 | 消除"大盘走 from\_trace、个股走 chat、板块无"的割裂 |
| 跨粒度级联   | **输入组装**（非事件驱动）：板块预判运行时主动拉当日大盘溯源结论作上下文                                | 大盘溯源 → 板块预判（见 §5.4）                 |

**fast/slow 双通道路由（✅ P1，避免硬捏成单一实现）**：四个产出方恰好对应两种性质，统一入口应是 facade + 内部路由：

```python
def predict(target: Target, snapshot) -> PredictionResult:
    if snapshot.is_structured_trace and template_matches(snapshot):
        return ScenarioPredictSkill.run(get_profile(target.kind), snapshot)  # fast：结构化溯源链，模板套用，毫秒级
    return PredictAgent.run(target, snapshot)                                 # slow：生资讯/chat，需理解→检索→构造，多步推理
```

- **fast path**：`predict_from_trace` 形态（输入已是结构化 `CausalChain`，条件分支模板直接套用，固定成本）。

- **slow path**：`run_chat_prediction` 形态（输入生资讯/对话，需理解→检索→映射→构造分支）。

- 迁移安全：四个旧产出方逐个收编到 facade 后面，schema 不用一次改完。

**落地支撑**：Spec A（条件化预判改造）先把 `PredictionResult.conditions[]` 定稿；`predict(target)` 统一入口作为 Spec A 的**目标结构**（不强制 Spec A 一次到位，但 schema 设计必须兼容 `target` 维度）。

### 3.3 验证环：`verify(prediction, target) -> verification`

| 层              | 抽象                                                                                            | 三粒度适配                                                      |
| -------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| target 分类      | **统一** **`classify_target`**（已实现）                                                             | index/sector/stock/unknown                                 |
| 到期判定           | **统一** **`_verify_horizon`** **/** **`_verify_conditions`**（Spec B）                           | 三粒度共用                                                      |
| 数据源            | `_fetch_kline_window` 分粒度                                                                     | index（指数 K）✓ / sector（板块 K）✓ / stock（个股 K + 成交量，Spec B 已接） |
| 画像             | `read_validation_profile(target)`                                                             | 三粒度统一画像                                                    |
| **事实验证（双向印证）** | **溯源归因时回流**（Spec Cbis）：归因结论场景命中历史预判 `conditions[].scenario` → 产 `PredictionConfirmation` 回流画像 | 采集点挂共用 `CausalChain`，随溯源三粒度天然对齐                            |

> **验证双渠道（✅ P1，Spec Cbis 落地）**——验证 = 到期价 + 事实验证，两条渠道正交、分渠道记录、合并呈现，**不合并成单一数字**：
>
> - **渠道A（到期价）**：确定性判定（`_verify_horizon` 比对 kline 的 hit/miss），可自动、无人值守。**主渠道，主渠道不动。**
>
> - **渠道B（事实验证/双向印证）**：溯源归因发现的事实确认历史预判场景 → `evidence-confirmed` 回流画像。带证据链路（`source_trace_id`），信息量 > 价格 hit/miss。**采集点挂溯源链，失败降级不阻断归因。**
>
> 读画像（`read_validation_profile`）同时给两渠道信号 + `scenario_harvest`（被现实多次印证的场景 / 多次预判却从未被印证的场景），供预判反哺与迭代消费。

**落地支撑**：Spec B（验证逻辑落地）——skill 化 + 画像落库；**画像 key 必须用 Target 而非字符串**；个股数据源接入是本环打通三粒度的关键缺口。

### 3.4 迭代环：`iterate(agent, ground_truth_kind) -> variants`

| 层         | 抽象                                                                  | 三粒度适配                                                                                                |
| --------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 注册表       | **统一** **`IterableAgentAdapter`**（已实现）                              | 三粒度四环都能挂                                                                                             |
| evaluator | **抽象化**：归因评分器（已有）+ 验证评分器（Spec C）                                    | 归因类用归因评分；预判类用验证评分                                                                                    |
| 产片源       | `case_sourcers` 分粒度                                                 | review/market\_close\_snapshot、event\_store\_scan、sector\_close\_snapshot、prediction\_verified\_scan |
| 变体引擎      | `variant_engine` 复用（prompt\_diff/workflow\_diff/data\_source\_diff） | 三粒度共用                                                                                                |

**迭代双链路显式分离（✅ P0，防 Spec C 混用评分器）**——两条链路是本质不同的东西，必须作为结构固定，不得互相越界：

```
链路一（溯源迭代 · 历史切片监督式）：
  历史切片 → 重跑 TraceAgent → 对比标准答案(归因) → 修正溯源 Skill/prompt

链路二（预判迭代 · 验证驱动式）：
  到期预判 → 验证评分(evaluate_verification) → 按条件分支聚合 → 低命中分支更新
```

| <br /> | 链路一（溯源迭代）                  | 链路二（预判迭代）                          |
| ------ | -------------------------- | ---------------------------------- |
| 标准答案来源 | 历史切片 + 人工/事后标注             | 到期验证结果（due\_dates 锚点）              |
| 评分器    | `evaluate_attribution`（已有） | `evaluate_verification`（Spec C 新增） |
| 触发条件   | 归因偏差大                      | 条件分支命中率低                           |
| 更新对象   | 溯源 Skill / 证据权重            | 预判 Skill 的条件分支                     |

> **迭代三层统一（✅ P1，Spec Cbis 补充）**——"迭代"不只是逻辑层改进。凡系统可自我生长（喝过反馈 → 有固化点 → 前后可测量）皆算迭代。三层的反馈信号、固化点与落地各不同，**不合并为单一机制**：
>
> | 层   | 机制                       | 验证信号                                 | 固化点                                           | 落地            |
> | --- | ------------------------ | ------------------------------------ | --------------------------------------------- | ------------- |
> | 逻辑层 | 变体→回放→评分→合入              | `evaluate_verification`（价格 hit/miss） | 预判 prompt / conditions 规则                     | Spec C（正在做）   |
> | 印证层 | 溯源回流事实验证 → 画像场景信号        | `evidence-confirmed`（双向印证）           | `read_validation_profile` 的 scenario\_harvest | **Spec Cbis** |
> | 知识层 | 已验证证据链路沉淀为可检索知识，"遇况越多越强" | 命中链路复用                               | 画像证据池 / 知识库                                   | **跟随项**（不在本轮） |
>
> 原则（防"万物皆迭代"不可证伪）：每一层必须能回答三件事——**喝过什么反馈 / 固话在哪 / 改前改后怎么测**。三层共用一套 `read_validation_profile` 画像通道与预判反哺接口（`enrich_prediction_input`），互不新建立独立环。

**落地支撑**：Spec C（迭代改进）——预判接入验证驱动闭环 + evaluator 抽象化（归因评分器 + 验证评分器两套，不混用）；Spec Cbis（印证层）——溯源回流事实验证，画像新增场景信号。

## 4. 共享基础设施（Skill 契约 + 存储层）

> 前四个 Spec 落地会共享两类基础设施，全局先定义，避免各自建表/各自写函数导致不统一、迭代环消费不了。

### 4.1 Skill 契约定义（最小契约）

`skill` 不是普通工具函数，而是"参数化接口 + 执行逻辑 + 输出 Schema + 示例"的完整资产包，**必须有版本、固定 I/O、可独立替换**（否则迭代环无法"替换 Skill 版本"）。每个 skill 目录下须有 `skill.yaml`：

```yaml
name: prediction_validation
version: v1
input_schema:
  prediction: PredictionResult
  target: Target
  actual_kline: DataFrame
output_schema:
  condition_results: list[ConditionResult]
  score: float
  profile_update: dict
```

约束：

- 四环的 skill（trace/predict/verify/iterate）都遵循此契约，`version` 用于迭代环追踪"哪个版本产出的预判"。

- `input_schema`/`output_schema` 用 Pydantic 模型定义（非手写 dict），保证跨 skill 类型一致。

### 4.2 Context 存储层（三张最小表）

三张表是 Spec B 画像数据源 + Spec C 迭代输入，全局先定义，前四个 Spec 直接消费：

```text
trace_chain 表：
  chain_id
  target_kind, target_internal_id, target_name   # 用 internal_id（§2.1），不用 name
  trigger_time
  chain_json          # CausalChain 序列化
  created_at

forecast_snapshot 表：
  prediction_id
  target_kind, target_internal_id, target_name
  trace_chain_id      # 可空（无溯源直接预判时）
  conditions_json     # conditions[] 序列化
  due_dates           # 到期锚点
  skill_version       # 产出该预判的 skill 版本（§4.1）
  status              # pending / verified
  created_at

validation_result 表：
  validation_id
  prediction_id
  target_kind, target_internal_id
  condition_results_json
  total_score
  verified_at
```

> **⚠️ 与现有** **`prediction_records`** **对齐**：你们已有 `prediction_records` 表（含 source\_type/source\_id/prediction/due\_dates/verification）。`forecast_snapshot`/`validation_result` 应与其**对齐或复用**（优先扩展 `prediction_records` 而非新建重复表）。三表是最小语义模型，落地时映射到现有表结构，勿重复建表。

## 6. 依赖关系与实施顺序（闭环优先）

```
Target 维度（本文档地基）
      │
      ├─ Spec A（条件化预判）── conditions[] 定稿 ──┐
      │                                            ├─ Spec B（验证）── 画像 + 个股数据源
      │                                            │        │
      ├─ Spec D（板块四环）── 溯源+预判+验证+迭代 ──┘        ▼
      │                                            Spec C（迭代）── 验证驱动闭环
      │                                                  │
      │                                            Spec Cbis（预判验证升级）──
      └─（四环三粒度架构最终成型）                      溯源回流事实验证（双向印证）
```

**推荐实施顺序**（以闭环价值 + 依赖排序）：

1. **P0：Target 维度定稿**（本文档地基，Spec 落地前必须先定）——`Target` 模型（internal\_id + ts\_code + name）+ `TargetProfile` 注册表（§2.3）+ 数据卫生（§2.1 码空间冲突/板块改名）。**这是前四个 Spec 的共同约束，不定稿则四处各写一套。**
2. **Spec A**（条件化预判）先定 `conditions[]` schema —— 它是预判/验证/迭代的共同数据基础。
3. **Spec B**（验证逻辑）——消费 Spec A 的 conditions，落地验证 skill + 画像 + **个股数据源**（打通验证环三粒度）。**⚠️ 个股数据源是全盘杠杆最高的单一动作：conditions\[] 定稿后立即并行启动，不等 Spec A 收尾。**
4. **Spec C**（迭代改进）——消费 Spec B 的画像，落地验证驱动闭环 + evaluator 抽象。
5. **Spec Cbis**（预判验证升级）——在 Spec C 后、Spec D 前落地验证环双渠道：溯源归因时回流事实验证（双向印证），画像新增场景信号（feed 预判反哺与迭代）。
6. **Spec D**（板块四环）——消费前三者，落地板块溯源 + 板块预判 + 板块验证 + 板块迭代，补全三粒度。

## 8. 风险与约束

1. **Target 维度落地成本**：`classify_target` 目前是验证器内部函数，提升为全局 Target 需改造多处调用点（预判/验证/迭代）。**约束**：Spec A/B/C/D 落地时，`target` 相关字段统一用 Target 或至少保留可被 `classify_target` 归类的字符串，避免四处各写一套。
2. **个股数据源是验证环最大缺口**：`_fetch_kline_window` 无 stock 分支，个股验证"未接"。**Spec B 必须补齐**，否则预判三粒度无法验证闭环。
3. **evaluator 抽象勿过度设计**：归因评分器 + 验证评分器两类即可，不预设计更多评分器（YAGNI）。
4. **变体回写红线**：迭代闭环最优变体只落盘建议，不自动覆盖生产 prompt（对齐 iterate 现状）。
5. **四环边界**：溯源（历史切片）与预判（验证驱动）迭代方式不同，勿混用评分器。
6. **前四个 Spec 双向联动**：本文档定架构后，前四个 Spec 需回改；若前四个 Spec 落地发现架构不合理，也可回改本文档（但 Target 维度 + 四环抽象是稳定内核，不轻易改）。
7. **TargetProfile 勿过度设计**：它是数据注册表（§2.3），不是框架。只收拢四环真实会用到的粒度差异，不为"未来第五粒度"预留字段（YAGNI）。
8. **存储层勿重复建表**：三张最小语义表（§4.2）落地时优先扩展现有 `prediction_records`/`analysis_reports`，不新建重复表；否则新旧表并存导致迭代环消费两条链路数据。

## 9. 非目标

- 不新增第五环（如"报告"环）——四环已够，展示层复用现有前端。

- 不推翻现有 review/stock\_trace 的归因框架——只做结构复用，语义分层。

- 不做领涨板块溯源（sector\_trace 设计稿已明确仅主因板块）。

- 不做定时调度外的新触发方式（事件链 + cron 已够）。
