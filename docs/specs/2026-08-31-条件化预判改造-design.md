# 条件化预判改造设计文档

> 日期：2026-08-31
> 状态：✅ 已交付实施（三端全量收尾，2026-09-01）
> 关联 Spec：`2026-08-31-四环三粒度复用架构-design.md`（**全局指导总纲，本 Spec 的约束来源**，见 §3.2 fast/slow 路由 + §2.3/§5.1 TargetProfile）、`2026-08-31-自选股洞察升级-事件统一与两次打点-design.md`（本 Spec 定义预判内容结构，自选股洞察 Spec 负责生成时机/范围/落库）
> 涉及仓库：aistock-agent-py（预判 skill 改造，核心）、aistock-app-api（prediction\_records 验证接口）、aistock-app-frontend（预判展示）

## 1. 背景与问题

老师（王岢）反馈，目前\*\*预判 skill（含大盘预判）\*\*存在两个问题：

1. **无条件产出**：目前预判逻辑是"无条件地产出短/中/长期的预判内容"（如"短期震荡、中期看涨、长期向好"），没有给出前提条件。
2. **无验证**：预判产出后没有验证逻辑（虽然 `prediction_records` 基础设施已存在，但验证能力未接入预判产出端）。

老师的想法：**预判要加条件——满足不同条件，预判后续的情况会不同**。预判应结构化输出"条件 → 情景"对，并明确阈值和时间节点以便验证（8/28 会议：王岢强调预判需明确涨幅阈值和时间节点；王昌泽建议分放量/缩量等场景设计验证逻辑）。

### 1.1 预判 skill 现状全景（三个产出方，共用 PredictionResult）

| 产出方                                               | 触发                      | 输入                                | 输出                                                                |
| ------------------------------------------------- | ----------------------- | --------------------------------- | ----------------------------------------------------------------- |
| **prediction skill**（`skills/prediction.py`）      | 对话预测意图词（会涨/会跌/预测/后市/未来） | quote + 资金流快照                     | 三段式（现状+影响持续性推演+免责声明），`prediction_status` 恒 hypothesis             |
| **predict\_from\_trace**（`prediction_service.py`） | review\_done 事件 / 手动触发  | **大盘溯源报告**（trace）+ 市场快照（snapshot） | `PredictionResult` 落 `prediction_records` + due\_dates + 16:00 验证 |
| **晨报 morning\_forecast**（`services/cache.py`）     | 晨报生成                    | 大盘分析结论                            | 晨报预测结构化摘要 + 预测验证                                                  |

**问题根源在** **`PredictionResult`** **schema**（`schemas/prediction.py`）：`horizons[]` 每档是"固定时间尺度（short 1-5交易日/mid 1-4周/long 1-6月）+ direction + metric\_projection"的无条件定性预测，没有"条件 → 情景"结构。条件化改造 = 在 schema 中引入 `conditions[]`。

> **现状补充（同事 PR #124 已合入 main，2026-08-31）**：预测侧已叠加五组**确定性增强**，全部保留不推翻，本 Spec 在其之上加 `conditions[]`：
>
> - **A1 失效触发**（`prediction_invalidation.py`）：指数跌破 MA20 三态迟滞状态机 → `early_exit`（按 `horizon` 为 key 写 `verification`）
>
> - **A2 独立源佐证**（`prediction_service.corroborate_evidence`）：news 方向冲突检测 → `evidence_corroboration`（仅佐证，不改置信度）
>
> - **A3 置信钳制**（`_apply_confidence_cap`/`clamp_confidence_by_bucket`）：历史命中率 Wilson CI vs baseline → 确定性钳制 confidence + `confidence_source` 字段
>
> - **C1/C2 节奏大师**（`rhythm_engine.ma_breadth`/`conflict_penalty`）：MA20/MA60/前低技术位佐证 + 顶/底背离惩罚
>
> - **B1 迭代标注**（`iterate_analyzer`）：四维 evidence\_kind 静态标注
>
> **这些改动与"条件化"是两件事**：A1/A2/A3 都是"验证/可靠性增强"，没有引入"条件→情景"结构，`schema_version` 仍为 2.0。本 Spec 的 `conditions[]` 改造与其互补不冲突。

## 2. 目标

1. 预判从"无条件短中长期三段"改为**条件化结构**：`conditions[]`，每条含条件、情景、验证锚点（horizon + threshold）。
2. 覆盖范围（已确认）：**个股预判 + 大盘预判一起改**。
3. 接入验证：`anchor` 落库到 `prediction_records`，到期比对"条件是否成立 + 预判是否命中"，回写验证结果；前端展示验证进度。
4. 与自选股洞察联动：自选股洞察卡片的预判区展示条件化预判摘要（最多 2 条）。

## 3. 条件化预判结构（核心 Schema）

### 3.1 LLM 输出结构

```json
{
  "conditions": [
    {
      "condition": "若明日放量站稳前高 82.50 元",
      "scenario": "则趋势延续，上看 +5%",
      "anchor": { "horizon": "short", "threshold": "+5%", "metric": "close", "direction": "bullish" }
    },
    {
      "condition": "若缩量跌破 5 日均线",
      "scenario": "则短期转弱，注意回踩 75.00 元",
      "anchor": { "horizon": "short", "threshold": "-3%", "metric": "close", "direction": "bearish" }
    }
  ]
}
```

| 字段                 | 说明                               | 约束                                                                                                                               |
| ------------------ | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `conditions[]`     | 条件化预判列表                          | 2–3 条，互斥覆盖主要情景（上行/下行/震荡）                                                                                                         |
| `condition`        | 触发条件（可验证的事实描述）                   | 必须含**可量化条件**（放量/缩量、价位、均线、情绪温度等）                                                                                                  |
| `scenario`         | 条件满足后的走势预判                       | 尽量含幅度/目标位                                                                                                                        |
| `anchor.horizon`   | 验证周期                             | short / mid / long（对齐现有 `PredictionHorizonType` 与 `HORIZON_TRADING_DAY_OFFSETS`：5/20/120 交易日）                                    |
| `anchor.threshold` | 验证阈值（涨跌幅%）                       | 明确数值，用于比对                                                                                                                        |
| `anchor.metric`    | 验证标的                             | close（默认）/ high / low / volume / index\_close 等                                                                                  |
| `anchor.direction` | 该条件的**情景方向**（验证 scenario 命中主判依据） | bullish / bearish / neutral；**自挂不依赖** **`horizons[].direction`**（同档不同情景方向可能相反，且个股轻量预判不自建完整三档）；**必填**，LLM 缺失时由归一化层确定性提取兜底（见 §4.1） |

> **设计原则（✅ 已确认，参考节奏大师 C1/C2 思路）**：**"LLM 产结构 + 确定性算判定"**。`conditions[]` 的 condition/scenario 由 LLM 产出（token 用于生成语义），但 `condition_met`（条件成立判定）**不用 LLM 二判**，复用确定性计算（`ma_breadth` 等，见 §4.2）——验证端 0 token，且判定更稳、可审计。这与节奏大师 `detect_phase(tech=...)` 佐证只进 evidence 的哲学一致。
>
> **✅ 已落地（2026-09-16）**：判定实现为纯函数 `services/condition_met_judge.py`（无 IO、无日志、只用标准库）。⚠️ 原文举例的 `rhythm_engine.ma_breadth` **已不存在**（已删除且有测试守卫禁止回归），技术位判定为**新写确定性实现**；实际口径见 §4.2 落地块。

> 硬约束：禁止产出"无条件短中长期"式空洞预判；至少 1 条 condition 含成交量维度（呼应王昌泽"分放量/缩量场景"）。

### 3.2 大盘预判结构（对齐个股）

大盘预判（review 大盘溯源 / morning 晨报大盘预判）使用同一 `conditions[]` 结构，`anchor.metric` 缺省为上证指数 close：

- 例：`{condition:"若上证放量站上 3xxx 点", scenario:"则趋势延续…", anchor:{horizon:"short", threshold:"+1%", metric:"index_close", direction:"bullish"}}`

### 3.3 与 PredictionResult 的关系（schema 落点）

- **不改** **`horizons[]`** **字段**（存量数据兼容），在 `PredictionResult` **新增** **`conditions: list[PredictionCondition]`**（可选字段），`schema_version` 升级 `"2.0"` → `"3.0"`。

- 新产出必须带 `conditions[]`（非空）；旧记录（无 conditions）保持 `schema_version=2.0`，与 3.0 隔离。

- **版本分桶口径（执行前置澄清，勿与验证口径混用）**：`schema_version`（PredictionResult 数据结构版本）与 `methodology_version`（验证器判定口径，当前已是 `"3.0"`，`prediction_validator.py`）是**两个独立维度**，不能互相替代。过滤"是否含 conditions"必须按 `schema_version`，**不得**用 methodology\_version 过滤——否则会误伤存量已按 3.0 验证过的 2.0 记录。实施时需在 execution 清单确认种子起分桶依据。

- `anchor.horizon` 取值对齐现有 `PredictionHorizonType`（short/mid/long），`_compute_due_dates`（`HORIZON_TRADING_DAY_OFFSETS`：5/20/120 交易日）与验证器直接复用。

- **schema\_version 硬编码多方同步**：`PredictionResult.schema_version` 目前是 `Literal["2.0"]` 硬编码，且 `_coerce_prediction_payload` 会兜底 `data.setdefault("schema_version", "2.0")`；`run_chat_prediction` 走 `with_chat_structured_output`（json\_mode 直接出 Pydantic 对象）绕过该兜底。升 3.0 时类型字面量、兜底值、json\_mode 路径**三处需同步改**。

- **PR #124 既有字段原样保留**（不因升 3.0 删除）：`PredictionHorizon.confidence_source`（A3）、`PredictionRisk` 扩展（indicator/direction/window/measure/snapshot\_value/triggered，A1）、`PredictionResult.evidence_corroboration`（A2）。`conditions[]` 与它们并存；A3 只钳制 horizons 的 confidence，不涉及 condition。

- **Target 维度兼容（✅ 对齐全局指导 spec §2）**：`PredictionResult` 需能关联 `target`（当前 `horizons[].target` 是自由文本）。本 Spec 落地时，`PredictionResult` 增加可选 `target: Target | None`（或保留 `horizons[].target` 但验证环 `classify_target` 归类时改用全局 `Target` 对象），供三粒度复用。**不强制本 Spec 一次到位**，但 schema 设计不能阻碍后续 `predict(target)` 统一入口。

## 4. 改造范围

### 4.1 预判 skill（aistock-agent-py，核心）

**现状**：三个产出方共用 `PredictionResult`（`horizons[]` 无条件三档）——对话 prediction skill、大盘 `predict_from_trace`、晨报 `morning_forecast`。

**改造**（三个产出方统一接入 `conditions[]`）：

1. **`schemas/prediction.py`**：新增 `PredictionCondition`（condition/scenario/anchor）与 `PredictionResult.conditions`（可选），`schema_version` 升 3.0（§3.3）。
2. **预测入口 prompt 重写（两个入口，非共用）**：

   - **`run_predict`**（`predict_from_trace` 调用，大盘溯源预测）：输入 = 溯源报告 + 市场快照，输出强制含 `conditions[]`。

   - **`run_chat_prediction`**（prediction skill 调用，对话内预测）：输入 = quote/flow 快照 + 新闻，输出同样强制含 `conditions[]`。

   - 均增加字段对照校验（沿用 REVIEW\_PROMPT 字段对照表经验）+ 归一化层。

   - **direction 归一化兜底（✅ 已决策）**：`anchor.direction` 为 schema 必填，但 LLM 缺失时归一化层从 `condition`/`scenario` 文本确定性提取（"涨/升/站上/看多"→bullish，"跌/破/回踩/看空"→bearish，否则 neutral），复用 A2 `_direction_sign` 同构逻辑，避免 `model_validate` 直接 parse\_failed。

   - **`run_chat_prediction`** **现状为"死代码"（✅ 已决策：方案 A）**：当前其返回结果**不落库、不验证（A3 裁决移除 due\_dates）、调用结果被丢弃**（`prediction_service.py` 注释明示死代码，PR #124 仍保留该注释）。**✅ 已决策方案 A**：对话预测也落库 + 接入验证（"V2 落库验证"），重写输出结构含 `conditions[]`，恢复 `_compute_due_dates` 调用。**在 PR #124 基础上进行**：保留 A2 佐证（`evidence_corroboration`）、A3 置信钳制（`confidence_source`）、红线 `_hard_validate_chat_prediction`，仅补落库 + due\_dates。
3. **大盘预判**：`predict_from_trace` 输出含 `conditions[]`；morning\_forecast 同步结构化。
4. **红线保留**：不产生交易指令、非点位预测（剥离绝对点位逻辑保留）、`prediction_status` 语义不变。
5. **统一入口** **`predict(target)`（✅ 对齐全局指导 spec §3.2，目标结构，非本 Spec 一次到位）**：

   - **fast/slow 双通道路由**：`predict_from_trace`（结构化溯源链 → fast，模板套用）+ `run_chat_prediction`（生资讯/chat → slow，多步推理）收敛到统一入口 facade 后面，勿硬捏成单一实现。

   - **TargetProfile 约束**：所有 `if target.kind == ...` 的粒度差异改为 `profile = get_profile(target)`（全局 §2.3），不散落在四环各处。

   - 本 Spec 只定 `conditions[]` schema + 产出方输出结构，`predict(target)` 统一入口作为**目标结构**（Spec 后续阶段收编），不阻塞 schema 落地。

### 4.2 落库与验证（aistock-app-api）

- 复用现有 `prediction_records` 表（source\_type/source\_id/schema\_version/prediction/due\_dates/verification）：

  - 预判产出时，将 `conditions[]` 写入 `prediction.prediction`，`anchor` 映射到 `due_dates`（按 horizon 展开）。

  - **大盘溯源** **`predict_from_trace`**：已有 `POST /internal/predictions` 写入链路，升级为含 `conditions[]`。

  - **对话 prediction skill（`run_chat_prediction`）一并落库 + 接入验证**（§9 决策 A：对话预测也写 `prediction_records` 并接入 16:00 到期验证、恢复 `_compute_due_dates`），输出含 `conditions[]`；**保留 PR #124 的 A2（evidence\_corroboration）+ A3（confidence\_source）后处理**。

  - **⚠️ chat 落库按 target 分流（✅ 已决策，防 pending 堆积）**：`run_chat_prediction` 的 target 常为**个股**，而验证器 v1 仅支持 index/sector。落库时按 `prediction.horizons[0].target` 分类：`classify_target(target)` ∈ {index, sector} → 正常 `status=pending`；∈ {stock} → **`status=skipped`** **+** **`skip_reason="chat 个股 target 超出 v1 验证范围"`**（复用 `save_skipped_prediction`），避免无法验证的个股记录污染 16:00 验证队列。

  - **晨报 morning\_forecast**：沿用晨报缓存（`get_cached_morning_forecast`），是否落 `prediction_records` 待定（默认不落，仅展示）。**⚠️ 边界声明**：不落库 ⇒ 晨报预判不参与 16:00 验证画像与迭代闭环（Spec B/C）——这是**有意边界**（晨报是摘要展示，非闭环主链）；若后续想让晨报预判闭环，须改走 `light_predict` 通道落库（见 §4.4）。

  - **轻量预判的验证（可选）**：核心 condition 的 anchor 落 `prediction_records`（source\_type=`light_predict`，见 §4.4）。

- 验证：

  - 保留 agent-py 每日 16:00 到期验证任务（阶段 0 起口径 3.0）。

  - 验证逻辑升级：对每条 `condition`，先判定"条件是否成立"（用当/次日实际行情比对），成立才验证 `scenario` 是否命中（threshold 比对），回写 `verification`。scenario 命中主判方向取 **`anchor.direction`**（条件自身方向，不依赖 `horizons[].direction`）。

  - 验证结果新增字段：`condition_met`（条件是否成立）、`hit`（命中与否）、`actual`（实际值）。

  - **`condition_met`** **判定复用 PR #124 确定性逻辑，不重复造轮子**：技术位条件（跌破/站上 MA20/MA60/前低）复用 `rhythm_engine.ma_breadth(closes)`（warning/recovery/breakdown\_ma60/below\_prior\_low 映射）；涨跌幅类条件用 `prediction_invalidation._ma` 或 kline pct 直接比对；volume 类首批跳过（`condition_met: null`）。

- **✅ 条件成立判定「已落地」（2026-09-16；agent-py `64b06b6`/`8230a64`/`b361764` + app-api `fa5c6b3`/`edb9941`）——以下为代码实际口径，与上文原始表述有出入处已在每条内标注**：

  - **技术位类 = 新写确定性实现（替代 `ma_breadth`，原文该处已失效）**：纯函数 `services/condition_met_judge.py`（禁 LLM、无 IO）。**路由优先级（终审 #2 修正后）**：volume 关键词 → **绝对点位** → 明示技术位（`跌破|下破|失守|站上|突破|收回|前低|新高|均线|日线|周线|月线|MA\d+`）→ 涨跌幅/阈值。技术位判定： 严格**前低**（末点 close < 窗口内其余点最小值）/ 严格**新高**（> 其余点最大值）/ **均线近似**（文本含 `MA60|60日` 取 60 日线，否则默认 MA20；均线取"可用样本均值"近似，v1 不做严格窗口补齐，样本 < 2 个 → 无法判定）；多空方向取关键词优先（跌破/下破/失守→down，站上/突破/收回/新高→up），否则回落 `anchor.direction`，neutral 不产判定。
  - **绝对点位类首批 omit（终审 #2 新增，阻塞项修复）**：文本含数字点位（`\d{3,}(\.\d+)?\s*(点|元)`，或"站上/突破/跌破/上穿/下破/击穿/失守/收回"+紧邻数字，排除"数字+`%`/日/周/月/个交易日"）→ 恒 **`None`（不产 `condition_met` 键）**。原因：点位阈值口径未定，旧路由把"站上 3000 点""突破 3300 点"丢进技术位分支用 MA 近似判定，在顺势行情下误判 `true`；而 `true` 一旦写入不可撤回（D1 只写 true 不写 false）→ 宁可 omit。
  - **涨跌幅/点位类 = 窗口累计**：优先 `closes` 首末比值；`closes` 不足 2 个（板块链路端点可能无 close）→ 回退 `pct_chgs` **复利累计**；与 `anchor.threshold` 按 `anchor.direction` 比对（bullish：累计 ≥ 阈值且 > 0；bearish：累计 ≤ 阈值且 < 0；neutral：|累计| ≤ 0.5%，与 `_NEUTRAL_PCT_THRESHOLD` 同口径）。
  - **volume 类首批 omit**：命中 `放量|缩量|成交额|成交量` 的条件恒**不产判定**；`volumes` 入参已保留供后续扩展。取数侧已铺数据基础：T2（`64b06b6`）令 `_fetch_kline_window` 保留 `close`/`vol`；T9（`edb9941`）令板块日 K 端点透传 `close`/`vol`/`amount`（`amount` 上游 `ths_daily` 无此字段 → 契约位恒 `null`）。
  - **只写 true 不写 false（决策 D1）**：判定不成立 / 无法判定 / 数据源故障一律**不产键**（不写 `false`，也不写 `null` 覆盖）。前端在无 `condition_met` 数据时回退"全量展示"降级分支。

## 8. 风险与注意事项
