## 1. 背景与目标

当前"提醒"Tab（首页 `AlertContent.vue`）是两个割裂模块：

- **自选股洞察**：涨停雷达 + 价格异动归因（溯源逻辑），数据实时性依赖盘中 5 秒轮询。
- **个股情报**：资讯/公告/研报 AI 研判（预判逻辑），定时抓取 + 点击"AI解读"才实时生成完整研判。

老师（王岢）8/28 会议意见：两个模块应综合在一起；异动监测只需早盘后/尾盘后两次，避免盘中假动作；同一股票的多条情报应合并展示。

### 目标

1. **事件层统一**：涨停雷达合并进价格异动分析逻辑（涨停 = price 事件的特例），归因链路唯一化。
2. **异动监测改两次打点**：移除盘中 5 秒轮询，只保留 11:30（午盘）+ 15:05（收盘）两次打点。
3. **个股情报模块保留现状**（已确认）：事件列表 + `ai_impact` 利好/利空研判 + 通知中心逐条推送 + event-catcher 完整列表页，**不参与聚合改造**（速览层）。
4. **自选股洞察升级**：按股票聚合一张卡（溯源区 + 预判区），覆盖当日异动 ∪ 重大利好/利空资讯的自选股（深度层）。
5. **定时轻量预判**：在两次打点后对"异动 ∪ 重大资讯"自选股批量生成条件化预判（quick 模型 1–2 句），落库供自选股洞察卡秒读。**对齐架构**：目标对象用 `Target(kind="stock")` 维度过关（不裸 symbol），可读验证画像反哺（Spec B），可经 `light_predict` 通道纳入验证/迭代闭环（见 §4.3）。

## 2. 现状梳理

### 2.1 自选股洞察（溯源链路）

| 环节 | 现状 |
|---|---|
| 涨停发现 | `LimitUpRadarCrawler` 爬虫，独立建 `watchlist_insight`（limit_up_radar 类型）事件 |
| 异动发现 | `stock_trace` 事件层 + `PriceTriggerDetector` 盘中 5 秒轮询（`STOCK_TRACE_TRIGGER_ENABLED` 控制，默认关） |
| 定时打点 | `PriceMoveService.run('midday')` 11:30、`run('close')` 15:05（已存在） |
| 归因 | 事件落定（收盘/反向落定）后入队，Python consumer 归因，主因 `primary_cause` |
| 落库 | `watchlist_insight`（涨停雷达）+ `stock_trace`（价格异动）两张表 |

### 2.2 个股情报（预判链路）

| 环节 | 现状 |
|---|---|
| 抓取 | `event_scrape_daily` 08:45 盘前全量 + `event_scrape_intraday` 10:00–14:00 每小时 + `event_scrape_close` 15:05 收盘汇总 |
| 研判 | 事件入库带 `ai_impact`（利好/利空）；完整 AI 研判（alert agent）**仅用户点击"AI解读"时** SSE 实时生成（当日缓存 `getAlertReport`） |
| 数据源 | 同花顺牛股资讯等；已知单源依赖问题（2026-08-19 起日供稿量下降），不在本 Spec 范围 |

### 2.3 前端

- 首页 Tab：`MainTabs` → `AlertContent`（自选股洞察 ListCell 行 + 个股情报 ListCell 行两个模块）。
- 详情页：`insight-detail.vue`（涨停雷达）/ `insight-detail-move.vue`（价格异动）两页并存；`event-catcher.vue`（个股情报完整列表）+ `alert-analysis.vue`（AI 研判）。
- 洞察融合列表：`insight.vue` 已按 event_type 分流。

## 3. 设计决策（已确认）

| 决策点 | 结论 |
|---|---|
| 模块分工 | **个股情报保留现状**（速览层：事件+研判+逐条推送）；**自选股洞察升级**（深度层：聚合卡+完整溯源/预判） |
| 卡片模型 | **按股票聚合，一只股票一张卡**（当天有异动或重大事件都只出一张）；卡内"溯源区 + 预判区"**并行展示**（非串行两行），按最近活动时间倒序 |
| 卡片生成规则 | 股票当天有异动/涨停 → 含**溯源区**（归因主因，必有）+ **预判区**（归因驱动条件预判，必有）；仅重大利好/利空资讯（无异动）→ 只有**预判区**（事件影响预判）；交集（异动+重大资讯）→ 两区都有，预判综合归因 + 当日重大事件补充输入（已确认） |
| Tab | **全部 / 预判 / 溯源**：全部=所有卡；预判=有预判区的卡；溯源=有溯源区的卡（交集卡在两个 Tab 均出现） |
| 卡片样式 | 采用 event-catcher 的 Card 样式（股票名+代码+行业+标签+标题+底部按钮），弃用 ListCell 简单行 |
| 同股票多条情报 | 同股票多条 STOCK 事件在卡内折叠展示（卡内可展开事件列表），老师"综合在一起"诉求 |
| 异动监测时点 | **11:30 + 15:05 两次打点**（复用现有 `PriceMoveService`），移除盘中 5 秒轮询；**只影响自选股洞察溯源区，不影响 event_scrape 情报抓取节奏** |
| 涨停雷达 | **保留爬虫做涨停候选发现源，归因统一走 price 事件层**；`watchlist_insight` 的 limit_up_radar 类型退役 |
| 预判生成范围 | 当日有异动/涨停 **或** 有重大利好/利空资讯 的自选股（**并集**，去重后每只一张卡）；目标对象以 `Target(kind="stock", internal_id, code, name)` 维度过关（全局 §2.1），预判输入/画像 key 用 `internal_id`，不裸 symbol |
| 轻量预判定位 | **方案 B 已确认**：定时轻量预判（quick 模型，两次打点后触发），对并集股票每只生成条件化预判；交集股票按溯源逻辑（归因驱动 + 当日重大事件）。**对齐架构（全局 §3.2）**：本 Spec 的轻量预判 = 统一入口 `predict(target, snapshot)` 的**轻量化产出方**——场景 A（有归因）类比 **fast**（结构化溯源链→模板套用）、场景 B（仅资讯）类比 **slow**（生资讯→构造分支），但都收敛为 quick_think 单次，**不引入完整 PredictAgent/slow 多步推理** |
| 推送机制 | **保留通知中心逐条推送**（个股情报层，每重大事件一条通知，旧逻辑不动）；自选股洞察页聚合展示，两者不冲突 |
| 详情页完整研判 | 保留点击懒生成 + 当日缓存（不改为定时） |
| 实施方式 | **单人全量实施**（按 §7 分阶段）；预判 `conditions[]` 结构依赖条件化预判 Spec（另人实施），先按该 Spec 的 JSON 示例对齐，schema 定稿后校验字段 |

## 4. 后端改动（aistock-app-api + aistock-agent-py）

### 4.1 异动监测改两次打点

- 移除/停用 `PriceTriggerDetector` 盘中 5 秒轮询路径（`STOCK_TRACE_TRIGGER_ENABLED` 相关逻辑改为不再启用盘中轮询）。
- 以 `PriceMoveService.run('midday')`（11:30）与 `run('close')`（15:05）为**唯一**发现入口：
  - 两时点对自选股做价格判定（涨幅/跌幅达到阈值即建/更新 `stock_trace` 事件）。
  - 涨停判定并入：`midday`/`close` 打点时涨幅 ≥ 涨停阈值 → 该事件标记 `is_limit_up`（price 事件的涨停特例），不再单独走涨停雷达归因。
- 归因时机沿用现有"事件落定即入队"约束（`UNIQUE(event_id, trigger_revision, ...)` 幂等），落定只发生在两次打点路径。
- `settleActiveEvents()` 15:05 兜底保留，作为 close 打点的一部分。

### 4.2 涨停雷达 → price 事件层

- `LimitUpRadarCrawler` 保留爬取能力，但产物从"独立事件"改为"**涨停候选池**"：打点时将候选 symbol 喂给 price 事件层判定/合并。
- `watchlist_insight` 表 limit_up_radar 类型：**存量数据只读迁移**（历史记录保留展示），新事件不再写该类型。
- 事件模型扩展（`stock_trace` 事件增加字段）：
  - `forecast` JSONB：轻量预判（结构见 Spec A），由轻量预判任务回写。
  - `is_limit_up` boolean：涨停特例标记（替代原 limit_up_radar 语义）。

### 4.3 轻量预判任务（新，方案 B 已确认）

**定位**：自选股洞察卡片（一只股票一张卡）的条件化预判由定时轻量预判任务统一产出（quick 模型，非完整 alert agent 3 子 Agent 并行）。

> **架构对齐（✅ Target + 统一入口 + 验证反哺 + 闭环）**：
> - **Target 维度（全局 §2.1）**：单只股票的预判统一用 `Target(kind="stock", internal_id=ts_code, code=ts_code, name)` 对象（后端维护一个稳定的 symbol→ts_code 映射，`internal_id` 即带交易所后缀的 ts_code）；预判输入组装、画像 key 一律用 `internal_id`，前端卡片仍可用裸 code 展示。
> - **数据/快照走 TargetProfile（全局 §2.3）**：个股快照、日 K、成交量等来源经 `get_profile(target)` 读取（`snapshot_builder`/`kline_fetcher`），不写 `if stock` 分支。
> - **验证反哺（Spec B §2.2/§4.1）**：每只股票产出前**可选**调 `read_validation_profile(target, ...)`，命中率低则降档/降低 direction 置信，画像只作输入参考（不改 `prediction_status` 语义）。
> - **闭环通道（Spec A §4.4 / Spec B / Spec C）**：需纳入验证/迭代的自选股（首推异动股）经 **`light_predict` 通道**落 `prediction_records`（`source_type='light_predict'`）复用 16:00 验证 → 画像 → 迭代闭环；不落者仅停留 `forecast` 展示层。

- 触发时机：两次打点（11:30、15:05）后触发。
- **生成范围（并集，去重后每只一张卡）**：当日有异动/涨停 **或** 有重大利好/利空资讯（`ai_impact` ∈ 重大利好/重大利空）的自选股。
- **输入规则（已确认）**：
  - 有异动的股票（含交集）→ **按溯源逻辑**：输入 = 归因报告（归因驱动）+ **当日该股票重大利好/利空资讯（补充）** + 盘口快照。
  - 仅重大资讯、无异动的股票 → 按事件影响逻辑：输入 = 重大资讯 + 盘口快照。
- 内容：条件化预判摘要（结构见 Spec A 的 `conditions[]`），1–2 句。
- **落库（按打点 slot 分存）**：`forecast` 按 slot 存两份——`{ midday?: {...}, close?: {...} }`；有异动的股票写 `stock_trace.forecast`，仅重大资讯的股票写情报事件 forecast。**前端优先展示 close（收盘终版），盘中仅有 midday 时展示 midday**。
- 幂等：同一 (symbol / slot) 只生成一次；15:05 close 不覆盖 11:30 midday（各自保留，前端取最新）。
- token 控制：范围严格限定为并集（自选股子集），全市场不生成。

#### 4.3.1 预判过程（三段流水线）

```
Step 0 触发：11:30 / 15:05 打点后，目标集合 = 当日异动/涨停 ∪ 当日重大利好/利空 的自选股（去重）
Step 1 依据组装（确定性代码，零 LLM）：每只并行拉 [归因报告（若有）+ 重大资讯 + 盘口] → 精简特征串
Step 2 LLM 生成：quick_think 单次 + json_mode 结构化输出 conditions[]（Spec A / `PredictionCondition` schema）
Step 3 校验 + 落库：conditions 非空 / anchor 必含 horizon+threshold / ≥1 条含成交量条件
```

#### 4.3.2 预判依据（分场景，与大盘溯源机制对齐）

**场景 A：当日有异动/涨停的自选股（含交集）→ 归因驱动条件预判**

核心依据 = **自选股溯源报告**（对标大盘 `predict_from_trace` 的 trace 输入）：
- `attribution_status` / `confidence` / `primary_phrase`（主因）
- 主因链 nodes（stage/claim）+ 证据（evidence）
- 五层候选 verdict（company/sector/market/capital/technical）

**补充依据（已确认，交集必加）** = 当日该股票的重大利好/利空资讯：
- 标题 + 摘要 + `ai_impact`（与预判区覆盖的事件一致，防止只依赖归因窗口漏信息）

辅助上下文 = 盘口快照（对标大盘的 snapshot 输入）：
- `/internal/quote/:symbol`：最新价、涨跌幅、量比/换手
- `/internal/flow/:symbol`：主力净流入/流出
- `/internal/quote/:symbol/kline`：5/10 日均线、20 日高/低点

预判角度：**归因驱动 + 事件补充**——条件锚点来自归因结论（"主因是 XX → 若 XX 延续则…，若 XX 消退则…"），当日重大事件作为额外条件锚点。

**场景 B：仅重大利好/利空、无异动的自选股 → 事件影响预判**

依据：
- 重大资讯：标题 + 摘要 + `ai_impact`（重大利好/重大利空）
- 盘口快照（同上 quote/flow/kline）

预判角度：**事件影响持续性**——条件围绕事件兑现/落空、股价反应。

#### 4.3.2.1 事件时间窗口

| 场景 | "事件" | 时间窗口 |
|---|---|---|
| 场景 A（有异动，含交集） | ① 归因报告证据链（归因驱动）② **当日重大利好/利空资讯（补充输入）** | ① **归因采集窗口** = 事件冻结区间（`window_start_at` → `window_end_at`，由异动首次触发与最终修订决定）。窗口内证据**已含当日个股事件**：异动触发时经 event_triggered 模式采集当日东财个股情报（`collect_eastmoney_judgements`，symbol 关联的 news/announcement，company 层证据）。LLM 只允许引用 `occurred_at ≤ window_end_at` 的证据（prompt + `_strip_post_window_market_references` 双重约束）。② **当日为主**（08:45 盘前 + 每小时 intraday 抓到的事件） |
| 场景 B（仅重大资讯） | 重大利好/利空资讯 | **当日为主**（08:45 盘前 + 每小时 intraday 抓到的事件）；盘前无当日事件时回溯**近 3 个自然日**（覆盖周末/隔夜重大事件） |

> **重要澄清：事件抓取频率（每小时）≠ 预判生成频率（两次打点）**。事件按 08:45/10:00–14:00 每小时/15:05 入库，但预判只在 11:30、15:05 打点后批量生成：
> - **11:30 午盘预判**：消费上午事件（08:45 + 10:00 + 11:00），盘面 = 午盘实时 → 盘中条件预判（先行版）。
> - **15:05 收盘预判**：消费全天事件（含下午新增），盘面 = 收盘定格 → 收盘条件预判（终版，信息更全，前端优先展示）。

可选增强：大盘情绪温度（`sentiment_temp`，15:45），首批不接入。

#### 4.3.3 实现落点（复用现有先例，不造轮子）

- **新增 `aistock-agent-py/services/light_predictor.py`**：入口签名对齐统一入口 `predict(target, snapshot)`（全局 §3.2）——`run_light_prediction(target: Target, scenario_type, features, profile=None) -> ConditionalPrediction | None`（scenario_type ∈ `trace`/`intel`；`target` 为全局 `Target(kind="stock")`，内部读 `get_profile(target).snapshot_builder`/`kline_fetcher`，不 if-else `stock`；`profile` 为可选验证画像，供降档）。
  - 复用 `prediction_service.py` 的 `get_quick_think()` + `with_chat_structured_output`（json_mode）模式（对话内预测现成先例）。
  - **场景 A（有异动，含交集）**：输入 = 归因报告（五层候选 + 主因链 + primary_phrase）+ **当日重大利好/利空资讯（补充）** + 盘口快照——对标 `predict_from_trace(trace, snapshot)` 双输入 + 事件补充。
  - **场景 B（仅重大资讯）**：输入 = 重大资讯（标题/摘要/ai_impact，当日或近 3 日窗口）+ 盘口快照。
  - prompt 放 `prompts/workers/light_predict.py`（按 Spec A / `conditions[]` schema 指令）。
- **`scheduler.py` 注册两个任务**：11:30、15:05 打点后对目标集合批量跑（并发，单只失败不阻断）。
- **降级**：单只失败跳过 + warning 日志，不落库、不重试（对齐"LLM 失败跳过"硬约束）。

#### 4.3.4 轻量 vs 完整 AI 解读（token 对比）

| | 轻量条件化预判 | 完整 alert agent（AI 解读） |
|---|---|---|
| 模型 | quick_think 单次（json_mode） | deep_think + 3 子 Agent ReAct |
| 输入 | 预组装特征串 | 多轮工具调用 |
| 输出 | conditions[] 1–2 句 | 完整 display_report |
| token | ~几百 | 数千~上万 |
| 触发 | 定时批量（两次打点） | 用户点击 |

## 5. 前端改动（aistock-app-frontend）

### 5.1 自选股洞察页（AlertContent 自选股洞察块升级）

> **模块分工**：首页"提醒"Tab 的**自选股洞察块**升级为聚合卡（下方结构）；**个股情报块保留现状不动**（事件列表 + ai_impact 研判 + 通知中心逐条推送，`event-catcher.vue` 完整列表页保留）。

- 结构（**按股票聚合，一只股票一张卡**，卡内溯源区/预判区并行展示，按最近活动时间倒序）：
  ```
  提醒 Tab · 自选股洞察块
  ├── Segmented [全部 | 预判 | 溯源]
  └── 股票卡列表（一只股票一张卡）
      ├── 股票名 + 代码 + 行业 | [异动涨/跌] [利好/利空] 标签
      ├── 溯源区（当日有异动/涨停时必有）
      │    现象标题（涨停/异动）+ 溯源主因（归因结论）
      ├── 预判区（异动股票必有=归因驱动；仅重大资讯股票也有=事件影响）
      │    条件化预判摘要（conditions[] 前 2 条，close 优先 / 盘中 midday）
      ├── 情报事件列表（同股票多条折叠，点击展开）
      └── 最近活动时间 · [AI解读] 按钮
  ```
- 数据组装：并行拉 `stock_trace` 事件（溯源区）+ event_scrape STOCK 情报（预判区/情报折叠）→ **按 stock_code 分组** → 每只合成一张卡。
- Tab 逻辑：全部=所有卡；预判=有预判区的卡（异动股票 + 仅重大资讯股票）；溯源=有溯源区的卡（异动股票，含交集）；仅重大资讯股票只出现在"全部/预判"。
- 排序：按"最近活动时间"（异动打点时间 / 情报抓取时间取 max）倒序。
- **卡片点击（统一入口）**：卡片主体 → 合并后的**洞察详情页**（见 5.2，详情页按该股票数据动态渲染溯源区/预判区/情报列表）；"AI解读"按钮 → `alert-analysis`（完整 AI 研判，独立于卡片）。
- 推送：**通知中心逐条推送保留不动**（个股情报层，每重大事件一条通知），自选股洞察页负责聚合展示。
- `event-catcher.vue` 保留，作为**个股情报完整列表页**（不参与聚合改造）。

## 9. 风险与注意事项

- **盘中实时性下降**：异动/预判只在两个时点更新，需在 UI 标注打点时间，避免用户误以为实时。
- **watchlist_insight 存量数据**：只读迁移，历史 limit_up_radar 记录仍可查看。
- **轻量预判 token 控制**：范围严格限定为"异动 ∪ 重大资讯"自选股子集，全市场不生成，可控。
- **forecast slot 语义**：midday/close 分存不覆盖，前端需按"close 优先"规则取最新，避免展示过期盘中预判。
- 与条件化预判 Spec（全局 **Spec A**）×验证 Spec（**Spec B**）的边界：本 Spec 只负责"何时生成、生成谁、存哪"，预判**内容结构 `conditions[]` / 大盘预判 / 验证画像 / 迭代闭环**在 Spec A/B/C；本 Spec 的轻量预判只消费 `conditions[]` schema + 可选复用 `light_predict` 验证通道，**不重定义预判结构**（对齐全局 §5.1/§5.2）。
- **`light_predict` 不重复造表**：纳入验证的自选股复用 `prediction_records` 的 `light_predict` 通道，不新建表；是否全部自选股都进验证通道由 portrait 样本量决定（`sufficient_sample`），样本不足不硬塞（对齐 Spec C §8）。
