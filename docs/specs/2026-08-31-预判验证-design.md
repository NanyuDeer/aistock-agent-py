# 预判-验证（Prediction Validation）实现设计文档

> 日期：2026-08-31
> 状态：**实施中**（单人实施；P1-P6 已完成，run\_predict/chat 绑定已落地，morning 展示侧反哺已落地）
> 关联 Spec：`2026-08-31-四环三粒度复用架构-design.md`（**全局指导总纲，本 Spec 的约束来源**，见 §2.1 数据卫生画像 key + §5.2 个股数据源杠杆）、`2026-08-31-条件化预判改造-design.md`（本 Spec 的验证对象是条件化预判的产出；`conditions[]`/`condition_met`/`c{i}` key 以该 Spec 为准）、`2026-08-31-预判迭代改进-design.md`（验证结果作为迭代闭环输入）
> 涉及仓库：aistock-agent-py（核心，验证 skill + 到期验证接管）、aistock-app-api（prediction\_records 验证画像落库，若需）

## 1. 背景与目标

### 1.1 背景

项目预判链路（三个产出方共用 `PredictionResult`：对话 prediction skill、大盘 `predict_from_trace`、晨报 `morning_forecast`）即将完成条件化改造（`conditions[]`）。与之配套的**验证环节**现状是：

- **已有确定性验证引擎**：`prediction_validator.run_once()` 每日 16:00 cron 扫描到期记录，比对 kline 判 hit/miss/insufficient，回写 `verification`；`prediction_stats` 计算命中率/Wilson CI/baseline。

- **缺验证"解释层"**：验证结果只有结构化 entry（hit/miss + condition\_met），没有"为什么 miss / 失效模式是什么 / 对预判逻辑意味着什么"的可读结论。

- **缺验证与预判的绑定**：预判 skill 产出时不读取历史验证画像（除 A3 置信钳制的粗粒度命中率外），无法让"历史验证结果"反哺下一次预判。

- **无"验证 agent/skill"**：验证逻辑散落在 validator 服务中，不可被预判 skill 复用。

### 1.2 目标

1. **验证 skill 化**：新增可复用的验证 skill（确定性判定 + LLM 解释层），供预判四处产出方（run\_predict / run\_chat\_prediction / morning\_forecast / 轻量预判）在产出时同步调用。
2. **到期验证接管**：`run_once` 保留确定性判定引擎，但**回写后新增"验证画像"落库**（condition 级历史命中率、失效模式分类、condition\_met 分布），供预判 skill 读取 + 迭代闭环消费。
3. **验证反哺预判**：预判产出时读取该 target 的历史验证画像作为输入上下文（如"short 档条件历史命中率仅 20%"→ 预判自动降档/调整 direction 置信）。
4. **为迭代闭环提供输入**：验证画像落库后，`2026-08-31-预判迭代改进-design.md` 消费它做变体实验。

## 3. 设计决策（已确认）

| 决策点               | 结论                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| 验证 agent vs skill | **✅ 做成 skill，不设独立 agent**：预判 skill 多处复用、预判和验证不可分割；独立 agent 会破坏同步调用链。确定性判定仍走 `run_once` 代码，skill 只在其上做"解释层 + 画像读取" |
| 到期验证接管            | `run_once` **保留确定性引擎不重写**；接管 = 回写后新增"验证画像落库"（condition 级命中率/失效模式/condition\_met 分布）                               |
| LLM 介入范围          | 只做**解释层**（把 hit/miss + condition\_met + 失效模式汇总成可读结论），**判定永远走确定性代码**（对齐"LLM 产结构 + 确定性算判定"原则）                       |
| 画像存储              | 优先存 `prediction_stats` 扩展或新表（`prediction_validation_profile`），避免重复拉全量 verified 计算（现状 A3 每次拉 500 条）                |
| 与条件化 spec 边界      | 本 Spec 消费条件化 spec 的 `conditions[]`/`condition_met`/`c{i}` key；不重复定义 schema                                        |
| 前端                | 不新增页面；验证进度展示已由条件化 spec §4.3 覆盖                                                                                    |

## 4. 改造范围（aistock-agent-py 核心）

### 4.1 验证 Skill（新增 `skills/prediction_validation.py`）

**定位**：可复用的验证 skill，供预判产出方在产出时同步调用。三层结构：

```
┌─ 确定性判定层（复用，不重写）
│   prediction_validator._verify_horizon / _verify_conditions
│   → 到期 hit/miss + condition_met（condition 级）
├─ 画像读取层（新增）
│   read_validation_profile(target, horizon) → {hit_rate, n, ci, condition_met_rate, miss_patterns}
│   （缓存优先，避免每次拉全量 verified）
├─ 解释层（新增，LLM 仅此层介入）
│   explain_verification(profile, entries) → {summary, miss_reasons, condition_met_insights, prediction_implications}
└─ 反哺接口（新增）
    enrich_prediction_input(base_input, profile) → 把画像并入预判 LLM 输入上下文
```

**关键函数签名**：

```python
async def read_validation_profile(
    target: Target, horizon: str | None = None
) -> dict[str, object]:
    """读取 target 的历史验证画像（缓存优先，miss 时拉 verified 计算）。
    Returns: {target, hit_rate, n, ci, sufficient_sample, condition_met_rate,
              miss_patterns: [{pattern, count}], horizon_breakdown: {...}}"""

async def explain_verification(
    profile: dict[str, object],
    entries: list[dict[str, object]],
) -> dict[str, object]:
    """LLM 解释层：把画像汇总成可读结论。
    Returns: {summary, miss_reasons, condition_met_insights, prediction_implications}"""

def enrich_prediction_input(
    base_input: dict[str, object], profile: dict[str, object]
) -> dict[str, object]:
    """把验证画像并入预判 LLM 输入（纯函数，不改原 dict，返回新 dict）。
    新增 ``validation_profile`` 块（target/n/hit_rate/sufficient_sample/condition_met_rate），
    样本充足且命中率低时附 ``note``（"请降低置信/补充更严条件"）；只作输入参考，
    不改判定/不产交易指令/不覆盖 A3 置信钳制（红线对齐 §3）。"""
```

> **⚠️ Target 维度（✅ 对齐全局 §2/§5.2）**：`target` 是全局 `Target` 对象（非字符串），画像缓存键强制用 `target.internal_id`（不用 name/裸码，防板块改名断画像 + index/stock 码空间冲突）。`read_validation_profile` / `build_validation_profile` 内部一律用 `Target` 通行。
>
> **⚠️ Skill 契约（✅ 对齐全局 §4.1）**：`prediction_validation` 属四环 skill，目录下须带 `skill.yaml`（`name: prediction_validation` / `version` / `input_schema` / `output_schema`，schema 用 Pydantic 模型，非手写 dict）。`version` 供迭代环追踪"哪个版本产出/验证了预判"，与 `PredictionResult.schema_version`（Spec A §3.3，数据结构版本）**两个维度，不可混用**——skill 版本升 `v2` 不代表 schema 升 3.0，反之亦然。

**解释层 prompt**（`prompts/workers/prediction_validation.py`，新增）：

- 输入：画像（hit\_rate/n/ci/condition\_met\_rate/miss\_patterns）+ 到期 entries 摘要

- 输出：结构化 `{summary, miss_reasons, condition_met_insights, prediction_implications}`

- 硬约束：只解释验证结果，不改判定、不产交易指令、不覆盖 confidence（对齐 A2 佐证不改置信度原则）

### 4.2 到期验证接管（prediction\_validator.run\_once 改造）

- **保留**：确定性判定（\_verify\_horizon / \_verify\_conditions）、A1 early\_exit、wait 窗口、backfill。

- **新增**（`run_once` 收尾，`_report_stats` 之后）：

  1. 汇总本次验证的 entries → 更新**验证画像**（condition 级命中率、miss\_patterns、condition\_met 分布）；
  2. 画像按 target 维度落库（防 A3 每次拉 500 条的全量扫描）。

- **画像计算归属**：`prediction_stats` 扩展 `build_validation_profile(entries, target)`（纯函数），或新建 `validation_profile.py` 服务。

- **`condition_met` 两段语义（✅ 已落地，2026-09-16；agent-py `64b06b6`/`8230a64`/`b361764` + app-api `fa5c6b3`/`edb9941`）**：`condition_met` 由同一 16:00 `run_once` 内两段产出，**口径以条件化 Spec §4.2 为准**（本 Spec 只消费，不重复定义）：

  1. **第①段·到期前点亮**：`_scan_condition_met` 对 `due_date > today` 的 condition 取 **`[created_at, today]` 区间**日 K（`_condition_scan_range`：上限 120 自然日，越界裁剪到 `today-120d`；created_at 缺失同回退，未来脏值直接跳过不发请求；"最近 60 个交易日"只是取数后的判定尾部切片 `_CONDITION_SCAN_WINDOW`，非取数窗口——条件化 Spec §4.2 为准），条件一成立即回写 `verification[c{i}].condition_met=true`，**该 entry 不含 `result`**（Node PUT 已放行该中间态，否则 400）；判定纯函数 `condition_met_judge.judge_condition_met`（技术位严格前低/新高 + MA20/60 近似；涨跌幅/点位窗口累计，closes 优先、缺 close 回退 pct_chg 复利；可用数据点 < 2 恒不判定；**volume 类首批 omit**）。**只写 true 不写 false**：不成立/无法判定/数据源故障一律不产键（不写 `false`/`null`）。
  2. **第②段·到期 hit/miss 且保留点亮**：`_verify_conditions` 照常写 `c{i}` 的 `result`（hit/miss/insufficient），并**把①已点亮的 `condition_met=true` 原样带出**——Node 端 jsonb 为键级浅合并，但要防显式写 `null` 抹掉点亮值（早期实现 `base` 硬写 `condition_met: None`，已修）。

  幂等：已点亮 / 已有 `result` / `due_date <= today` 均跳过；两段共用既有 `prediction_validate` job（cron `0 16 * * 0-4`），**未新增 cron**；`c{i}` key 与 horizon key（A1 early_exit 按 horizon）并存互不覆盖。

- **`c{i}` entry 不参与 `status=verified`（既有事实，勿误判为回归）**：Node `PredictionRecordService.appendVerification` 的 `allVerified` 只遍历 `prediction.horizons[].horizon` 这三个**档位 key**、要求其 `result ∈ {hit,miss,insufficient}`；`c{i}` 条件 entry（含仅点亮 `condition_met` 的中间态）**不参与该判定**。故条件化预判的 `status` 仍由 horizon 档位决定，`c{i}` 只驱动：① 前端条件"条件成立"分支；② condition 级统计/画像（按 entry 是否含 `result` 计入，见 §4.1 `condition_met_rate`）。

### 4.3 预判产出方绑定（prediction\_service.py 改造）

- `run_chat_prediction`：产出前调 `read_validation_profile(target, ...)`，经 `enrich_prediction_input` 并入 LLM 输入；若画像 `sufficient_sample` 且命中率低，prompt 里提示"该 target 同类条件历史命中率低，请降低置信/补充条件"。✅ **已落地**（`_enrich_chat_input_with_profile` + `enrich_prediction_input`，有单测）。

- `run_predict`（大盘溯源）：trace 无单一 symbol，代表 target 取市场指数"上证指数"（`_MARKET_PROFILE_SYMBOL`，与 `prediction.horizons[].target` 归一化一致）→ `_enrich_market_predict_input` 并入画像。✅ **已落地**（有单测）。

- `morning_forecast`：摘要可带 `历史命中率：short 档 60%（n=50）`；**仅展示侧反哺，不落库 ⇒ 不进验证画像/迭代闭环**（Spec A §4.2 边界声明）。✅ **已落地**（`_enrich_morning_summary_with_profile`，写缓存后返回前调用，吃 market 画像 sufficient\_sample 时追加摘要，异常降级保持原文，有单测）。

- **红线**：画像只作为**输入参考**，不改 `prediction_status` 语义、不产交易指令、不覆盖 A3 置信钳制结果。

### 4.4 存储（aistock-app-api，若需）

- 优先方案：画像放 `prediction_stats` 已有统计出口（结构化日志 + 可选缓存键 `prediction:profile:{internal_id}`，**用 internal\_id 不用 name/裸码**），**不新建表**（避免 DB 迁移）。

- 若画像需长期查询，再考虑 `prediction_validation_profile` 表（target\_internal\_id PK，jsonb profile），本 Spec 默认不建。

### 4.5 验证数据源三粒度统一（✅ 对齐全局 §3.3 + §5.2）

**个股数据源接入是全盘杠杆最高的单一动作**（全局 §5.2）：同时解锁个股预判收敛（有验证才有闭环）、个股迭代挂载、三粒度矩阵第一个打穿。

| 数据源                | 现状                                         | 本 Spec 动作                                                                                                                         |
| ------------------ | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| index（指数日 K）       | ✓ `get_index_kline`                        | 不改                                                                                                                                |
| sector（板块日 K）      | ✓ `get_ths_daily_range`                    | 不改                                                                                                                                |
| stock（个股日 K + 成交量） | ✗ **未接**（`_fetch_kline_window` 无 stock 分支） | **接入**：`_fetch_kline_window` 补 stock 分支（`/internal/quote/:symbol/kline` 或 Tushare 个股日 K + 成交量），使 `condition_met` 的"量能/均线/价位"判定可落地 |

- **TargetProfile 约束**：数据源函数名走 `profile.kline_fetcher`（全局 §2.3，index/sector/stock 各自登记），`_fetch_kline_window` 不写 `if kind == ...`，改读 `get_profile(target.kind).kline_fetcher`。

- **实施时序**：个股数据源在 `conditions[]` schema 定稿后**立即并行启动**，不等 Spec A 完全收尾（全局 §6 杠杆判断）。

## 7. 测试要点

- `build_validation_profile`：空 entries / 单 target / condition\_met 分布 / miss\_patterns 归类。

- `read_validation_profile`：缓存命中 / 缓存失效拉取 / 数据源故障降级。

- `explain_verification`：LLM 输出 schema 校验（summary/miss\_reasons/condition\_met\_insights/prediction\_implications）、红线（不覆盖判定/不产交易指令）。

- `run_once` 接管：验证后画像落库；early\_exit-only 不影响画像（无 result 不计入）。

- 预判产出方绑定：画像并入输入不破坏 LLM 输出；命中率低时 prompt 生效（可断言 prompt 含画像摘要）。

- **对齐条件化 spec**：condition\_met/`c{i}` key 以条件化 spec 为准；验证 skill 与条件化 spec 的 `_verify_conditions` 共用画像数据源。

## 8. 风险与注意事项

- **拉取开销**：画像必须缓存（`prediction:profile:{target}`），避免每次预判拉全量 verified（现状 A3 已每次 500 条，反哺后频率更高，必须缓存）。

- **LLM 越权**：解释层 LLM 只解释、不判定；`_sanitize_llm_output` 同构清洗（对齐 iterate\_analyzer 经验）——LLM 输出的"结论"不得覆盖确定性 hit/miss。

- **与 A3 置信钳制关系**：画像反哺是"输入参考"（prompt 提示），A3 是"输出钳制"（confidence 覆盖）——两者正交，A3 不因画像引入而回退。

- **与迭代 spec 边界**：本 Spec 只产出画像；消费画像做变体实验属迭代 spec（`2026-08-31-预判迭代改进-design.md`），勿越界。

## 9. 执行前置清单

1. **依赖条件化 spec**：`conditions[]`/`condition_met`/`c{i}` key 定稿前，`build_validation_profile` 的 condition 级画像字段先用 `condition_met` 占位，schema 定稿后对齐。**✅ 已对齐（2026-09-16）**：`condition_met` 两段语义（含"只写 true 不写 false"与"`c{i}` 不参与 `status=verified`"）见 §4.2。

## 10. 生产验证测试报告 — 缺陷修复记录（2026-09-03）

> 依据 `2026-09-03-预判验证生产链路测试报告.md`（同事服务器实测）归档缺陷、决策与修复范围。测试方式：直连生产（只读审计 + 受控补验，未直接 SQL 写库）。**结论：16:00 到期验证每日触发但从未真正回写成功**（0 行 verification、11 条过期堆积）。

### 10.1 缺陷清单与归属

| #  | 缺陷                                                                                                                                     | 位置                                                           | 层           |
| -- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------- |
| D1 | `appendVerification` jsonb 合并 UPDATE 的 `$1`（horizon）参数类型无法推断 → **每次回写 HTTP 500**                                                       | `aistock-app-api` PredictionRecordService.appendVerification | Node        |
| D2 | Python `run_once` 以 `isinstance(record_id, int)` 门禁，Node internal 列表返回 **string id**（pg BIGSERIAL，仅 publicRouter 归一）→ 每条跳过，`updated=0` | agent-py↔Node 契约（internalRouter 列表未归一）                       | Python↔Node |

| D4 | `data_client.put()` 吞 5xx（返回 None 不抛）→ `updated` 虚增、"写失败"告警分支永不触发，D1 被静默                                                               | agent-py data\_client.py                                     | Python 观测   |

### 10.2 决策（2026-09-03，组长拍板）

- **D3 口径：以逻辑闭环为主，允许大改。** 画像/统计/回流的有效数据源改为**档位级扫描**——扫全部记录（不再限 `status=verified`）中**已有 result 的档位**，按 target+horizon 聚合；short/mid 到期即计入画像，不等待 long（2027）。`status` 字段保留全档完结语义（Node 判定不动），仅消费侧解耦。

- **D1/D2 修复顺序**：先 Node D1（SQL 参数 cast），再 Python D2（契约对齐），避免 D4 静默产生假日志。

- **D4 观测**：`put()` 失败返回结构化结果，`run_once`/`backfill` 依据真实回写结果计数与告警。

### 10.3 修复范围与增量注意（并入本 Spec 验收口径）

1. **D1**：SQL 显式收窄参数类型——`jsonb_build_object($1::text, COALESCE(verification->>$1, '{}')::jsonb || $2::jsonb)`（`->>` 取文本避免下标歧义）。存量单测 mock Service 层不触达 PG，需以**真实 PG 受控补验**为验收（PUT 1-2 条 due 过期档位回写 200）。
2. **D2 治本**：internalRouter 列表响应对齐 publicRouter 的 `id: Number(row.id)` 归一；**连带** Python cursor 分页（`isinstance(cursor,int)` 早退）与 `backfill_no_data` 的 `int(record["id"])` 均依赖 int——Python 侧同步兼容 `str|int` 双保险。
3. **D3 实现**：`_write_validation_profiles`/`_report_stats`/skill `read_validation_profile` 数据源改为 pending+verified 全记录档位级过滤（`verification` 各 entry 含 `result` 即计入），画像 `n>0` 后晨报后缀/迭代闭环/渠道B 才有输入。
4. **板块四环同受 D1–D3 影响**：`source_type='sector_prediction'` 走同一条回写链，是修复后画像/Cbis 回流最大数据输入，纳入修复后首轮验证范围。
5. **端到端验收**（修复后补验）：造/选一条 due 已过记录 → `run_once` → 验证落库 → 画像 `n>0` → 晨报后缀出现 → 迭代闭环有输入。
6. **回归纪律**：任何含 `$N` 未 cast 的 jsonb/`->`/`->>` 组合 SQL 合并前必须真实 PG 复现（跨仓联调缺口教训，同 memory #59）。
