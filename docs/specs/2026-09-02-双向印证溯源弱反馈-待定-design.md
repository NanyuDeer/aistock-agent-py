## 已确认的现状（本次讨论输入 ✅）

- **Spec Cbis 渠道B**：溯源归因时采到 `PredictionConfirmation`（场景/证据层印证），回流画像形成 `evidence_confirmed` 与 `scenario_harvest`，供预判反哺与迭代。
- **迭代双链路分离（总纲 §3.4）**：溯源迭代=归因监督式（历史切片 `evaluate_attribution`），预判迭代=验证驱动（`evaluate_verification`）。评分桶不得混用。
- **用户诉求**：希望双向印证不只能迭代预判，也能**提高溯源的准确性**。
- **范式定位判断**：Cbis 对溯源而言，既非监督式（无人工 gold label、无历史切片标准答案对照），也非纯无监督（不是纯结构自洽）。它应定位为**自监督 / 弱监督反馈**：用「这条客观事实被采集到了」当锚点 + 「预判场景」当隐式靶标，系统自己给自己造出可比的信号。

## 1. 背景与目标

### 1.1 背景

Cbis 渠道B信号的**评价对象是预判**（"预判场景假设是否被现实印证"），据此驱动预判迭代。但渠道B的信号**源头在溯源**（`evidence_confirmed.source_trace_id` 指向溯源产物，证据是溯源归因时采集到的）。既然溯源是事实的发现者，而渠道B恰好暴露了一批"被现实/被预判交叉关注的客观事实"，很自然的追问是：**这批事实能不能反向校准溯源自己？**

### 1.2 问题本质与缺口

| 缺口 | 现状 | 本 Spec 目标 |
|---|---|---|
| 溯源提高准确性只有一条路 | 历史切片监督式迭代（`evaluate_attribution`），需人工/事后标注，成本高、时效慢 | 补一条**轻量、自监督**的溯源弱反馈旁路，不依赖人工标注 |
| 渠道B信号只喂预判 | `scenario_harvest` 只进入预判反哺与预判迭代 | 复用同一信号，**分成三条溯源侧弱反馈动作**（证据提权 / 检索盲区反哺 / 置信度微调） |
| 溯源已知的"事实重要性"没被用上 | 归因对证据的权重/排序与事实是否被市场持续关注无关 | 被历史预判高频指向的已采事实，在归因中提权（只调权，不改因果方向） |

### 1.3 范式定位（关键决策，先钉死语义）

**Cbis 对溯源 = 自监督 / 弱监督反馈，不是监督式，也不是纯无监督。**

- **不是监督式**：没有人工 gold label，也没有历史切片那种"标准答案对照"。
- **不是纯无监督**：它不是靠结构自洽（如把归因结论聚类看一致性），而是有明确锚点——「事实被采集」+「预判场景」构成隐式靶标，系统自己造 target。
- **是自监督反馈**：介于两者之间，指"用自产信号校正自身产出"，且**只用于事实重要性/覆盖度，不用于因果正确性判定**。

> 设计时必须坚持：**Cbis 对溯源是"软反馈"，不是"硬监督标签"。** 避免把它误写成第二套归因 gold label。

## 2. 关键决策（已确认 ✅）

| 决策点 | 结论 |
|---|---|
| 信号复用 | **复用 Cbis 渠道B产物，不新增采集点、不重复采证据**。溯源只多一层"消费自己采到的事实 + scenario_harvest"的弱反馈逻辑 |
| 评价对象 | **落在"事实重要性 / 覆盖度"，不落在"因果正确性"**。预判被印证只证明"市场确实在演绎这个因素"，证明不了"归因把它当主因是因果正确的" |
| 迭代定位 | **独立松耦合旁路**，不并入归因监督桶（`evaluate_attribution`），也不并入验证评分桶（`evaluate_verification`）。溯源迭代仍以历史切片监督式为主线，本弱反馈只补充维度 |
| 动作收敛 | 只做三条：① 证据提权 ② 检索盲区反哺 ③ 置信度微调（见 §3） |
| 触发方式 | 沿用现有事件链 + cron，不新增独立触发；随溯源归因跑批和迭代评估时机 |
| 是否可逆/回滚 | 弱反馈只影响权重/排序/置信，不硬改归因结论文本；验证能力生效不再，退化为现状即可 |

### 2.1 红线 / 边界

- **量错对象红线**：严禁落地成"体现 → 溯源因果正确"。不得把渠道B当归因的 gold label，不得让 Cbis 信号进入 `evaluate_attribution` 的标题统计。
- **双链路分离红线（总纲 §3.4）**：弱反馈是第三条"旁路"，不并入归因评分桶、不并入验证评分桶。
- **不改 Cbis 既有实现**：采集点、画像字段、预判反哺接口全部保持原样；本 Spec 只在"Cbis 画像产出之后"追加消费逻辑。
- **不强归因**：证据提权只调权重/排序，不重写 `CausalChain` 的因果方向或 stage 结构。

## 3. 设计决策落地（三条弱反馈动作）

> 落地形态按**由低风险到高风险**排序，实施时可视情况只做 ①② 或全做。

### 3.1 动作① 证据提权（证据重要性 → 归因权重/排序）

**原理**：一个事实被溯源采集之后，又被历史预判场景多次循环指向，说明它是**市场正在持续演绎的活跃因素**（供需/情绪的公共焦点），这类事实在归因中应比"一次性、孤立的事实"权重更高。

**落点**：溯源归因的证据打分/排序阶段，对 `evidence`（或证据来源条）增加一档"被印证权重"：

```python
def evidence_importance_boost(
    evidence_source_id: str,
    scenario_harvest: dict,   # 复用 Cbis 画像 scenario_harvest.confirmed
) -> float:
    """按被印证次数上调证据权重系数（0..1 之外的同源系数，供归因证据加权）。"""
    # 仅用于证据重要性加权，不许改动因果链方向 / stage（红线 §2.1）
    n = scenario_harvest.get("confirmed", {}).get(evidence_source_id, 0)
    return min(1.0 + 0.1 * n, 1.6)
```

**只调权，不改因果**：权重系数只进证据排序/加权计算，不改 `CausalChain` 的 `nodes` / stage 结构。

### 3.2 动作② 检索盲区反哺（高频预判场景 → 溯源检索覆盖）

**原理**：某预判场景被反复设定、却从未被溯源采到的证据印证（`scenario_harvest.unconfirmed` 可见、或 `evidence_confirmed` 长期为空），提示**该题材/板块的溯源检索存在盲区**——不是市场没这个逻辑，是溯源没搜到相关证据。

**落点**：溯源归因的检索词 / 覆盖范围生成，加入"盲区场景"提示：

```python
def coverage_gaps(scenario_harvest: dict) -> list[str]:
    """未确认场景 → 溯源检索盲区提示（feed 定向 query / 覆盖范围）。"""
    unconfirmed = scenario_harvest.get("unconfirmed", {})
    # 只对"反复预判却从未被印证"的场景告警，防止单次噪声
    return [sc for sc, c in unconfirmed.items() if c >= MIN_PREDICTION_COUNT]
```

**衔接点**：与板块溯源（Spec D）的定向 query 天然衔接——盲区场景可映射为补充检索词。若 Spec D 未实施，本动作在 index 溯源同样适用。

### 3.3 动作③ 置信度微调（印证多 → 置信上调）

**原理**：被现实多次印证的场景对应的因子，其归因置信度可上调一档；从未被印证（从不挂回显信号）时保守化。

**落点**：归因置信度打分辅助：

```python
def adjust_trace_confidence(
    base: float,
    confirmed_hits: int,
    unconfirmed_hits: int,
) -> float:
    """弱反馈置信微调：印证多上调、空白保守，只动附件不动因果结论。"""
    # 红线：不改 attribution_status 的语义（confirmed/hypothesis 判定仍走既有 `CausalChain` 校验）
    return base * (1.0 + 0.05 * min(confirmed_hits, 4)) * (0.95 if unconfirmed_hits else 1.0)
```

**注意**：`attribution_status`（sufficient/insufficient、confirmed/hypothesis）语义不变，只在上报/排名的输出置信上浮动，供展示与迭代排序参考，不作为校验通过/失败依据。

## 4. 消费链路（数据流）

```text
Cbis 画像（evidence_confirmed / scenario_harvest）
        │  （追加消费层，Cbis 实现不动）
        ├─→ ① 证据提权：归因证据排序/加权
        ├─→ ② 检索盲区反哺：溯源检索词/覆盖
        └─→ ③ 置信度微调：归因输出置信浮动
              │
              ▼
      溯源迭代评估（仍历史切片监督式为主线）+ 展示
```

## 5. 验收清单（仅当实施时用；当前为待定）

- [ ] 三条动作各有确定性纯函数测试（证据提权 / 覆盖盲区 / 置信微调），红线用例覆盖"不改因果方向"
- [ ] 不修改 Cbis 采集点与画像字段；不修改 `evaluate_attribution` / `evaluate_verification` 评分逻辑
- [ ] 弱反馈不进入归因 / 验证评分桶（用测试证明信号被隔离）
- [ ] 回归全绿：`tests/unit` 相关 + 溯源既有测试 + Cbis 既有测试

## 6. 非目标（本 Spec 明确不做）

- **不做因果正确性监督**：不把渠道B写成第二套归因 gold label。
- **不改 Cbis 既有实现**：不重开采集点，不重定义画像字段。
- **不并入评分桶**：不作为 `evaluate_attribution` / `evaluate_verification` 的输入。
- **不新增迭代链路**：仍是旁路弱反馈，溯源迭代主线还是历史切片监督式。
- **不强归因**：不重写因果链方向 / stage。
- **不新增调度**：不新增触发方式。

## 7. 待定项 / 实施前评估点

> 本 Spec 为待定，以下问题不在此刻决策，实施前必须再评估：

1. **证据提权的收益信噪比**：被印证次数与归因质量提升是否真的正相关？需先用离线数据验证假设，避免把"常见题材=高权重"变成一种廉价热门度优先。
2. **盲区反哺的误报**：`unconfirmed` 目前 Cbis 中是**预留空字段**（Spec Cbis §5.2 已说明需"预判侧主动探针"补齐）。实施前需先补 `unconfirmed` 采集，否则动作②无输入。
3. **置信微调的必要性**：是否值得单独做（可能增益小、耦合 `attribution_status` 语义）？可优先权衡只落地 ①②。
4. **跨仓库影响**：是否涉及 Node 端报告展示/排序，实施前锁定改动面。
