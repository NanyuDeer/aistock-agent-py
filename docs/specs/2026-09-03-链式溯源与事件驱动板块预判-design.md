## 1. 背景与动机（v3 修订）

- **M1 预判依据局限**（修订 v2）：每日批量预判本身保留，但依据仅行情/资金/榜单，**未纳入事件影响**——"发生了什么"与"预判怎么做"脱节。
- **M4 缺少"大盘-板块-事件"链式根因视图**（保留）：大盘归因、板块溯源、事件三者各自产出、未贯通；多板块共同驱动时只下钻单主因板块；"板块被大盘带还是驱动大盘"无方向标记。
- **M2/M3 明确本期不解决**：同板块跨日预判可能方向并存（"跨日冲突"）、验证时点定死——原计划靠事件驱动模型（在途唯一 + 不定死窗口）解决，**随事件驱动方案否决而本期不处理**，留作后续候选（§9）。
- **M5/M6/M7 作废**：双向印证不对称、事件事实无链式载体、印证未接回迭代——均以"事件驱动预判"为前提，前提消失后不再成立；Cbis 现状（渠道B 覆盖链式溯源）维持不变。

## 2. 定位与目标（重写）

### 2.1 两轨分离（v3 核心原则）

| | 轨道 A｜风口龙头（榜单） | 轨道 B｜大盘溯源链 |
|---|---|---|
| 做什么 | **只做每日预判**（现有节奏，19:30 批量） | **只做链式传导溯源**（大盘→主驱动板块→事件） |
| 不做什么 | 不做溯源 | **不做预判**（不在榜单的溯源板块不跑预判） |
| 本期要改 | **预判依据增强**（注入事件影响，§4） | **事件层**：中台优先 + 检索补漏，追溯到最本质事件（§3） |
| 展示 | 板块四环/板块详情（沿用现有每日卡形态） | 市场洞见页「今日影响大盘的主要板块」溯源卡列表（§7） |

- 两轨**数据上互通、在职责上隔离**：轨道 B 的链上事件与归因结果是轨道 A 预判依据的一部分（§4.2）；轨道 A 的预判结果不回写轨道 B（避免"预判驱动溯源"的循环）。
- **榜单板块若同在链上**：市场洞见卡仍只展示溯源（§7.2），预判结果由板块详情/板块四环承载，两处不混排。

### 2.2 定位（第一性）

- **溯源环产出** = 当日"大盘-板块-事件"链式归因树，回答"大盘为什么动、谁在驱动、根因是什么事"。**事件要追到最本质的那件事**（不是只抓到表层新闻）。
- **预判环产出** = 每日对风口榜单板块的方向预判，依据 = 行情/资金 + **事件影响**；不绑定事件生命周期。

### 2.3 验收口径（G）

- **G1 链**：每个大盘异动交易日产出归因树；多板块共同驱动时多主驱动板块全入链。
- **G2 方向标记**：板块节点带 `self_driven | market_follow`。
- **G3 事件到根**：链的板块节点带事件层，事件引用中台事件 `event_id`；溯源到的板块**强制走检索补漏**，追溯到最本质事件；无法确认时如实标"未确认根因"。
- **G4 依据增强**：每日预判的输入含事件影响（链上事件 + 中台相关事件），且留痕可审计（注入了哪些事件）。
- **G5 两轨隔离**：溯源板块不产预判；风口榜单板块的预判不引入溯源专属字段（事件前提/在途状态）。
- **G6 展示**：市场洞见页出现「今日影响大盘的主要板块」溯源卡列表（不在风口榜的板块也能看到）；大盘/板块详情链树含事件节点。
- **G7 兼容**：无链日、无事件匹配日，预判与展示均降级到现状，不报错、不空壳。
- **G8 预判卡**：卡片形态与展示规则以 `2026-09-03-洞见卡Label字段与预判卡重构-design.md`（含 2026-09-16 §7 决议）为准。

### 2.4 非目标

- 不做事件驱动预判（触发源改事件、在途唯一、不定死窗口、Pre/Post 分流）。
- 不建事件事实链（阶段/进展/终局状态机）与检索状态机。
- 不改大盘/个股预判内部生成逻辑（沿用 R8"不平凡"口径）。
- 不做事件的语义 Merge（沿用 Event Entity 方案边界：`canonical_event_key` 只做确定性幂等）。
- 不做盘中实时链路、不重建事件库。

## 3. P1 链式溯源（v3 修订）

### 3.1 已落地基线（P1a/P1b，2026-09-04）

| 项 | 已实现 | 证据 |
|---|---|---|
| 大盘→板块 | `extract_primary_sectors`（单→多，跌方 losers 优先）、多板块并行 `run_sector_trace`、父链引用 `attribution_parent` | agent-py `sector_trace.py`、`event_consumers.py` |
| 方向标记 | `judge_sector_driver_relation` 出 `self_driven/market_follow` | 同上 |
| 链树组装与落库 | `assemble_attribution_chain` + `POST /internal/attribution-chain` upsert `attribution_chains` | agent-py `attribution_chain.py`、app-api `attributionChainRouter.ts` |
| 读取与展示 | `GET /api/agent/attribution-chain/:date`；大盘溯源页链视图；板块详情洞见卡溯源行（大盘联动） | app-frontend `AttributionChainView.vue`、`SectorInsightCard.vue` |

**未完成**：链的事件层（板块→事件）、链树节点结构（`node_type/ref_id/parent_id/event_id`）、市场洞见主驱动板块列表。

### 3.2 改造（v3 口径）

1. **大盘归因输出主驱动板块集合**（保留 v2）：`primary_sectors: [{sector, contribution, direction, is_sector_driven}]`；大盘非板块驱动时为空并停在大盘事件层，不强行下钻；旧记录回退单板块行为。
2. **链式下钻**（保留 v2）：对 `primary_sectors` 逐个 `run_sector_trace`，板块 trace 带父链引用，建立显式父子关系。
3. **方向标记**（保留 v2）：`self_driven | market_follow`；跟随板块保留在链上（follow 标记）。
4. **事件层（v3 新口径）**：
   - 来源顺序：**先事件抓取中台存量事件**（按板块别名/关键词/实体匹配）→ **再检索补漏**（复用大盘溯源同款的事件检索逻辑）。
   - **溯源到的板块一律强制走检索补漏**，目标是**追溯到最本质的事件**（而非停在表层新闻转载）；补漏仍无结果时，事件节点标"未确认根因"，不编造。
   - **存储**：事件节点**直接引用中台事件 id**（`event_id` / `source_event_id`），仅记录 `source: 中台命中 | 检索补漏` 与一句话摘要；**不新建事件表、不做事件事实链与终局状态机**（原 v2 §3.4 的 `event_chains` 作废）。
   - 去重口径：同一现实事件不产生多个事件节点（`canonical_event_key` 幂等优先，其次 embedding 相似度），判定留痕（命中率/相似分）供调参。
5. **链树落库与结构（修订 v2）**：`attribution_chains` 节点集扩展为三层结构 —— `{node_type: market|sector|event, ref_id, parent_id, self_driven?, event_id?, source?, headline}`；大盘/板块层沿用现有 JSON 结构向后兼容（旧记录无事件层 → 前端按无事件渲染）。
6. **展示**（§7）：大盘详情/市场洞见渲染链树（事件节点可跳事件原文）；市场洞见页主驱动板块**溯源卡列表**。

### 3.3 调度（保留 v2）

链式溯源在 `review_full`（18:30）完成后串联（`review_done` 事件总线）：多板块链式下钻 + 事件层一步；19:30 前完成，供预判依据读取。交易日守卫、数据就绪守卫沿用。

### 3.4 与事件中台 / Event Entity 的对接口径

| 项 | 口径 |
|---|---|
| 事件身份 | 一律引用中台事件 id；若该事件已物化到 Event Entity，则同时记录 `app_event_id`（用于跳时间线与去重） |
| 时间/状态 | 只消费不改写；Event Entity 的 `event_status`（scheduled/upcoming/ongoing/occurred）**不作预判档位的触发/生命周期依据**（预判仍每日批量）；**但事件类条件的成立判定以其状态迁移作确定性锚**（见 §12.4，本章口径优先） |
| 覆盖缺口 | Event Entity P0 只物化"新闻中带绝对日期"的事件，Calendar→Entity 物化属对齐 P0.5 未落地 → 本 spec **不依赖**其物化程度：事件层以中台存量 + 检索补漏为准 |
| 排除项 | 不使用 `impact_scale`/`chain_stages`/`tracking_queries`/终局状态机（随事件驱动预判作废）；不引入 Pre/Post 分流 |

## 4. 预判依据增强（替代 v2 §4 事件驱动预判）

### 4.1 节奏与触发（不变）

- 每日 19:30 批量预判照旧（风口榜单板块，现有 `sector_wind` / `predict_sector` 口径与白名单不动）。
- 触发集合**不含**溯源板块（两轨分离，§2.1）；不做 Event Entity 驱动、不做强异动兜底特设触发。

### 4.2 依据增强（本期核心）

在现有输入基础上增加"事件影响"一层：

| 来源 | 内容 | 用途 |
|---|---|---|
| 链上事件 | 该板块在当日链上的事件节点（`event_id` + 一句话 + 来源标记） | 主依据（有链必用） |
| 中台相关事件 | 当日/近日与板块相关的中台事件（别名/关键词/实体匹配，含检索补漏命中） | 补充依据（无链时仍有事件视角） |
| 大盘归因结论 | 当日 `attribution_summary` + 大盘指数涨跌 | 上下文（区分"跟随大盘"与"事件驱动"） |
| **验证画像**（2026-09-17 补） | 该板块的 `validation_profile`（`read_validation_profile(target, horizon)`） | 依据（对齐大盘；对齐方式见 §13.4） |

> **时序前置（必须，见 §13.1）**：本节的"链上事件"要求预判输入时**当日链已组装完成**；当前生产时序相反（链在级联预判之后才组装），落地本节前必须先解决 §13.1 的时序约束，否则级联路径取不到当日链。

- **输入侧扩展**：prompt 注入上述事件上下文，并要求预判结果**说明是否受事件驱动**；**输出侧不改结构**（沿用现有 `PredictionResult` + `label` 字段，见 `2026-09-03-洞见卡Label字段与预判卡重构-design.md`）。
- **留痕**：每条预判记录其注入的事件 id 列表（供审计与后续效果归因），不新增业务语义字段。

### 4.3 明确不引入（随 v2 §4 内容作废）

事件前提字段 `event_context`；`stance_relation`/`termination_reason`/`prev_prediction_ref`；同板块同档"在途唯一"与"事件进展条件"语义；两段验证（事件进展点亮 + 提前兑现 + 尘埃落定）；窗口不定死（开预判起算改造）；Pre/Post 分流；`predictions-active`（方向 C）。

### 4.4 成本与上限

- 每板块注入事件条数设上限（建议 ≤5 条，含链上事件优先）。
- 检索补漏按板块计次，设每日上限 + 缓存（复用既有搜索缓存），避免成本失控。
- 无事件匹配日：维持现状预判（不降级、不报错）。

### 4.5 与验证/迭代的关系

验证与迭代**完全沿用现状**（Spec C 渠道A：档位到期回填 hit/miss；Cbis 渠道B 事实验证回流不变）。本期不因事件注入改变验证口径。

## 7. 前端（重写）

### 7.1 市场洞见页（`modules/analytics/pages/traceability.vue`）

**改造现有「主因板块 · 板块研判」区块**为「**今日影响大盘的主要板块**」（不新建区块）。

- 每卡内容：板块名 + 角色徽（自驱动 / 跟随大盘）+ 涨跌幅 + 驱动事件（事件节点，可跳事件原文）+ 一句话原因 + 「依据详情 ▾」（展开板块自身链，见 §7.3）；**去掉原区块的预判内容**（两轨分离，§2.1）。

- 与现有内容关系：MarketInsightCard（大盘洞见）之下、归因链树视图之上；链视图本身保留（可看全链）。
- 跟随板块无事件节点时只显示角色徽 + 一句话原因，不硬编事件。

### 7.2 大盘详情 / 大盘溯源页

## 10. 风险与开放问题

- **R1 事件匹配噪声**：板块别名/关键词匹配可能把不相关事件挂上链（误关联），或漏掉真根因。缓解：中台优先 + 强制补漏 + 去重留痕 + 每板块事件条数上限；标注"未确认根因"而非硬挂。
- **R2 检索补漏成本**：溯源板块强制补漏，按板块数计费。缓解：每日检索次数上限 + 缓存 + 交易日守卫。
- **R3 预判 token 成本**：每日批量 + 事件上下文注入，输入量上升；缓解：条数上限、无匹配维持现状。
- **R4 覆盖率**：非榜单溯源板块不预判（产品决策），用户只能看到溯源；靠市场洞见溯源卡承接，验收时确认接受度。
- **R5 与 Event Entity 的边界漂移**：对方 P0.5/P1 可能引入 Calendar 物化、语义 Merge、Pre/Post 分流。本 spec 不依赖其物化程度，**但事件类条件判定要消费其 `event_status` 迁移作锚**（§12.4），对方若调整状态口径需回对版（避免两套语义）。
- **R6 数据就绪守卫**（保留 v2 R7）：板块日行情 refresh 失败时降级告警，不静默用旧数据推进。
- **R7 大盘/个股不平凡**（保留 R8）。
- **R8–R10（条件触发与验证闭环）**：见 §12.7：覆盖率（2026-09-17 实测记录级 5.5%）、误点亮不可撤回、未成立态缺失。
- **R11 链与预判时序**（§13.1，**最高优先级风险**）：链在级联预判**之后**才组装（`event_consumers.py:485 与 :487-497` vs `:472-476`）→ 不先解决时序，P2' 的依据增强对级联路径**完全无效**。缓解：P0' 作为 P2' 的硬前置。

## 12. 条件触发与验证闭环（2026-09-17 追加，含实测依据）

> 动机：条件化预判的"条件是否成立"此前从未真正落地（`prediction_validator._verify_conditions` 中 `condition_met` 恒写 `null`，注释"两段判定推迟 §9-5"）。2026-09-17 已实现两段判定的最小闭环（到期前确定性点亮 + 到期保留），但**实测覆盖率仅 5.5%**，故本章把缺口写入基线。

### 12.1 已落地基线（2026-09-17，代码层）

- 判定：`services/condition_met_judge.py`（技术位 MA20/60 + 严格前低/新高；涨跌幅/点位用 `threshold`；**含点位数字或 volume 词一律不判**）。
- 扫描：`_scan_condition_met`（到期前、窗口 `[created_at, today]` 上限 120 自然日、空窗不发请求、按 `(target_type, code, 窗口)` 记忆化），成立写 `condition_met=true`（**不改 `result`**，只写 true）。
- 到期：`_verify_conditions` 写 `result`（hit/miss/insufficient）并**保留**已点亮的 `condition_met`。
- 链路：Node PUT 放行"`condition_met===true` + `condition_index` 整数 + 无 `result`"的中间态；板块日 K 端点已补 `close/vol`；前端按 `conditions[].met` 渲染折叠/已触发/到期未触发三态。

### 12.2 覆盖率实测（2026-09-17，a 的依据）

- **样本**：服务器生产库 `schema_version='3.0'` 记录 **146 条**（`sector_prediction` 137 / `market_trace` 9），conditions **326 条**。
- **按条件文本分类**：含成交量口径（成交额/缩量/量能）**316 条 = 96.9%**（现状不判）｜纯涨跌幅类 8 条 = 2.5%（可判）｜明示技术位 1 条 = 0.3%｜含点位 1 条 = 0.3%（不判）。
- **记录级**：仅 **8/146 = 5.5%** 至少有一条条件可判 → 不补本节能力，结论模式将长期停留在折叠态。
- **脱节证据**：`anchor.metric` 分布恒为 `close`(312)/`index_close`(14)，而条件文本里写的是成交额/参考位 → 生成侧与判定侧口径不一致；`threshold` 无缺失（0%）。
- 抽样另见大量参考位表述（"跌破今日盘中低点 / 站上今日高点 / 跌破今日开盘价 / 站稳20日均线"）——日 K 上拿不到"今日盘中低点/今开"，当前判定层无法处理。

### 12.3 条件可判定性契约（a，完整力度）

1. **`anchor` 扩展**（生成侧约束 + 兼容旧记录缺省）：
   - `metric ∈ {close, index_close, volume, amount, ma20, ma60, prior_low, prior_high, today_open, today_high, today_low}`
   - `op ∈ {gte, lte, above, below, cross_above, cross_below}`
   - `level: number`（数值阈值，与用于涨跌幅的 `threshold` 百分比并存）
   - 生成侧硬约束：每条条件**至少映射到一个可判定维度**；无法映射者必须由归一化层降级为 `unjudgeable`。
2. **判定层按 `condition_type` 分流**：
   - `market`：① 涨跌幅（`threshold` + `direction`，窗口累计）② 技术位（`ma20/ma60/prior_low/prior_high`）③ **成交量**（`volume/amount` 与 `level` 按 `op` 比较；窗口取最大/均值，口径写入实现）④ **参考位**（`today_open/high/low`，需取数层补当日行）
   - `event`：见 12.4
   - `unjudgeable`：显式 `met: null` → 前端显示**「无法判定」**（不再等同"未触发"）
3. **同源维护**：`anchor` 维度枚举由判定层与生成 prompt 共用一份定义，禁止两侧各写一套（防再次脱节）。

### 12.4 事件类条件三层判定（当前样本 0 条，事件驱动方向会引入）

| 层 | 判定方式 | 确定性 | 适用条件文本 |
|---|---|---|---|
| ① 状态锚 | 消费 Event Entity `event_status` 迁移（scheduled/upcoming → ongoing/occurred）→ 自动点亮；条件需带 `event_ref`（事件 id） | 确定性 | "若事件落地/正式实施/会议结果公布" |
| ② 受限 LLM | 仅事件类；输入限定"事件标题 + 进展摘要 + 条件文本"，输出 `true/false/unknown` + 置信；低置信走 `unjudgeable`；每次判定留痕（prompt 版本、事件 id、结论） | 半确定性 | "若细则落地并扩散至产业链" |
| ③ 兜底 | `met: null`（无法判定） | — | 无法量化且无事件可锚 |

> 口径修订：§3.4 原写"不使用 Event Entity 的状态机"——**仅对预判档位的触发/生命周期仍不使用**；事件类条件的成立判定**改用其状态迁移作锚**（本章为准）。

### 12.5 未成立态表达（b）

- 现状：只写 `true` → "到期未触发"与"在途未触发"前端不可区分（现以卡级 `verification=miss` 近似到档）。
- 目标：**到期（`result` 落库那一刻）对未触发的条件写 `condition_met=false` + `checked_at`**；到期前保持只写 true。
- 影响面：Node PUT 放行条件从"仅 true"回调为"布尔 + `condition_index` 整数"；`condition_met_rate` 恢复可算（false 进分母）；前端无需改（已按"存在布尔 met"与 `lit` 分流）。
- 观感：到期且全未成立 → 结论态空态「条件未成立 · 暂无已验证结论」（已有结论）；与"未触发折叠"（仍在途）是两种 UI。

### 12.6 历史回溯补算（c）

- 现状：`run_once` 只扫 `status='pending'`；已 `verified` 记录不再被扫 → 存量记录条件永远无 `met`（实测 88 条 entry 全无布尔 `condition_met`）。
- 方案：一次性任务 `backfill_condition_met`（离线、可重入、限速）：① 扫 3.0 的 `verification` 中 `c{i}` 与无布尔 `condition_met` 的记录；② 按 §12.3/12.4 判定（窗口以 `created_at` 起，上限 120 自然日）；③ 幂等只补 `condition_met`，不覆盖已有 `result`；④ 输出统计（扫描/点亮/不可判定）。
- 边界：与 `backfill_no_data` 同款（独立入口、只读扫描、可控写回）；**不改** `status` 语义。

### 12.7 排期与风险补充

- 新增排期：**P4' 条件可判定性契约**（§12.3 + §12.4，**优先级高**）、**P5' 未成立态 + 历史回溯**（§12.5 + §12.6）。两者均以 §12.2 实测为前提。
- 新增风险：
  - **R8 覆盖率**（实测 5.5%）：不补 P4' 则结论模式长期折叠。
  - **R9 误点亮不可撤回**（只写 true + jsonb 键级浅合并无删键）：判定宁可 `null` 不可误判；补 P4' 时同时补最小样本守卫与误点亮回滚预案。
  - **R10 未成立态缺失**：由 §12.5 收口；在此之前前端"未命中"标签为卡级近似。
- 部署顺序：条件判定跨 agent-py 与 app-api（PUT 放行/板块日 K 字段）→ **app-api 先行**，否则中间态写入被 400 拒绝。

## 13. 闭环补全（2026-09-17 追加，落地完 §3/§4/§7/§12 仍缺的 4 处）

> 判定标准：闭环 = 溯源 → 事件 → 预判依据 → 预判 → 条件触发 → 验证 → 回流，且每一环的数据**在生产路径上真实可达**。下列 4 项是 §3/§4/§7/§12 全落地后仍存在的断点。

### 13.1 链与预判的时序约束（关键）

- **问题**：§4.2 假设"预判输入时当日链已存在"，但生产时序相反——链在 `SectorTraceConsumer` 的 `asyncio.gather` **之后**才组装（`services/event_consumers.py:485 与 :487-497`），而**级联板块预判在 gather 内部已执行完**（`:472-476`）。→ 即使完成 P2'，级联路径**拿不到当日链**，依据增强对该路径无效。
- **方案（二选一，实施时必须择一并在代码中标注）**：
  - **A（推荐）**：调整编排——`gather` 只做各板块溯源，**链组装完成后再统一触发级联预判**（把 `_cascade_sector_prediction` 移出 gather 之后，按链上 `self_driven` 板块逐个/批量触发）；
  - **B**：预判输入改读**前一交易日**链（`GET /api/agent/attribution-chain/:date` 取 T-1），并在 prompt 中显式标注链的日期（避免"今日"误读）。
- **裁决（2026-09-17，组长拍板）**：采用**方案 A** —— 链**只承载溯源**（不含预判产物/预判 id）；"该板块预判"由前端用 `prediction_records` **二次 join** 呈现（§7 已按此设计）。由此消解重要项"链携带预判产物与链后预判互斥"的冲突；若后续确需链上引用预判，须改为链的二次写入（patch）并单独立项。
- **验收**：级联路径产出的预判记录中，能查到其注入的链事件 id 列表非空（或链日期为 T-1 且已标注）；单测覆盖"链未就绪"与"链已就绪"两种时序。

### 13.2 `event_ref` 字段落点（§12.4 状态锚的前置）

- **问题**：§12.4 要求"事件类条件带 `event_ref`（事件 id）"，但 `PredictionCondition`/`anchor` 现无该字段（`schemas/prediction.py` 的 `PredictionCondition` 与 `anchor` 仅含 `horizon/threshold/metric/direction`，`schema_version=3.0`）→ 状态锚无法实现。
- **方案**：在 **`anchor` 上**新增 `event_ref?: string`（与 `metric/op/level` 同级，集中承载判定输入）。
  - 生成侧：`condition_type=event` 时**必填**（prompt 约束）；无法给出事件 id 的条件不得标为事件类（降级 `unjudgeable`）。
  - 兼容：可选字段、旧记录缺省 → 不升 `schema_version`；判定层遇 `event_ref` 缺失即按 `unjudgeable` 处理（`met: null`）。
  - 判定：`event_ref` 走 Event Entity `event_status` 迁移（§12.4 ①）；`event_ref` 指向的事件不存在或未物化 → 走 ②/③ 层。
- **验收**：事件类条件在生成侧产出带 `event_ref`；判定层能据此走状态锚；缺 `event_ref` 的事件类条件不误点亮。

### 13.3 溯源自身的反馈回路（原 §5 P2f → 提为排期）

- **问题**：§5 将"溯源弱反馈"列为候选不排期 → 溯源质量不会被验证/迭代修正（预判侧有 Spec C/Cbis 回流，溯源侧没有）。
- **方案**：把 P2f 提为排期（见 §8 的 P6'），口径仍遵守总纲 §3.4"迭代双链路分离"：
  - 输入：预判验证结果（hit/miss）与链上板块的后续走势；
  - 输出：**只用于溯源侧的弱信号提级/降权**（例如同一板块多次"溯源到但预判未中"→ 降低该溯源模板权重），**不直接改写预判**；
  - 留痕：弱反馈动作必须可审计（记录触发规则、样本数、影响对象）。
- **验收**：能给出"某板块溯源反复与验证结果背离"的报告条目；无反馈动作时链产出与现状一致。
- **落地记录（2026-09-18）**：

**触发条件**：当日复盘 `primary_chain_id` 为空（或主链未命中任何板块名）。这类"证据不足但板块集中异动"的日子是**常态**（9/17 实测 4 候选全 `weak`）。

**三级兜底（严格降级，上一级有产出即不进入下一级）**

| 级 | 来源 | 判定 | 标记 |
|---|---|---|---|
| **T1** | 主链 `primary_chain_id` 对应候选的 `chain.nodes[].claim` | 命中快照 `top_losers`/`top_gainers` 板块名 | `source="primary_claim"`，**不标注** |
| **T2** | 全部 `trace.candidates[]`（含 `status=weak`）的 `chain.nodes[].claim` | 同上（保持 candidate 顺序） | `source="candidate_claim"` + `weak=true` |
| **T3** | 快照 `a_share.sectors` | 直接取 `top_losers` 头部（不足补 `top_gainers`） | `source="snapshot"` + `weak=true` |

上限：`max_sectors=3`，跨链跨来源**去重**（保留最先命中来源）。

**兜底板块必须补跑板块溯源（2026-09-18 组长口径）**

兜底命中的板块（T2/T3 来源）**除入链外必须逐个真跑一遍 `run_sector_trace`**（复用既有实现，不另写一套），产出四段 `stages`（phenomenon/trigger/transmission/impact）与 `sector_trace` 报告，使链 `children[].trace_summary` 与该板块溯源都有**真实**内容（而非只看得到板块名）。

- **理由**：兜底若只把板块"名字"写进链、不为这些板块真跑溯源，`children[].trace_summary` 只能落中性兜底「溯源未确认驱动原因」；而前端按「未确认就不展示」口径（`isUnconfirmedAttribution`）过滤后，**当日内容近乎为空**——恰恰是"板块集中异动但证据不足"（`sector_concentration` 型弱归因）最需要溯源的日子反而什么都看不到。补跑让弱归因日也有真实归因：有证据即出真实驱动句，确实无证据才落中性表述。
- **上限**：兜底补跑数量 ≤ `max_sectors`（默认 3，与该链路既有上限同值，实现为 `SECTOR_TRACE_FALLBACK_MAX_SECTORS`）；超出按提取顺序截断并留痕 `sector_trace_fallback_truncated`（记 `total/kept/dropped`）。
- **实现口径**：T1 命中与 T2/T3 兜底**分流**后一并 `asyncio.gather` 并行溯源（兜底带 `fallback_level ∈ {T2,T3}` 标记，逐板块记 `sector_trace_fallback_started/done/failed`，字段含 `sector/来源级别/elapsed_ms`）；分流而不是"对同一板块再跑一遍"，避免弱归因日的 LLM/检索成本翻倍。既有的并发/超时/重试/降级策略原样复用。
- **失败/无证据**：单板块补跑失败**逐项 try/except 隔离**——只 warning（`sector_trace_fallback_failed`），该板块如实未确认（不入链），不影响其它板块与链保存（`attribution_chain.save_failed` 语义不变）；溯源成功但检索无命中/证据不足 → 照旧如实降级（快照 `attribution_status="insufficient"`、摘要中性），**绝不编造、不得用行情综述填充**（继续遵守 `is_driving_event` 事件准入）。
- **时机**：补跑发生在"链组装/保存**之前**"（否则进不了 `children`），级联预判仍在链保存之后触发（P0' 时序，见 §13.1）。
- **反向约束**：T1（有主链）路径的调用次数/入参/日志**逐字不变**，且不出现兜底日志与弱标记。

**弱依据的表达与约束**
- 链：`root.evidence_weak=true` + root 记录 `attribution_status`；root 摘要空缺时用中性表述（**禁止编造主因**）；每个兜底 children 带 `extraction.source/weak`。
- 预判：兜底板块**照常触发级联预判**（保证"溯源到的板块要有预判"），留痕到 `attribution_weak`/`extraction_source`，供前端弱化展示与后续统计。
- 反向约束：T1 路径**不得**出现 `evidence_weak`/`extraction.weak`。

**风险**：T3 是"有异动但无归因理由"的链，展示与统计时需可区分（靠 `extraction.source`）；若未来 T3 占比过高，说明归因能力（而非兜底）是瓶颈。

### 13.8 报告写入收敛：多板块「一天一份」（2026-09-18 追加，生产问题驱动）

**问题（生产实证）**：`run_sector_trace` 每个板块各写一次 `report_type="sector_trace"` 报告，Node upsert 键 `(report_type, report_date, COALESCE(user_id,''))` 让**同一天后写的板块覆盖先写的** → `agent_analysis_reports` 全库仅 2 条、每条 `display_report.sectors` 长度**恒为 1**（`2026-09-17 → ["玉米"]`、`2026-09-18 → ["先进封装"]`）。消费侧 app-api `sector-insight` 读该报告 `display_report.sectors` 作 `review_primary` 候选集 → 多主因日在**报告层**不成立（§13.7 兜底补跑并行跑多板块后更明显：仍只剩最后一个）。

**口径**：写入收敛为**一次**——逐板块溯源不再自写报告，`asyncio.gather` 结束后由 `save_sector_trace_report` 聚合写当天全部已溯源板块。

| 项 | 约定 |
|---|---|
| 写入入口 | `run_sector_trace(persist_report=...)`：默认 `True` = 单板块自写（`run()`/iterate/replay 等既有调用方**逐字不变**）；多板块调用方 `SectorTraceConsumer` 传 `False`，gather 后由 `save_sector_trace_report` 写一次 |
| `display_report.sectors` | 当天**全部成功**溯源板块名（按 gather 入参顺序去重：T1 主链命中在前、兜底按提取顺序在后）→ `review_primary` 候选一个不少 |
| `display_report.sector_traces` | **加性新字段** `{板块名: trace 序列化}`：`market_trace.trace` 只能放一个板块的 trace，多板块日其余板块的 `attribution_status/stages/missing_evidence` 由此按板块名索引（app-api 后续可按需消费，本轮不改 app-api） |
| `market_trace` | 仍是**单板块**形状（首个板块的 `snapshot`+`trace`）→ 既有读取方（app-api `extractSectorTraceInfo`/`extractTraceSummary`）契约不变 |
| `schema_version` | 仍 `"2.1"`：既有键类型/语义未变、仅新增键，非破坏性变更 |
| 失败隔离 | 溯源失败板块**不进 `sectors`**（该字段语义是"已溯源确认的板块"，写进去会让 `review_primary` 出现无 trace 支撑的候选），其它板块照写、不 panic；报告写失败只 warning `sector_trace_report_save_failed`（不把 review_done 拖进 retry/DLQ） |
| 幂等/重入 | 按板块名去重（同名只留首次）；同一天重复跑（重放/补跑）覆盖同一行且清单一致、不重复 |
| 留痕 | 新增 `sector_trace_report_saved`（`sector_count`/`sectors`）；既有 `sector_trace_done`、`sector_trace_fallback_started/done/failed/truncated` 全部不变 |

**未闭环**：app-api 仍只读 `display_report.sectors`（`review_primary` 候选集）与 `market_trace.trace`（单板块 summary）；`sector_traces` 的 per-板块展示（如按板块切 summary）待 app-api/前端按需接入（本轮跨仓 0 改动）。
