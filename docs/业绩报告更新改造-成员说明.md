# 业绩报告 / 业绩预测 自动更新——改造说明（转交成员版）

> 目的：说明本轮"财报披露更新"改造的背景、最终目标映射、**哪些已改好 / 哪些需要你改**，以及现存 bug。
> 注意：本项目有**两套不同的业绩能力**，极易混淆，先读第 1 节。

## 1. 两套能力，别搞混

| | **业绩预测（盈利预测）** | **业绩报告（财报/快报/评级通知）** |
|---|---|---|
| 主文件 | `ProfitForecastAutoUpdateService.ts` / `profitForecastController.ts` | `PerformanceReportAutoUpdateService.ts` / `performanceReportController.ts` |
| 落库表 | `earnings_forecast` | `performance_reports` |
| 内容 | 机构的盈利预测（EPS/净利润/机构数） | 财报披露、业绩快报(预告)、研报评级的**通知记录** |
| 发现源 | **`report_rc` 已用**（昨日有研报的股→再去同花顺爬预测） | formal/express/rating 三个 report_type |

> 结论：你确认的"业绩预测候选采用 report_rc"对应的是第 1 套（ProfitForecast），**它本来就对，无需改**。
> 本轮"财报滞后 bug"发生在**第 2 套（业绩报告）**里，下面 2–4 节都在讲它。

## 2. 背景 bug（业绩报告）

财报披露通知时间错位：某股 8.18 披露正式财报，但旧逻辑拿 `report_rc`（昨日研报）当候选名单找该股，
8.19/8.20 它无新研报就漏扫，直到 8.21 有新研报进名单、拉 `income` 才首次发现 8.18 那条 → 通知落款 8.18 却夹在 8.21 之间。
**根因：拿研报当财报的风向标**，而 `disclosure_date`/`income` 数据本身早已入库。

---

## 3. 目标映射（无候选池，四源按日期增量）

旧方案：拉大候选名单，对每只候选股依次查 `income + forecast + report_rc`（候选数×3，慢且重）。
新方案：**不做候选池**，各类型只去**自己的发现源**按"前一天日期"批量找"昨天谁更新"，调用量从 O(N×3) 降到常数。

| report_type | 含义 | 发现源（=前一天批量查谁更新） | 取数方式 | 状态 |
|---|---|---|---|---|
| `formal` | 业绩正式报告 | **`disclosure_date.actual_date`**=昨日（真实披露日，T+1 权威，根治滞后） | 对命中股逐只拉 `income`（income 只能按股，仅命中时才拉） | ✅ 已改好 |
| `express` | 业绩快报 | **`express_vip`**（最近两个报告期全量分页）→ 客户端过滤 `ann_date`=昨日 | 行内自带 revenue/n_income | ✅ 已改好 |
| ~~业绩预告(forecast)~~ | ~~预告~~ | **去掉，不做**（见第 4 节"待修改"） | — | 🔧 需改 |
| 预披露提醒 | — | **`disclosure_date.pre_date`** 前瞻 | 目前用不上 | 🔧 需改 |
| `rating` | 研报评级 | `report_rc.report_date`=昨日 | 行内自带 eps/rating/org | ⚠️ 见第 4 节开放问题 |

- 各源 `INSERT + 通知`，已存在（`symbol+report_type+ann_date`）跳过；通知 `sourceKey` 幂等。
- 若昨日四源均无新增，用前 2 个自然日窗口重扫补漏（仍按日期批量，轻量）。

## 4. 已改好 ✅ / 待修改 🔧 清单（诚实标注）

### ✅ 已经改好的
1. **业绩正式报告 `formal`** ← `disclosure_date.actual_date=昨日` 全市场发现（根治滞后），命中后才逐股 `getIncome`。`TushareService` 已有 `getDisclosureDate` wrapper。
2. **业绩快报 `express`** ← `express_vip(end_date=最近两个报告期)` 全量分页 + 客户端过滤 `ann_date`=昨日。`TushareService` 已有 `getExpressVip` wrapper。
3. **业绩预测（第 1 套）**：`ProfitForecastAutoUpdateService` 已用 `report_rc` 做候选 —— 本来就对。
4. 无候选池架构落地：`run()` → `processSingleDay(昨日)` → 前 2 日兜底。

### 🔧 需要修改的（以下是我当前代码里**尚存**的问题，不要误读为已改好）
1. **业绩快报的源用错接口**：当前 `PerformanceReportAutoUpdateService` 里有一个分支（第 1 段）用 **`forecast`（业绩预告）** 往 `report_type='express'` 塞数据。
   你的要求是——业绩快报只该用 **`express`/`express_vip`**，业绩预告单独不建逻辑。
   **待办：删除 forecast 分支，快报只保留 express_vip 一路。**
2. **预披露提醒用不上**：当前 `run()` 会调 `sendPreDisclosureReminders()`（用 `disclosure_date.pre_date` 推未来 3 天预计披露）。
   你说 pre_date 目前用不上。
   **待办：下线该提醒（移除调用，或默认关闭）。**

### ⚠️ 开放问题（需要你拍板，未动）
- **`rating` 是否要保留**：`PerformanceReportAutoUpdateService` 里 report_type=`rating` 直接插 `report_rc` 行并通知；
  而第 1 套业绩预测也已用 `report_rc` 做候选。两者会造成同一批研报触发**两套通知**（一个 `forecast` 类别、一个 `performance_report/rating`）。
  如果你希望 report_rc 只归业绩预测，则业绩报告里的 `rating` 分支应一并去掉。

## 5. Tushare 接口事实（实测，务必遵守）

- `disclosure_date`（`actual_date`/`pre_date`）/ `forecast`（`ann_date`）/ `report_rc`（`report_date`）：**支持按日期全市场批量**查出"当天谁更新"。
- `express_vip`：**按 end_date / quarter 一次返回某报告期全部公司**（全量分页），**不支持按 ann_date 过滤** → 需整报告期拉全量、客户端筛 `ann_date`。
- `income` / `cashflow` / `balancesheet` / 普通 `express`：**必须先传 `ts_code`**，只能逐股取，无法按日期批量发现 → 只用于"已命中股票的明细拉取"。

## 6. 现存 bug / 其余待办

1. **批量接口未分页兜底**：`getForecastByAnnDate`、`getReportRc` 当前未传 `limit/offset`。单日公告量几十条安全；若某日超接口默认返回上限会漏，建议补分页防御（含上面要删的 forecast 分支一起处理）。
2. **`income` 逐股拉取在披露高峰日偏慢**：并发 3 + 500ms 间隔；财报高峰日（4 月底/8 月底/10 月底）命中可能上百只。当前窗口取近 7 天、只采纳 `ann_date`=昨日一行，窗口内有多次披露会重复查。
3. `report_rc` 分支里 `if (!reportDate || !row.eps) continue` 会丢弃"无 EPS 的评级"通知——若想保留需去掉该条件。
4. 三表（income/cashflow/balancesheet）必须带 ts_code，普通 express 只能单股——这是 Tushare 硬约束，不是 bug，但依赖它的调用方要做好"只能按股"的设计。
