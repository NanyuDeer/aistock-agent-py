# 异动捕手（stock_trace）优化点评估与设计方案

> 日期：2026-08-21（v2，已吸收评审反馈：按高/中/低三档重排优先级并给出具体设计）
> 范围：aistock-app-api（Node 侧检测/快照/入队）+ aistock-agent-py（Python 侧消费/归因）
> 前置：2026-08-21 已实施"落定后归因一次"。本方案所有评估建立在该决策之上，**不推翻它**。

---

## 1. 背景与评估方法

对异动捕手全链路（检测 → 事件 → 快照 → 归因 → 回写 → 展示）梳理出 8 个候选优化点。本方案逐项核对当前代码现状（附文件+行号证据），结合评审反馈按 **高 / 中 / 低** 三档给出结论与落地设计。

### 评估前提（关键）

2026-08-21 已把"盘中每次 revision 即时 LLM 归因"改为"事件落定后归因一次"（落定三条路径：恢复窗口到期 / 反向落定 / 收盘兜底 15:05）。影响：

- LLM token 消耗约降 66%（从"每 revision 一次"降为"每事件一次"）；
- **改变了部分优化点的价值权重**：例如"时序耦合""全量扫描"因不再即时跑 LLM 而成本大幅下降，但鲁棒性缺口仍在。

## 2. 优化点总览与结论

| # | 优化点 | 现状摘要（证据见 §9） | 结论 |
|---|--------|----------------------|------|
| 1 | 快照与任务消费时序耦合 | 事件落定入队 → 发布，enriched 五域采集需数十秒级，消费首轮可能 `SNAPSHOT_NOT_READY` 空转等 reclaim；无"快照就绪才发布" gate | **高：加发布 gate + 超时兜底** |
| 2 | DLQ 只写不消费 | 死信仅 `xadd` + 日志，无人重投、无告警 | **高：巡检 + 告警 + 手动重投** |
| 3 | LLM 校验拒绝直接判失败 | `VALIDATION_REJECTED` 直接计入重试，未利用"带纠错提示重试一次"，浪费已采集快照 | **高：纠错单次重试 + 指标** |
| 4 | detect 手动触发无并发/分批 | `detect()` 顺序 `await` 逐股处理，自选股多时耗时明显 | **中：并发/分批控制** |
| 5 | revision 全量重采 corrected | 每次修订全量重采全部域，Tushare/东财请求压力大 | **中：增量差异采集** |
| 6 | 事件抓取无重试 | `triggerEventScrape` 失败仅 `console.error`，事件库证据缺失降归因质量 | **中：加 1-2 次重试** |
| 7 | 轮询窗口可更精细 | 午休/非连续竞价**已跳过**（见 §5.1） | **低：无需改动** |
| 8 | 可观测性补强 | 心跳 + `/health/ready`（60s）已具备；缺 Stream lag、processing 卡超时、DLQ 计数告警、业务指标 | **低：补指标与告警** |

## 3. 高优先级（建议实施）

### 3.1 快照就绪才发布 gate（优化 1）

**现状**：enriched 快照为**异步五域采集（耗时数十秒级）**。任务入队后 `publishPending` 立即发布，consumer 首轮大概率拿 `SNAPSHOT_NOT_READY` → 不 ack 靠 pending reclaim 空转（consumer.py L118-121）。2026-08-21 落定后归因已让正常路径（5 分钟恢复窗口 >> 采集耗时）很少命中，但**鲁棒性缺口仍在**：若 enriched 异步采集失败/进程崩溃，job 会在 reclaim 中无限空转且不占 attempt。

**设计（二选一或叠加）**：

1. **发布 gate（主方案）**：`StockTraceJobService.publishPending()` 发布前检查该 job 的 `(event_id, trigger_revision)` 的 `enriched` 快照是否存在；未就绪的 job 标记 `held` 留待下轮发布，**不再过早进入 Stream**。落定路径在入队前同步 `await` 确保 enriched 就绪（缺失则触发一次同步采集兜底）。
2. **完成标记（备选）**：发布 payload 带 `snapshot_ready=true/false`，consumer 未就绪直接跳过不轮询 reclaim，等下一轮 gate 补发。

**配套兜底**：consumer 为每个 job 记录首次 `SNAPSHOT_NOT_READY` 时间（Redis hash 或消息字段），超过阈值（如 10 分钟）→ `_dead_letter(SNAPSHOT_TIMEOUT)`，清理过期 key，杜绝无限空转。

**验证指标**：`stock_trace_snapshot_not_ready_total`（命中次数应趋近 0）。

### 3.2 DLQ 巡检 + 告警 + 手动重投（优化 2）

**现状**：`_dead_letter` 仅向 `stock-trace.jobs.dlq` `xadd` + `report_job(dead_letter)` + `xack` + 日志。**无人重投、无告警**，死信任务对运维不可见。

**设计**：

1. **定时巡检**：周期性 `xlen(DLQ_STREAM)` + 最近死信时间 → 指标 `stock_trace_dlq_length`、`stock_trace_dlq_total{error_code}`。
2. **告警**：DLQ 长度 > 0 持续超过阈值（如 15 分钟）→ 结构化日志告警（复用现有 structlog 通道）。
3. **手动重投接口**：`POST /admin/stock-trace/dlq/replay`（`verify_internal_token` 保护），支持过滤（全部 / `error_code` / `job_id`），读回 DLQ 消息 re-xadd 到主流 `stock-trace.jobs`，单次批量上限（如 50 条）防风暴。

**边界**：重投前校验 error_code 白名单（`INVALID_JOB_MESSAGE` 等结构性错误不允许重投）；永久性业务错误由人判断。

### 3.3 LLM 校验拒绝：纠错单次重试 + 指标（优化 3）

**现状**：`validate_stock_trace_result` 校验失败捕获 `StockTraceValidationError` → 记录 `stock_trace_validation_failed` → 返回 `failed / VALIDATION_REJECTED`，**直接计入重试**（最终可能死信），未利用"带纠错提示重试一次"提升通过率，**已采集快照被浪费**。展示端已有 `getEffectiveArtifact` 回退上一版有效归因（2026-08-20），用户侧历史事件有兜底，但新事件归因质量静默下降。

**设计**：

1. **纠错单次重试**：校验失败时，把校验错误详情（缺哪个字段 / 哪条链不符合约束 / 字段对照表）并入下一轮受限归因 prompt，**重试一次**；仍失败才返回 `failed`。
2. **指标**：`stock_trace_validation_failed_total{error_type}`、`stock_trace_validation_retry_success`，监控 prompt/schema 漂移。
3. **明确不做**：不做无限重试（token 保护）；不改展示端回退逻辑。

## 4. 中优先级（按需实施）

### 4.1 detect 并发/分批控制（优化 4）

**现状**：`detect()` 对自选股 `for...of` **顺序 `await processPriceFact`**（PriceTriggerDetector.ts L66-82），无并发/分批限制；自选股多且多个异动时，单轮检测耗时长（每次 `processPriceFact` 含 DB 写入 + 命中时快照采集）。`runOnceForce` 手动触发同样受影响。

**设计**：用并发池（如 `Promise.all` 分批，并发上限 5-10）处理自选股，保留 `this.running` 防重入；`processPriceFact` 内部已有幂等/状态机，可安全并发。注意：异动写入（建事件/写快照）并发时需依赖现有事务与 UNIQUE 约束，避免同股并发重复建事件（评估后若无约束保护则退回串行，仅对**快照采集**并行）。

### 4.2 revision 增量差异采集（优化 5）

**现状**：每次 revision（涨跌幅扩大 ≥2% 或 severity 升级）→ `captureSnapshots('revised')` → `captureCorrected` + `scheduleEnriched` → **全量五域重采**（Tushare/东财多接口），第三方压力大。

**设计**：仅刷新与价格强相关、盘中可能变化的域（quote / capital / technical）；company / sector 复用最近一次同 event 快照（盘中基本不变）。enriched 最终快照保证五域齐全（缺失域用上一版本合并补齐，`getAnalysisContext` 仍按 event_id+revision+enriched 精确取数不受影响）。

**取舍**：降低第三方请求量，但增加实现复杂度。若监控标的量大 / 外部 API 配额紧张再实施。

### 4.3 事件抓取 1-2 次重试（优化 6）

**现状**：`triggerEventScrape` fire-and-forget，失败仅 `console.error`；事件库证据缺失会降归因质量（事件库已是快照采集的一级证据源，见 `loadEventStoreEvidence`）。

**设计**：加 1-2 次指数退避重试（如 500ms/2s），仍失败打日志并累计 `stock_trace_event_scrape_failed_total` 指标；可叠加"失败后改由快照采集的缺库降级路径兜底"（已有）。

## 5. 低优先级

### 5.1 轮询窗口（优化 7）——已实现，无需改动

**核实结论**：`isAShareTradingTime` → `isWithinTradingWindows`（tradingTime.ts L41-47）已**排除午休 11:30-13:00** 及集合竞价间隙（仅 9:15-9:25 竞价、9:30-11:30、13:00-15:00 连续竞价才轮询）。第 7 点"午休仍在轮询"**实际已解决**。

**仅当自选股数量大幅增长（> 数百只）**：考虑把 `DETECTOR_INTERVAL_MS` 从 5s 调大（如 10s）——一行改动，先记入 backlog。

### 5.2 可观测性补强（优化 8）

**现状**：consumer 心跳 + `/health/ready`（60s）**已实现**（routes.py L1412-1428）。剩余价值在业务指标与告警。

**设计**（agent-py 暴露 `/metrics`，Prometheus 文本格式）：

| 指标/告警 | 说明 |
|-----------|------|
| `stock_trace_stream_lag` | 主 Stream 已消费 ID 与最新 ID 之差（消费积压） |
| `stock_trace_job_processing_age_seconds` | **job 卡 processing 超时**检测：超过阈值（如 10 分钟）告警 |
| `stock_trace_dlq_length` + `stock_trace_dlq_total{error_code}` | DLQ 计数告警（配合 §3.2） |
| `stock_trace_jobs_total{status}` / `stock_trace_jobs_attempts` | 终态分布与重试效率 |
| `stock_trace_analysis_duration_seconds` | 归因耗时直方图 |
| `stock_trace_validation_failed_total` | 校验失败率（配合 §3.3） |
| `stock_trace_snapshot_not_ready_total` | 验证 §3.1 发布 gate 效果 |

## 6. 落地顺序建议

| 梯队 | 内容 | 理由 |
|------|------|------|
| 第一梯队（低风险高收益） | §3.1 发布 gate、§3.3 校验纠错重试、§3.2 DLQ 巡检+告警+重投 | 消除无效轮询/死信不可见/归因质量下降三个真实缺口 |
| 第二梯队 | §4.1 detect 并发分批、§4.3 事件抓取重试 | 小改动、可独立落地 |
| 第三梯队（按需） | §4.2 revision 增量采集、§5.2 指标与告警 | 依赖量/配额/观测需求触发 |

**依赖**：§3.1 与 §5.2 的 `snapshot_not_ready` 指标互相印证；§3.2 与 §5.2 共享 DLQ 指标；§3.1 gate 与 §3.2 的 `SNAPSHOT_TIMEOUT` 死信共用同一兜底路径。

---

## 7. 风险与取舍

- **重试 token 增量**：校验失败单次重试约 +1 次 LLM 调用/失败事件；用指标监控失败率，持续偏高应优先修 prompt/schema 而非加重试次数。
- **DLQ 重投风暴**：单次批量上限 + error_code 白名单。
- **并发引入的写入竞争**：detect 并发化必须复用现有事务/UNIQUE 约束，否则同股并发建事件会重复。
- **不推翻 2026-08-21 核心决策**：检测/推送实时链路、落定后归因一次策略保持不变。
