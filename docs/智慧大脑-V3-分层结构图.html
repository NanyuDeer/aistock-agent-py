  metrics/      run 级度量汇总、trace、成本读取
注册只认 registry.yaml：手动登记 + python -m brain_v3.registry --check 双向校验 + registry.lock 拓扑指纹（id + deps + required_for + profiles.needs|optional 的 sha256）。固定节点 market_perception / event_perception / conflict_resolver / judgment_writer / briefing_writer 不登记，用保留 ID。
证据身份为 (source_type, source_id, snapshot_id)，subject 不进唯一键、可为空；snapshot_id = snap_{YYYYMMDD}_{HHMM} 由 OR-RUN 在 run 启动时生成、同 run 共用；evidence_id = ev_{source_type}_{sha1(source_id|snapshot_id)[:12]}。

一次 run 的完整链路：从触发到出口，节点之间怎么连

缩进表示调用关系；箭头上的字是交付物。研究层内部是唯一有循环的地方，且是目标驱动的有限轮循环（契约见 §4.2.1）。

状态模型：结论完整性 / 停止原因 / 缺失清单

名称层级取值用途
probe statusprobe只 ok，或抛可分类错误（timeout / empty / schema_mismatch / not_implemented）probe 不声明 partial / degraded / insufficient，降级权归主控
run statusrunok / partial / insufficient只表达结论完整性：ok = 必查全成功（可选缺失只记录）；partial = 必查缺失但有结论；insufficient = 必查缺失且无结论
stop_reasonruncomplete / budget / timeout / error与 status 正交；预算触顶只记 budget，不改变 status、不计入 partial 率
missing_probesrun（数组）[{id, required, reason}]缺了谁、是否必查；required=true 的缺失决定 partial / insufficient

研究循环：目标驱动，而不是跑完节点就交卷

状态做什么交付物
PLANAG-LEAD 出 ResearchPlan：问题、假设（含反方）、必查 / 可选、充分性判据、max_rounds=2（硬上限 3）/ max_depth=2plan
DISPATCH按 plan 用 Send 动态扇出到 probe；请求带 objective / output_format / source_hint / boundariesResearchRequest
COLLECTreducer 合并 claims / evidence / gaps；只回引用，正文落 KBResearchResponse
ASSESS确定性 SufficiencyCheck，是唯一岔路口；同时写进度账本SufficiencyReport + RoundLedger
REPLAN仅由 Gap 触发；stall=3 时重置计划（reset 上限 2），只走请求队列 + OR-ROUTER新 ResearchRequest
JUDGE → WRITE判据满足、收敛或耗尽后裁决落账Judgment
回查三类目标：上游节点重跑（快照过期）、同级 probe 补证（必须带 evidence_ids）、GX 换源换日期。去重键 (target, question, as_of, stage)；请求树出现 A→B→A 立即停止并标 circular_request；禁止 probe 直接调用另一个 probe。研究树字段 request_id / parent_request_id / round / purpose 进 trace。
停止条件按优先级：判据满足 → 预算 / 轮次耗尽（stop_reason=budget）→ 连续两轮无新增证据或候选排序稳定 → Gap 无法补齐（insufficient）。默认两轮，只有候选分歧大 + 关键缺口 + 预算充足才开第 3 轮；固定跑满 3 轮视为失败（多 agent 约 15x token）。
拓扑按档位选：大盘归因 / 风口扫描用"主控 + 并行 probe"；个股问答 / 单事件解读用单 agent + 工具。不为了形式统一强行上多 agent。
AG-LEAD 阶段标记：第一周为受限两轮主控（ResearchPlan + Gap 驱动 + 固定必查），第二周开放同级回查 / 上游重跑与自由 ReAct；Deep Agents 只作为 D6 spike 评估项，不直接进主链；超时与错误控制用节点级 TimeoutPolicy + error_handler，asyncio.wait_for 只作外层保险。

选型复核：哪些方案不用、哪些改用替代

选项优点不采用 / 调整的理由结论
CrewAI / AutoGen 进主链角色与团队抽象开箱，对话式协作成熟多一套运行时与状态；确定性路由弱；单写入口与审计难保证主链不用；CrewAI 仅离线（MT-EVOLVE / MT-REFLECT）
Deep Agents 整包todo / 子 agent / 上下文压缩开箱，跑在 LangGraph 上agent 可自主写记忆；工具权限与预算闸门要额外 middleware两阶段 + D6 spike；主用 AG-LEAD，离线可给 MT-EVOLVE / MT-REFLECT
端到端 RL 研究 agent长程检索强，能学"何时继续查"需大量轨迹与 RL 基建；不可审计；内网结构化数据不匹配改小模型判别器 + 轨迹蒸馏
异步子 agent降延迟，可动态补派一致性、回放、预算归因复杂；同步已满足 90s第一周不做，预留 seam
统一单 agenttoken 省，责任清晰广度易漏，上下文易爆仅 narrow 档位
统一多 agent广度覆盖强约 15x token，协调复杂仅 breadth 档位
