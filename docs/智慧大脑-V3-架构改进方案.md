## 3. 方案细则

### 3.1 目录

```text
brain_v3/                    # 运行时：会被打进生产镜像
  contracts/        # Pydantic 模型（唯一事实源）+ 生成的 JSON Schema（产物，禁止手改）
  graph/            # 主图装配、profile、运行入口
  nodes/            # 规则层：感知、裁决、落账、渲染
  probes/
    wind/ event/ capital/ fundamental/ macro/
  tools/            # app-api 内部接口的统一客户端 + run 级 memo，唯一取数入口
  adapters/         # 临时：包装老 worker 输出为 claim，标注删除日期
  registry.yaml     # 手动登记表（唯一事实源）
  registry.lock     # 生成的拓扑指纹基线（CI 比对，禁止手改）

brain_evals/                 # 离线：不进生产镜像，不被 brain_v3 运行时代码 import
  cases/            # 判断质量评测集、规则回归集
  replay/           # 历史回放、影子对照
  ab/               # A/B 脚本与配对统计
  metrics/          # run 级度量汇总、trace、成本读取
```

`brain_evals/` 为什么独立于 `brain_v3/`：① 评测数据与答案不随生产镜像发布；② pandas/matplotlib 等评测依赖不污染运行时；③ CI 可单独跑长任务；④ 标签相当于答案卷，访问权限可单独控制。它在仓库里的位置固定为 `aistock-agent-py/brain_evals/`。

依赖红线（CI 检查，逐条可执行）：
1. `brain_v3/` 内部禁止 import `aistock_agent.agents.workers.*`，只有 `adapters/legacy_*.py` 可以；
2. probe 不得自己请求外部源，只能经 `tools/`；
3. 每个 adapter 文件头注明临时标记与计划删除日期；
4. **分层单向**：`graph/` → `nodes/` → `probes/` → `tools/` → `contracts/`，禁止反向 import（用 import-linter 固化，防六人并行时 `probes/` 反向依赖 `nodes/` 形成环）；
5. **运行时不得 import 离线**：`brain_v3/` 任何模块禁止 import `brain_evals/`（防评测代码进生产镜像）。

### 3.2 契约单一事实源

生成链**只有一个方向**，每一环都禁止反向手写：

```text
brain_v3/contracts/*.py (Pydantic 源)
  → JSON Schema（datamodel-code-generator --output-model-type pydantic_v2 / model_json_schema 导出）
  → TS 类型（json-schema-to-typescript）
```

- Pydantic 生成 JSON Schema，TS 类型由同一份 Schema 生成；CI 重新生成后 `git diff --exit-code`。
- 产物位置固定：Schema 落 `brain_v3/contracts/schema/*.json`、TS 落 `aistock-app-api/src/modules/brain/contracts/*.ts`。已核查：`aistock-app-api/src/modules/brain/` 已存在（当前有 `BrainRunArchiveService.ts`），`contracts/` 为新建子目录。两者**入库**但**禁止手改**。
- **TS 侧只消费生成物**：app-api 不得手写契约字段或枚举，需要新字段时先改 Pydantic 再重新生成，否则跨语言双源必然复发。CI 检查生成物文件头有 `// generated, do not edit` 标记。
- 生成必须**确定性**：固定 Pydantic 版本、字段按声明顺序、禁止 `set`/`dict` 无序字段进契约、禁止无默认值的 `float` 进 ID 类字段；CI 连续生成两次比对 sha256 一致。
- 修正 §3.2 示例中损坏的 `fetched_at`。
- 证据三时间字段（`event_time / published_at / as_of`）必须在契约中显式声明。

**契约边界（避免"三模型"被误解）**：P1 跨 TS/PY、必须生成 Schema 的是 `Evidence` / `Judgment` / `ToolEnvelope` / `RunStatus`；只在 Python 内部流转的是 `Claim` / `ResearchResult` / `RunBrief`，不生成 TS。`Claim` 在 P3 归档接口落地时再加入跨界清单；不为暂时不跨界的数据生成第二份类型。

### 3.3 `judgment_id` 格式（决策 2）

格式（code 中的 `.` 一律替换为 `-`）：

```text
jdg_{YYYYMMDD}_{subjtype}_{code}_{horizon}_{jtype}_v{n}
```

| 段 | 取值 | 示例 |
|---|---|---|
| subjtype | `mkt` / `sec` / `stk` | `stk` |
| code | `{code_ns}-{code}`；`code_ns` 取 `ex`（交易所）/ `ths`（同花顺）/ `em`（东财） | `ex-600519-SH`、`ex-000001-SH`、`ths-881121`、`em-BK0475` |
| horizon | `intraday` / `1d` / `3d` / `1w` | `1d` |
| jtype | `forecast` / `attribution` / `assessment` | `forecast` |
| version | 同一 owner 键内递增 | `v1` |

示例：

```text
jdg_20261126_stk_ex-600519-SH_1d_forecast_v1
jdg_20261126_stk_ex-600519-SH_intraday_attribution_v2
jdg_20261126_sec_ths-881121_3d_forecast_v1
jdg_20261126_mkt_ex-000001-SH_1d_attribution_v1
```

命名空间必须显式，原因：`000001-SH` 带交易所后缀，而 `881121` / `BK0475` 是源内码，同一字段无法自校验，也无法区分"缺后缀的笔误"与"板块码"。解析规则固定为"首个连字符之前是 `code_ns`"。数据库另存 `code_ns`、`code` 两列，ID 只是可读视图。

规范化规则：
- 交易所后缀统一大写（`SH` / `SZ` / `BJ`），点号换成连字符；
- code 内禁止出现下划线，下划线只作段分隔符；
- 同一 code 的两种写法（带点/带连字符）视为同一个标的，入库前统一转换，禁止混存。

约束：
- 必须保留交易所后缀：`ex-000001-SH`（上证指数）与 `ex-000001-SZ`（平安银行）不能合并；
- 板块保留源命名空间（`ths-881xxx` / `em-BKxxxx`），避免不同源撞码；
- 唯一性由数据库兜底，且 owner 键**必须含 `type`**：`(type, code_ns, code, horizon, judgment_type) WHERE status='active'` 的部分唯一索引。缺 `type` 时 `market-000001-SH` 与 `stock-000001-SH` 会互相顶掉；
- 全表唯一索引 `judgment_id` 仅防 ID 重复，不承担 owner 语义。

版本分配与并发（唯一写入方是 app-api）：
- `version` **只能由 app-api 单事务接口分配**，Python 侧不得自算。流程：`SELECT ... FOR UPDATE` 锁 owner 键 → 取当前 active 的 `version + 1` → 旧版置 `superseded` → 插入新版，三步同事务；
- 冲突重试由 app-api 内部完成（建议 3 次指数退避），Python 只处理最终失败并标 `persist_failed`；
- `run_id` 单独存列，不塞进 ID。
- **ID 只用于引用、展示和日志，禁止代码反向解析取字段**：查询 owner、horizon、type 一律走数据库列。原因：code 里可能含连字符、标的简称会变，解析规则早晚会破；把 ID 当结构用，等于把展示格式变成契约。
- **ID 的最终拼装权在 app-api**：Python 只提交 owner key（`type / code_ns / code / horizon / judgment_type`）与 judgment 草稿；app-api 在分配 version 的同一事务里生成并回传 `judgment_id`。Python 不得自行拼最终 ID，否则 version 竞态下两边 ID 会不一致；在回传前，Python 只用 run 内的 `draft_id`。
- **`{subjtype}` 不单独存储**：它是 `type` 的短码映射（`stock→stk` / `sector→sec` / `market→mkt`），只出现在 ID 里，避免同一事实维护两套枚举。
- **`snapshot_id`**：`snap_{YYYYMMDD}_{HHMM}`（Asia/Shanghai），由 OR-RUN 在 run 启动时生成，同一次 run 的所有 probe 共用；写入 run 与每行 evidence。跨 run 只有显式复用同一 snapshot 才相同。
- **`evidence_id`**：`ev_{source_type}_{sha1(source_id|snapshot_id)[:12]}`，**不含 subject**；同一来源条目在同一 snapshot 下 ID 稳定，回放可复现。`subject` 只作为属性或 claim 关联，不参与 ID 与唯一键。

不接受把 `run_id` 放进 ID：同一天多次 run 是常态，ID 要表达"结论身份"，不是"运行身份"。

### 3.4 注册：声明依赖而非顺序（决策 6、9、10）

`registry.yaml` 每个 probe 声明三件事：**我是谁**（`id` / `module` / `owner`）、**我依赖谁**（`deps`）、**哪些档位需要我**（`required_for`）。默认不写 `order`；确需同层稳定展示时再引入，并把它纳入 `registry.lock` 指纹，**不得用来表达依赖**。

- 启动时与 CI 都用 `pkgutil.iter_modules` 扫描 `probes/`，与 YAML 双向比对：
  - 目录里有、YAML 没有 → **失败**（防遗漏）；
  - YAML 有、目录没有 → **失败**（防空登记）；
  - `deps` 成环或指向未登记 id → 失败并打印拓扑分层。
- **自动发现只做校验，不自动注册**：即使模块能被扫描到，只要没写进 YAML，主图就不加载它。
- 校验入口固定为一条命令（CI 与本地同一条）：`python -m brain_v3.registry --check`，输出"缺失项 / 多余项 / 循环依赖 / 指纹变化"四类。
- **指纹基线**：`--check` 对 `id + deps + required_for` 排序后取 sha256，与 `registry.lock` 比对；不一致时打印差异并失败。没有基线，review 里就看不见"拓扑被改了"。
- **档位双侧声明**（决策 10）：probe 侧 `required_for` 只回答"我属于哪些档位"，用于登记校验；profile 侧 `needs` / `optional` 回答"这个档位到底要什么"，用于执行期选择。只写 probe 侧无法表达"可选 probe"，只写 profile 侧则新增 probe 要改多处。
- **双侧一致性校验**：`needs / optional` 中出现的每个 probe，必须在 `required_for` 里登记对应档位；反之 `required_for` 声明的档位也必须出现在 profile 的 `needs / optional`。不一致直接失败，防止两处漂移。
- **指纹范围**：`registry.lock` 的 sha256 必须覆盖 `id + deps + required_for + profiles.needs / optional`，否则只改执行拓扑、不改登记也能绕过基线。

`registry.yaml` 示例：

```yaml
# 只登记 probe；L0 感知、裁决、落账、渲染是固定节点，不在此表
probes:
  - id: wind_probe
    module: brain_v3.probes.wind
    deps: [market_perception]
    required_for: [market_review, stock_on_demand, wind_board]
    owner: F1
  - id: event_probe
    module: brain_v3.probes.event
    deps: [market_perception]
    required_for: [stock_on_demand, event_driven]
    owner: F2
  - id: capital_probe
    module: brain_v3.probes.capital
    deps: [market_perception]
    required_for: [market_review, wind_board]
    owner: F3

profiles:
  market_review:
    needs: [market_perception, wind_probe, capital_probe]
    optional: [event_probe]
  stock_on_demand:
    needs: [market_perception, wind_probe, event_probe]
    optional: [capital_probe]
  wind_board:
    needs: [market_perception, wind_probe, capital_probe]
    optional: [event_probe]
  event_driven:
    needs: [market_perception, event_perception, event_probe]
    optional: [wind_probe]
```

固定节点的保留 ID（`market_perception` / `event_perception` / `conflict_resolver` / `judgment_writer` / `briefing_writer`）不在 registry 登记，由主图固定装配；`deps` 可以引用这些保留 ID，`--check` 对保留 ID 放行。

拓扑分层（主图按层并行，同层无相互依赖）：

| 层 | 节点 | 并行 |
|---|---|---|
| L0 感知 | `market_perception`、`event_perception` | 并行 |
| L1 研究 | 所有 `deps` 仅指向 L0 的 probe | 并行 |
| L2 裁决 | `conflict_resolver` → `judgment_writer` | 串行 |
| L3 出口 | `briefing_writer`、落账、渲染 | 并行 |

该表是**当前 `deps` 的示例分层，不是固定四层**。实际层号由 `deps` 做拓扑排序（Kahn）计算，允许 probe 依赖 probe（如 wind 依赖 capital 的 claim）；代码里禁止硬编码 L0-L3。

这条表是 `deps` 的落地依据；没有它，`deps` 只是声明，六人会各自脑补执行顺序。

### 3.5 AG-LEAD：功能面全通，能力分批（决策 3）

"功能完整"定义为路径完整，不是每个 probe 都已高质量：

| 能力 | 第一周 | 第二周起 |
|---|---|---|
| 5 个 probe 槽位 | 全部定义并可调用；未实现的走 adapter 或返回 `not_implemented` | 逐个替换为真实实现 |
| 必查 / 可选 probe | profile 双侧声明（`needs` / `optional`）并强制执行，见 §3.4 | 按失败样本调整档位 |
| 自主决定加查 | 接口存在，实现为确定性规则（按缺口选择） | 用真实失败样本评估是否开 bounded ReAct |
| 冲突与反证 | 多空 + 裁决链路全通 | 补等强度反证规则 |
| partial / 降级 | 全路径打通，出口有明确标记 | 优化降级文案与置信 |

即：AG-LEAD 的主控位置、输入输出契约、降级路径第一周全部存在；变化的是"选择 probe 的智能程度"，不是"功能是否齐全"。

**`degraded` 的判定权归主控，不归 probe**：probe 只返回 `ok` 或抛出可分类错误（`timeout` / `empty` / `schema_mismatch` / `not_implemented`），**不得自己声明 `degraded` 或 `insufficient`**；是否降级、是否判 `insufficient`，由主控按 `needs` / `required_for` 决定。原因：若 probe 自己声明 degraded，实现有缺陷的 probe 可以永远 degraded 而不被发现。配套机制：

- 每个 probe 的错误必须带 `reason` 枚举（`timeout` / `empty` / `schema_mismatch` / `not_implemented`），成功时只返回 `ok`；状态与指标口径统一见 §3.11；
- 主控统计 run 级与滚动窗口的 degraded 率，超过阈值（第一周 40%）在 trace 里打 `degraded_watchdog` 告警并计入 §3.7 评测；
- `not_implemented` 是 adapter 阶段的合法值，但必须在 `registry.yaml` 里标注 adapter 到期日，到期未替换则 CI 失败。

### 3.6 模型策略（决策 8、11）

| 用途 | 模型 | thinking | 结构化输出 | 超时 |
|---|---|---|---|---|
| 感知 / 摘要 / claim | deepseek-flash | disabled | 允许 | 45s |
| 多空论证 | deepseek-flash | disabled | 不要求 | 90s |
| 裁决 / 冲突消解 | deepseek-flash | disabled | **必须**（Judgment schema） | 120s |
| 分类 / 打标 / 向量 | 自建小模型 | 不适用 | 允许 | 30s |

**thinking 与结构化输出的边界**：开启思考模式时模型可能把推理写进正文，与 `with_structured_output` 的 schema 约束冲突，导致解析失败或字段漂移。默认规则：**裁决节点 `thinking=disabled` + `with_structured_output`**，因为它必须产出结构化 `Judgment`。若某场景确实需要深推理，走两步：先由 `thinking=enabled` 的分析节点输出自由文本，再由 `thinking=disabled` 的抽取节点转成结构化；禁止在同一个调用里同时开 thinking 和 schema 约束。该规则在 D2 写入节点配置，不允许各节点自行设置。

**时延口径澄清**：§4 的"run < 30s"指**最小链**（L0 感知 + 规则裁决，不含 LLM 裁决节点）；含 LLM 的全链目标另设 P95（第一周 ≤ 90s），两者不得混用为同一门禁。节点超时是**上限**，不是 run 预算；run 级硬上限 = 研究阶段预算 + 裁决阶段预算之和，在 D2 定稿。P95 是性能目标，不能当超时值用。

**成本与预算解耦**（决策 11）：
- 每 run 在 `trace` 头写入 `model / thinking / tokens_in / tokens_out / elapsed_ms / budget_limit`；
- token 上限（首版 6 万）触发时记 `stop_reason=budget`，**不改变 `run status`**（可能仍是 `ok` / `partial` / `insufficient`），且预算触顶率不计入 §3.7 的 partial 率（完整指标口径见 §3.11）。原因：预算机制本身会让 B 组（省 token）更容易触顶，若与 partial 混算，"更省钱"与"质量不劣化"两个判定会互相污染；
- 落库链路必须闭环：`trace` 头写入 → `brain_evals/metrics/` 汇总 → §3.7 A/B 读取。只记录不汇总等于没有数据；
- 预算超限的降级动作是"停止加查、用已有证据出结论"，不是"整条 run 失败"。

#### 3.7.1 A/B 样本的功能与构造原则

先明确功能：A/B 样本不是"考试卷"，是四类决策的证据：

1. **质量非劣**：证明 `required_scope` 相对 `all_probes` 在方向、主因上不下降；
2. **成本收益为真**：证明 token/P95 的下降不是靠少查证据、少调用 probe 换来的；
3. **回归防线**：改 prompt、工具或阈值后，同一批样本上不出现隐性退化；
4. **失败样本源**：为第二周"是否开自主加查"提供能定位到具体 probe/证据缺口的案例。

因此构造必须满足六条，缺一条结论就不可用：

| # | 原则 | 具体做法 |
|---|---|---|
| 1 | 时间冻结 | 每条 case 固定 `as_of`，所有输入按 `published_at <= as_of` 截断；`time_confidence=low` 的新闻样本剔除 |
| 2 | 可回放 | A/B 时工具读录制响应，不读实时源；否则两次 run 证据不同，差异无法归因到拓扑 |
| 3 | 分层统计 | market/sector/stock 分开统计，不混总算总分；第一周只做 market |
| 4 | 客观锚 | 方向用 T+3 行情（只走 `trading_calendar`），主因用双人盲评；没有客观锚的样本只做定性观察 |
| 5 | 含失败样本 | 至少 30% 来自已知失败（如基线里风口领涨 3/4 错），否则全是简单题，A/B 无区分度 |
| 6 | 留出集 | 70% 用于调参，30% holdout 只在定稿前跑一次，防过拟合 |

回放清单（每条 case 一个目录，构造时录制、运行时只读）：

```text
brain_evals/cases/{case_id}/
  case.json          # as_of / subject / profile / 期望方向 / 期望主因 / failure_tags / labelers
  calls.jsonl        # 每次工具调用：endpoint / params / response_hash
  replay/*.json      # 录制响应原文
```

构造顺序：选历史日期 → 按 `as_of` 调 app-api 历史接口 → 录响应 → 双人标注 → 冻结。**不要直接用 `prediction_records` 当样本**：它只有结论，没有当时的证据快照，也不是新 ID 格式；只能作为"选日期和选标的"的线索。

**A/B 设计 v0（草案，第二周执行并定稿）**：

| 项 | 设计 |
|---|---|
| 关键简化 | A 不另建系统，而是同一张图的另一个 profile：`all_probes` 强制全跑；`required_scope` 只跑档位声明的必查/可选（**确定性选择，不含 LLM 自主加查**）。真正的 `adaptive`（AG-LEAD 自主加查）作为第二阶段单独评 |
| 样本来源 | 用旧账本 `prediction_records` **只挑日期与标的**，再按 §3.7.1 的录制流程重建当时证据；不得直接把旧结论当样本（它没有证据快照，也不是新 ID 格式） |
| 样本类型与能力对齐 | 第一周只有风口、事件两个真实 probe，**A/B 只做 market**（10 条）；sector / stock 待对应 probe 补齐后再扩。否则测到的是降级路径，不是能力 |
| 时间线 | 方向命中依赖 T+3 客观结果，**最早 D10 才有判定**；D7 复盘只定 A/B 时间与样本，不做判定 |
| 指标 | 方向命中（T+3 客观）、主因一致（双人盲评）、证据引用率（自动）、token、P95；`partial` / `insufficient` 状态率、`stop_reason` 分布（budget/timeout/error）与 `degraded` 标志率分别统计（口径见 §3.11），不混算 |
| 盲评协议 | 两组输出脱敏为「组甲 / 组乙」，随机交换呈现顺序；两名评审独立打分，分歧交第三人裁决并记录分歧率；评审不得是 A/B 的实现者 |
| 判定 | 配对比较（**仅 n≥30 执行**；n=10 只记录方向性观察，不判定）：B 的方向命中比 A 少不超过 2 条；主因盲评不劣；token 或 P95 至少一项降 20%；partial 率不高于 A+5pp |
| 统计 | n=30 只做配对描述（命中/未命中交叉表），不报 p 值；要显著性需 n≥80 或只接受大效应 |
| 成本 | A/B 使用同模型、同工具缓存；单次评测设预算上限 |

**v0 的结论边界**：这轮只回答"多查可选 probe 是否值得"，不证明"AG-LEAD 自主加查更好"。后者要等 §3.9 的失败样本条件满足后，单独做 `required_scope` vs `adaptive`，样本与结论都不得混进 v0。

不再使用"差值 ≤ 3pp"：每类 8 题时 3pp 不足 0.25 题，统计上不可判定。

**样本有效性与判定门槛**：
- n=10（第一周仅 market）只做方向性观察，**不作判定**；判定门槛是 n≥30，且 sector/stock 对应 probe 补齐后再扩样本。
- 样本构造必须按 `published_at <= as_of` 过滤；`published_at` 缺失或 `time_confidence=low` 的样本剔除，避免未来函数污染主因标注。
- `verify_at` 与 T+3 的交易日计算只走 `trading_calendar`，`as_of` 统一 `Asia/Shanghai`。
- 预算触顶（`stop_reason=budget`）单独报告，且 B 的预算触顶率不得高于 A+5pp；否则即使 partial 更低，也判 B 未通过。

#### 3.7.2 第一批 10 条 market 样本：怎么选、录什么

**选取（10 条，全部 `market_review` 收盘后口径，`as_of = 当日 15:30 +08:00`）**

从最近 120 个交易日里先排除不可用日，再按四类分层：

| 类型 | 条数 | 筛选条件 | 目的 |
|---|---|---|---|
| 大幅波动 | 4 | 上证 \|涨跌\| ≥ 1.5%，或上涨家数占比 < 20% | 检验方向与主因是否站得住 |
| 结构轮动 | 3 | 指数 \|涨跌\| < 0.5%，但第一名板块涨幅 ≥ 3% | 检验"板块→大盘"传导 |
| 平静日 | 2 | 指数 \|涨跌\| < 0.3%，涨跌家数 40%–60% | 防"没有主因硬编一个" |
| 事件日 | 1 | 当日电报含政策/地缘关键词 ≥ 3 条 | 检验事件取证与外围判定 |

排除规则：`close-snapshot` 返回 409 的日期、长假后首个交易日、指数调仓日、当日电报 < 80 条的日期。每条样本必须同时满足：收盘快照可取、T+3 日线可取、事件日历可读。

**其中至少 3 条必须从已知失败案例中选**（如基线里风口领涨 3/4 错的日子），可跨上面四类；如果全是成功案例，A/B 只证明"简单题都会做"。所有新闻类证据还要过 `time_confidence != low`，否则主因标注会被未来信息污染。

**录制接口（只录可回放的）**

| 证据 | 接口 | 日期参数 | 说明 |
|---|---|---|---|
| 大盘快照 | `GET /internal/market/close-snapshot?date=` | 有 | 409 直接排除该日，不补数 |
| 指数 T+3 | `GET /internal/index/:code/kline`（`000001.SH`） | 历史 | 验证方向用 |
| 板块/个股日线 | `GET /internal/ths/:code/daily`、`GET /internal/quote/:symbol/kline` | 历史 | 传导与个股锚 |
| 当日电报 | `GET /internal/news/telegraph?date=&limit=500` | 有 | 只取 `published_at <= as_of` |
| 事件日历 | `GET /internal/calendar/events?dateFrom=&dateTo=` | 有 | 财报/政策事件 |
| 业绩披露密度 | `GET /internal/calendar/earnings-density` | 待确认 | 支持日期才录 |
| 恐贪指数 | `GET /internal/fear-greed` | **无** | 缺口 1 |
| 风口龙头 | `GET /internal/wind-leaders` | **无** | 缺口 2 |
| 盘中板块 | `GET /internal/market/sectors` | **无** | 第一周不做盘中样本 |
| 个股资金 | `GET /internal/flow/:symbol` | **无** | 第一周不做个股样本 |

**三个历史取数缺口（不补就无法真正回放）**

1. `wind-leaders` 只返回最新值：增加 `?date=YYYY-MM-DD`，读 `board_rotation_daily` 历史行；该日无数据返回 409 + reason，**禁止回退最新值冒充**。
2. `fear-greed` 只返回最新值：增加 `?date=`，读历史序列；无数据沿用现有镜像契约（200 + 空字段）。
3. `market/sectors` 是实时源：第一周 A/B 只做收盘后 `market_review`，板块字段用 `close-snapshot` 里的数据替代；盘中样本推迟到有录制能力之后。

这三项作为 **D 工作流（app-api 历史取数补丁）** 放进 D0-D1，与 A/B/C 并行；D1 前不完成，第一批 10 条里涉及风口/情绪的样本只能降级为"仅快照 + 电报"，A/B 结论不完整。

**录制与冻结**

- 目录：`brain_evals/cases/{case_id}/`，含 `case.json`、`calls.jsonl`、`replay/*.json`。
- `case.json` 必填：`case_id / as_of（含时区）/ profile / subject（type/code_ns/code）/ expected.direction / expected.primary_cause / expected.evidence_types / failure_tags / labelers`。
- `calls.jsonl` 每行：`endpoint / params / status / response_hash / recorded_at`。
- 双人独立标注方向与主因；分歧交第三人裁决，仍不一致则丢弃该样本。
- 冻结后把目录 sha256 写入 `brain_evals/cases/index.json`；A/B 运行前校验 hash，防止样本被偷偷修改。
- 与第一周 12 条烟雾集**不相交**；A/B 集第一周只构造、不运行。

### 3.8 "影子"与 Strangler Fig 的关系（决策 7）

两者不冲突，影子就是 Strangler Fig 的第一阶段：

| 阶段 | 老链路 | 新链路 | 用户看到谁 | 数据写哪 |
|---|---|---|---|---|
| Transform（影子） | 正常服务 | 用同一批输入并行跑，只做对照 | 老链路 | 新链路写**独立影子表** |
| Coexist（灰度） | 保留兜底 | feature flag 放 1%→10%→50% | 按比例分流 | 新链路写正式账本 |
| Eliminate（下线） | 只留 adapter | 100% | 新链路 | 正式账本 |

第一周只做 Transform：新链路跑完整流程、写影子表、与老链路输出对照，但**不改变任何用户可见出口**。原因是一周内没有评测能力证明新链更准，直接切出口会把未验证结论暴露给用户。第二周起按 Coexist 灰度，指标不劣化才扩大。

**影子对照的基线语义（关键）**：旧链路已被判定"不对"，因此影子阶段**只比工程指标，不比方向**：

| 可比 | 不可比 |
|---|---|
| 时延 P50/P95、token、成本、`partial` 率、预算触顶率（`stop_reason=budget`）、run 内去重率、跨 run 回放一致性 | 方向是否一致、主因是否一致、置信是否接近 |

方向类指标一律走 §3.7 的人工盲评。若用旧链路的方向作基线，等于拿错误答案校准新链路。

**影子 → 正式的 promote 规则**：
- 影子表与正式表**同结构不同表名**，影子行带 `is_shadow=true`，永不进任何出口查询；
- promote 不是"改表名"，而是"灰度 run 重新写入正式表"：重新分配 `version`（走 app-api 单事务接口），旧 active 置 `superseded`，不允许直接把影子行搬过去复用 version；
- 影子行保留 30 天后清理，保留期用于回放与复盘。

**部署形态与版本约束**：同进程或独立进程都可以，但同进程有前提——旧链路仍依赖弃用的 `create_react_agent`，新链路的 `create_agent` 对版本更敏感。因此：

- 同进程影子必须**锁定当前 `lock` 文件**，任何人不得单独升级 `langgraph` / `langchain`；
- 一旦需要升级，必须先把老链路拆成独立进程（只提供 HTTP 输出），否则升级即炸影子基线；
- 该约束写入 CI：`lock` 文件变更需两人 review 并在 PR 模板勾选"已评估旧链路兼容"。

### 3.10 并行化与一致性前提

这四条不是实现细节，而是 `deps` 并行的前置条件，缺一条并行就不安全。

**1. 并行下 reducer 的顺序语义**
一旦 L0/L1 并行，`append` / `append_dedupe` / `set_union` 的合并顺序不确定，`claims[0]`、`evidence[-1]` 这类"按下标取值"会随并发漂移。规则：

- 排序键必须是内容，不是到达顺序：evidence 按 `(published_at, evidence_id)`、claims 按 `(producer_rank, claim_id)`；
- 禁止任何节点依赖通道内下标语义，读取必须用显式查找函数（如 `find_claim(producer)`）；
- 为每个 reducer 写一条"两次不同到达顺序 → 合并结果相同"的确定性单测。

**2. run 级 memo（决策 9 的配套）**
memo 解决的是**同一 run 内**重复取数，不解决跨 run 差异（它按 `run_id` 隔离）。跨 run 的确定性要靠固定 `as_of` + 录制工具响应回放，见 §6 验收第 2 条。`tools/` 必须内置 run 级 memo：

- scope 键：`run_id`；路径白名单（quote/index/trend/wind-leaders/event/calendar/forecast 等）；
- 命中失败也 memo（负缓存），避免同一 run 内重复打同一坏接口；
- 输出 `{total, unique, duplicates, failures}`，其中 `total = unique + duplicates`，作为 run 内去重率的分子来源；
- memo 只在一 run 内有效，不跨 run 共享缓存（跨 run 缓存会引入旧数据）。

**3. 契约冻结边界（D2 之后）**
"只加不改"必须说清冻的是什么：

| 冻结 | 可改 |
|---|---|
| `contracts/` 的 Pydantic 模型与生成的 Schema/TS | `registry.yaml`（登记新 probe） |
| `judgment_id` 格式与 owner 键 | `profiles` 的 `needs/optional` 组合 |
| 通道名与 reducer 类型 | `nodes/` 内部实现、probe 内部实现 |
| `status`（`ok/partial/insufficient`）+ `stop_reason` + `missing_probes` | 降级文案、置信校准参数 |

**4. 节点映射表与 API 可用性核实**
- 方案与契约 §2.3 的节点必须有映射表（`brain_v3` 节点 → 契约节点名），否则六人各自脑补执行序；
- §2 声称的 `TimeoutPolicy` / `error_handler` / `RunControl` 必须在 `langgraph==1.2.22` 上**实测可用**后再写进接入文档，D0 交付时附一行验证命令与输出，不允许"文档说可用"。

### 3.11 状态与指标口径

状态分两层，不能混用：

| 名称 | 层级 | 取值 | 用途与统计 |
|---|---|---|---|
| probe status | probe | `ok` / 抛错（`timeout` / `empty` / `schema_mismatch` / `not_implemented`） | probe 不声明 degraded；只上报事实 |
| run status | run | `ok` / `partial` / `insufficient` | 只表达结论完整性，是出口与评测的主状态 |
| `missing_probes` | run（数组） | `[{id, required, reason}]` | 缺失的 probe 及是否必查；`required=true` 的缺失决定 partial/insufficient |
| `stop_reason` | run | `complete` / `budget` / `timeout` / `error` | 停止原因，与 status 正交，避免"既有结论又超预算"被枚举吞掉 |

`run status` 只看结论完整性：`ok` = 必查 probe 全部成功（可选缺失只记录，不降级）；`partial` = 存在必查缺失但有结论；`insufficient` = 必查缺失且无法出结论。可选 probe 缺失写入 `missing_probes`，不改变 status。停止原因不再挤进 status；预算触顶记 `stop_reason=budget`，它可能同时是 `ok`、`partial` 或 `insufficient`。`stop_reason=timeout/error` 只指 **run 级**超时或致命错误；单个 probe 的超时/报错记在 `missing_probes` 上，不改变 run 的 `stop_reason`。

run 级指标定义（A/B 与验收共用，禁止各自解释）：

| 指标 | 定义 | 备注 |
|---|---|---|
| `partial` 率 | `status=partial` 的 run / 总 run | 有结论但存在必查缺失 |
| `degraded` 率 | `missing_probes` 中存在 `required=true` 的 run / 总 run | 由缺失清单派生，不另设布尔；包含 `insufficient` 的 run |
| `insufficient` 率 | `status=insufficient` 的 run / 总 run | 无法出结论，不写 judgment |
| 预算触顶率 | `stop_reason=budget` 的 run / 总 run | 单独统计，**不并入** partial |
| 方向命中率 | 方向命中数 / **参与判定的 run 数**（`ok` + `partial`） | 分母与排除项必须同时报告；两组排除量差 > 5pp 时判定无效 |

统计公平性：若 B 组通过更多预算触顶来降低 token，必须同时给出它的预算触顶率与"排除后分母"，否则"更省钱"是假象。`stop_reason=timeout/error` 也按同样方式单独报告，不得静默并入 partial。

### 3.12 `ResearchPlan` 与多轮研究循环

**问题**：现有 `review` 和多数 ReAct worker 是"一次取证 → 一次生成 → 校验"，没有"目标是否达成"的检查。证据缺了、某个 agent 的结论没拿到，流程仍然往前走，最后只能靠 LLM 硬编或降级。这是比"prompt 写得好不好"更根本的缺陷。

**目标**：把"一次分析"改成"目标驱动的有限轮研究"。AG-LEAD 仍然是唯一主控，但它先出计划、再按缺口补查，而不是一次把活派完。

#### 3.12.1 新增契约（Python 内部）

```text
ResearchPlan {
  plan_id,
  decision_type,        // attribution / forecast / risk / selection / monitoring
  questions[],          // 本次必须回答的 2-4 个问题
  hypotheses[],         // 3-5 个候选，至少 1 个反方
  required_probes[],
  optional_probes[],
  sufficiency_rules[],  // 每个问题需要什么证据才算够
  max_rounds: 2,        // 默认执行值
  hard_cap_rounds: 3,   // 仅 escalate_when 命中且预算充足时使用
  escalate_when[],      // 候选分歧大 + 关键缺口 + 预算充足
  max_depth: 2,
  budget
}

ResearchRequest {
  request_id, parent_request_id, round,
  requester, target,     // target 可以是上游节点、同级 probe、GX 工具
  objective,             // 一句话目标，必填
  question, purpose,     // purpose 必填，禁止“随便再看看”
  output_format,         // claim 列表 / 单值 / 时间序列
  source_hint,           // 优先数据源或接口，避免 probe 乱找
  boundaries,            // 不做什么、时间窗、标的范围
  expected_evidence[],   // 期望拿到的证据类型
  stage?,                // 归因场景下绑定 6 阶段之一
  deadline, budget
}

ResearchResponse {
  request_id, status,    // ok / partial / insufficient / rejected
  claims[], evidence[],  // 只回引用：evidence_ids + claim，正文落 KB
  gaps[],                // 缺什么、为什么缺
  suggested_requests[]   // 只是建议，由控制器决定是否执行
}

Gap {
  kind,                  // missing_data / missing_conclusion / conflict / low_confidence / stale_data
  detail,
  target_hint,
  expected_evidence[]
}

SufficiencyReport {
  question_id,
  status,                // satisfied / gap / conflict
  gaps[],
  can_judge: bool
}

RoundLedger {
  round, satisfied, in_loop, has_progress,
  new_evidence_count, stall_count,
  next_target, next_instruction,
  plan_reset_count
}
```

`ResearchPlan`、`ResearchRequest`、`ResearchResponse`、`Gap`、`SufficiencyReport`、`RoundLedger` 都是 Python 内部契约，不生成 TS；只有最终 `Judgment` 和 `RunStatus` 跨界。

#### 3.12.2 循环状态机

```text
PLAN
  → DISPATCH（按 plan 派发第一轮）
  → COLLECT（汇总 claims / evidence / gaps）
  → ASSESS（逐问题做 SufficiencyCheck）
      ├─ 全部 satisfied → JUDGE → WRITE
      ├─ 有 gap 且预算/轮次允许 → REPLAN → DISPATCH（下一轮）
      ├─ 无新增证据 / 候选排序稳定 → JUDGE（带 partial）
      └─ 达到 max_rounds / budget → JUDGE（带 insufficient 或 partial）
```

停止条件必须显式，按优先级：

1. `sufficiency_rules` 全部满足；
2. 预算或轮次耗尽（`stop_reason=budget`）；
3. 连续两轮没有新增证据，或候选排序不再变化（收敛）；
4. 出现无法通过允许工具补齐的 `Gap`（直接判 `insufficient`）。

**进度账本与重置**：每轮 `ASSESS` 另写 `RoundLedger`（`satisfied / in_loop / has_progress / new_evidence_count / stall_count / next_target / next_instruction / plan_reset_count`）。`stall_count` 连续到 3 就触发计划重置，重置上限 2 次；重置不是"再跑一遍"，必须重新读 `sufficiency_rules` 换问法或换目标。判据满足、收敛、预算耗尽任一成立都立即停，不为了"看起来努力"跑满轮次。

**轮次自适应**：默认执行 `max_rounds=2`；只有 `escalate_when` 同时命中"候选排序分歧大、缺口落在关键段、预算充足"才允许第 3 轮。固定跑满 3 轮视为失败——多 agent 约 15x token，日内链路还要守 P95。

**拓扑按档位选**：breadth-first 档位（大盘归因、风口扫描）用"主控 + 并行 probe"；narrow 档位（个股问答、单事件解读）用单 agent + 工具，不为了形式统一强行上多 agent。

#### 3.12.3 "回查上游 / 同级"怎么实现

不允许 probe 直接函数调用另一个 probe。所有回查都走**请求队列 + 路由器**：

- probe 在 `ResearchResponse.suggested_requests` 里提出请求，不自己执行；
- `OR-ROUTER`（确定性）按 `target + question + expected_evidence` 路由；
- 目标可以是：
  - **上游节点**：如感知快照过期 → 重跑 `SE-MARKET` / 重新冻结 `snapshot_id`；
  - **同级 probe**：如事件 probe 缺"外资暴露" → 请求 `AG-CAPITAL` 补一条 exposure claim；
  - **工具层**：如某数据源为空 → 请求 `GX` 换数据源或换日期；
- 每个请求必须带 `purpose` 和 `expected_evidence`，不能"开放式再查一遍"；
- 去重键：`(target, question, as_of, stage)`；重复请求直接复用已有响应；
- 环检测：请求树里出现 A→B→A，立即停止该分支并标 `circular_request`；
- 深度上限 `max_depth=2`，总请求数上限 `max_rounds × max_probes + max_peer_requests`。

**关键约束**：同级 agent 的"结论"不能直接当证据。它必须带着 `evidence_ids` 回来；没有证据链的 peer conclusion 只能算 `claim`，不能进 `KB-EVIDENCE`，也不能单独支撑 `confirmed`。

#### 3.12.4 不同功能怎么给不同方向

方向不是一句自然语言，而是 `decision_type` + `sufficiency_rules`：

| 功能 | 研判目标 | 必查 | 充分性判据 |
|---|---|---|---|
| 大盘归因 | 主因 / 次因 / 被否候选 | 资金、事件、风口、宏观 | 触发、传导、暴露三段有证据；反证已检验 |
| 个股异动 | 异动主因 / 持续性 | 风口、事件、资金、基本面 | 事件或资金至少一条成立；基本面反证已查 |
| 风口龙头 | 龙头 / 跟风 / 持续性 | 风口、资金 | 龙头与跟风股行为能互相解释 |
| 盘前预判 | 情景 / 概率 / 失效条件 | 宏观、事件、基本面 | 有历史类比 + 当前状态，不只靠叙事 |
| 风险监控 | 触发条件 / 暴露 | 事件、资金、宏观 | 尾部风险有反证，阈值可观察 |

**不新增第二个 LLM 方向的 agent。** AG-LEAD 内部多一个 `plan_research` 步骤；如果某些档位方向模板非常固定，用确定性的 `OR-PLAN` 生成骨架，AG-LEAD 只补充和排序。两个 LLM 决策者会带来"谁对结论负责"的问题，也容易让方向 agent 先有立场、研究 agent 只找支持证据。

#### 3.12.5 LangGraph 落地方式

- `DISPATCH` 用 `Send` 做动态扇出，`COLLECT` 用 reducer 合并 claims/evidence/gaps；
- `ASSESS` 用条件边或 `Command(goto=...)` 决定回 `DISPATCH` 还是去 `JUDGE`；
- 每个 probe 是独立子图或 `create_agent`，只返回 `ResearchResponse`，不直接写账本；
- `recursion_limit` 与硬上限对齐；另设总工具调用预算；
- `trace` 记录 `request_id / parent_request_id / round / target / purpose`，形成研究树，前端可回答"这轮为什么又查了一次"；
- **只回引用**：`ResearchResponse` 只带 `evidence_ids + claim`，正文落 KB；CI 设返回体长度阈值，超限失败；
- **异步 seam**：probe 不得有共享可变状态，预算与 `deadline` 随请求传递；第一周同步执行，P2 换调度即可，不改契约。

**第一周范围**：P0 只做"受限两轮"——第二轮只能从档位已声明的 `optional_probes` 里选，不允许自由发明工具；同级回查（peer request）放到 P1。验收看：一次 run 至少出现一次"因 gap 触发的第二轮"，且第二轮请求带明确的 `Gap`。

### 3.13 市场溯源 V3 映射（六阶段链）

**现状对齐**：现在不是"六条独立链"，而是 **4 个候选 × 同一条 6 阶段因果链**：

- `trace/chain.py` 定义 6 阶段：`structural_root → trigger → transmission → exposure → repricing → observable_result`；
- `schemas/market_trace.py` 里 `MarketTraceResult.candidates` 是 4 个候选，每个候选带一条 `CausalChain`；
- `workers/review.py` 用一次 LLM 生成 + 解析重试 + `validate_trace_against_snapshot` 校验；
- 复杂度来自"一个 LLM 同时找证据、编因果、选主因、自证"，不是链本身。

#### 3.13.1 V3 目标流程

```text
SE-MARKET 现象识别（规则 + 快照）
→ OR-PROFILE 选 market_attribution
→ AG-LEAD 出 ResearchPlan：4 类基线候选 + 1 个反方候选
→ 5 个 probe 取证；claim 打 stage 标签
→ DB-BULL 组装最强候选链
→ DB-BEAR 组装反方/次强候选，专攻弱阶段
→ DB-JUDGE 按阶段覆盖 + 证据质量 + 反证打分
→ DB-WRITE 写一条 judgment
→ EX-PAGE 渲染 6 阶段链
→ MT-VERIFY T+3 回填
```

#### 3.13.2 字段映射

| 现有 | V3 |
|---|---|
| `MarketTraceSnapshot` | `snapshot_id` + `SE-MARKET` 冻结快照 |
| `CandidateExplanation` | `CandidateChain`（增加 `missing_stages`、`status_reason`） |
| `CausalNode` | `Claim` + `stage` + `evidence_ids` + `confidence` |
| `primary_chain_id` | `Judgment.primary_candidate_id` |
| `attribution_status` | `Judgment.status` + 置信校准结果 |
| `unresolved_questions` | `Gap[]` + `missing_stages` |
| `prediction_validation` | `MT-VERIFY` 的到期回填 |
| `confirmed_prediction` | `KB-METHOD` / `KB-GOV` 的场景印证 |

#### 3.13.3 六阶段的硬规则

1. `structural_root` 是慢变量，允许标 `background`，不要求当天触发证据；
2. `trigger / transmission / exposure` 是 `confirmed` 的关键三段，缺任一段只能 `hypothesis`；
3. `transmission` 不允许只写"利率上行 → 成长承压"这种空话，每一跳必须有证据或可引用的机制条目；
4. `repricing` 指板块/指数重定价，`observable_result` 指广度、成交、涨跌家数，避免两段重复引用同一证据；
5. 每个 `CausalNode.evidence_ids` 必须能在 `KB-EVIDENCE` 解析；没有证据的节点只能标 `missing_reason`；
6. 被否候选保留链和 `counter_evidence_ids`，不能从结果里删掉。

#### 3.13.4 还需要完善的地方

1. **传导机制库**：`transmission` 是最弱一环，需要可引用的机制条目（利率→估值、汇率→出口链等），否则 LLM 会写正确的废话；
2. **暴露数据**：`exposure` 依赖持仓/成分数据，app-api 若没有，必须降级 `partial`，不能默认"外资重仓"；
3. **置信校准**：high/medium/low 不能由 LLM 自由给，按阶段覆盖、证据等级、反证强度映射，再用 T+3 校准；
4. **前端加性字段**：保留 `MarketTraceResult`，新增 `missing_stages`、`stage_confidence`，避免一次性改坏现网页面；
5. **评测方式**：拿 10 个历史交易日，对比"现有一发式 4 候选"与"V3 证据先行 + 多轮"，指标看主因命中、阶段证据覆盖率、置信校准，不只看 token。

### 3.14 从单轮到目标驱动：V3 智能升级包

前面两块是"补洞"，这一节是"让整个 V3 更聪明"的路线。核心判断：**智能不来自节点更多，而来自"知道什么时候该再查一次"。**

#### 3.14.1 分阶段升级

| 阶段 | 能力 | 不改什么 |
|---|---|---|
| P0（第一周） | `ResearchPlan` + 受限两轮 + `Gap` 契约 + 研究树字段 | 不加自由工具、不做 peer 直接调用 |
| P1 | 同级回查（peer request）+ 上游重跑 + 收敛检测 + 请求去重/环检测 | 仍由 AG-LEAD 单主控，仍单写入口 |
| P2 | 信息价值预算、红队自动补证、跨案例方法记忆 | 不改账本与出口契约 |

#### 3.14.2 六个关键升级

1. **目标驱动，而不是流程驱动**：先定义"这次要回答什么"，再决定查什么；每轮结束都做 `SufficiencyCheck`，不满足就补，不是跑完节点就交卷。
2. **研究树，而不是平铺证据**：`request_id / parent_request_id / round` 进 trace；能回答"第二轮为什么查、谁提出的、补上了没有"。
3. **信息价值预算**：预算优先给"最不确定、且最可能改变候选排序"的问题；简单启发式即可（候选分歧 × 证据缺口 × 成本），不需要 LLM 算。
4. **红队循环**：DB-BEAR 不只是写反方观点，可以提出"证伪请求"；每个主因至少经历一次针对性反证。
5. **跨案例记忆**：MT-REFLECT 统计"哪类 gap 反复出现"，下次在 `ResearchPlan` 里提前列为必查；方法库按 `decision_type` 存模板。
6. **收敛与停止**：候选排序连续两轮不变、没有新增证据、或预算耗尽就停；避免"为了多轮而多轮"。

#### 3.14.3 四条不能破的底线

1. 不允许 probe 之间直接函数调用；一律走请求队列 + 路由器，避免无限递归和上下文污染；
2. 不允许把 peer 的结论当证据；必须带 `evidence_ids`；
3. 不允许第二个 LLM 决策者；方向由 AG-LEAD 出，裁决由 DB-JUDGE 做；
4. 不允许无限循环；`max_rounds`、`max_depth`、总请求数、预算四个闸门同时生效。

#### 3.14.4 评测要多看三个指标

除了方向准确率、主因命中，还要加：

- **gap 闭合率**：第一轮发现的关键缺口，第二轮补上了多少；
- **无效补查率**：补查后候选排序没变、或没有新增证据的比例；
- **每条结论的平均轮次/成本**：防止"多轮 = 更贵但没更准"。

这三项能直接回答"多轮 loop 到底有没有让系统更聪明"。

### 3.15 主流做法核实与 V3 补强（2026-11-26 检索）

**结论：目标驱动多轮研究是主流，不是自创。** 我们缺的不是方向，而是主流的配套件：进度账本、任务简报、成本自适应、只回引用、过程评测。

| 来源 | 已验证的做法 | 对我们的意义 |
|---|---|---|
| Anthropic Research（orchestrator-worker） | lead 规划并派并行子 agent；子 agent 多轮检索、用 interleaved thinking 识别缺口；明确"linear, one-shot pipeline cannot handle these tasks"；多 agent 比单 agent 高 90.2%，但约 15x token | 证明"单轮一次生成"确实是缺陷；也证明多轮必须配预算 |
| LangChain Deep Agents | harness 内置 `write_todos` 任务规划 + `task` 子 agent + 上下文管理，跑在 LangGraph 上；自定义可用 `create_agent` | 我们已选 `create_agent`，可只借"todo + 子 agent 隔离"两个概念，不引整包 |
| Google ADK `LoopAgent` | 确定性 workflow agent，`max_iterations` + 终止条件/`exit_loop` 工具；本身不含 LLM | 验证"循环控制要确定性，判断才用 LLM" |
| Microsoft Magentic 编排 | progress ledger（是否满足/是否死循环/是否有进展/下一个谁/指令）+ stall 计数 → 自动 replan + plan reset | 我们只有"两轮无增量"，缺显式"卡住 → 重置计划" |
| AutoGen AgentChat | `termination_condition` + `max_turns`，无终止条件会无限跑 | 与我们的四道闸门一致 |
| S2G-RAG（ACL 2026） | 显式控制器判断证据是否充分，不充分则输出**结构化 gap 条目**，再映射成下一轮检索 | 几乎就是我们的 `ASSESS` + `Gap`，命名与口径可对标 |
| TradingAgents / FinRobot | 分析师角色分工 + 多空辩论 + 裁决；FinRobot 强调"数字由代码算、叙事由 LLM 写、全链路 provenance" | 验证 DB-BULL / DB-BEAR / DB-JUDGE 与"计算走工具" |

**五项补强（均已写入契约文档 §4.1 / §4.2.1 / §5.4）**：

1. **进度账本**：每轮除 `SufficiencyReport` 外，再写 `RoundLedger {round, satisfied, in_loop, has_progress, new_evidence_count, stall_count, next_target, next_instruction, plan_reset_count}`；`stall_count` 到 3 触发计划重置，重置上限 2 次（Magentic 同款），不再只靠"两轮无增量"这一条软判据。
2. **任务简报四件套**：`ResearchRequest` 补 `objective / output_format / source_hint / boundaries`，缺项直接拒绝。Anthropic 明确说模糊指令会导致子 agent 重复劳动和留缺口。
3. **轮次自适应**：默认 `max_rounds=2`、`hard_cap_rounds=3`；只有"候选分歧大 + 关键缺口 + 预算允许"才开第 3 轮。多 agent 约 15x token，日内链路还要守 P95。
4. **只回引用，不搬全文**：`ResearchResponse` 只带 `evidence_ids + claim`，正文落 KB；CI 设返回体长度阈值，超限失败。
5. **过程评测**：结果指标之外，加 gap 闭合率、无效补查率、工具效率、引用准确率；Anthropic 用 LLM-judge rubric，20 条起步即可看出大效应。

**四个"不做"项已逐项复核，结论不完全维持**：CrewAI/AutoGen 仍不进主链；Deep Agents 改为"两阶段 + spike"；端到端 RL 改为"小模型判别器 + 轨迹蒸馏"；异步第一周仍不做但必须预留 seam。逐项优缺点对比见 §3.16。

### 3.16 四个"不做"项的逐项复核（2026-11-26）

判断标准只有三条：**能不能审计、能不能控成本、能不能在六人并行下维护**。不按"我们已经有设计"来论证。

#### 3.16.1 CrewAI / AutoGen 进主链 —— 仍不引入

| 维度 | CrewAI / AutoGen | 现有 LangGraph 显式图 |
|---|---|---|
| 上手速度 | 快，角色/团队抽象开箱即用 | 慢，要自己画节点与边 |
| 控制粒度 | 弱，流程藏在 agent 协作里 | 强，路由和停止条件是显式代码 |
| 审计与复现 | 需另建 trace 与账本 | checkpointer + append-only 账本天然可复现 |
| 运行时成本 | 多一套运行时、状态与可观测 | 一套运行时 |
| 适合场景 | 对话式、探索式、原型 | 有固定契约、单写入口、强审计 |

结论：**不进主链，但可以进离线**。主链的硬约束是"单写入口 + 确定性路由 + 每条 claim 带 evidence_ids"，这正是角色抽象最弱的地方；而离线任务（`MT-EVOLVE` 错题分析、红队补证、`MT-REFLECT` 假设生成）延迟不敏感、产物只是 `proposed`、失败可重跑，正好是 CrewAI 的舒适区。落位理由见 §3.17.5。

#### 3.16.2 Deep Agents —— 从"不用"改为"两阶段 + spike"

| 维度 | 自研 harness（现状） | Deep Agents 整包 |
|---|---|---|
| 规划 / todo | 自己写 `ResearchPlan` | `write_todos` 开箱 |
| 子 agent 隔离 | 自己写 `Send` + 独立上下文 | `task` 工具开箱 |
| 上下文压缩 / offload | 需自己实现，长上下文易退化 | summarization + filesystem 开箱 |
| 账本写入权 | 完全可控 | agent 可自主写文件/记忆，需额外拦截 |
| 工具权限 / 预算闸门 | 自己实现，可控 | 需 middleware 补 |
| 版本风险 | 只依赖 LangGraph | 多一个高频演进包 |

结论：**第一周不引，D3 前做 1 天 spike**——只用 `create_deep_agent` 包 AG-LEAD，probe 仍走 `registry.yaml`，验证三件事：能否强制结构化输出、能否拒绝未授权工具、能否逐节点记账。三项全过，第二周替换 AG-LEAD 底座；任一不过，继续用 `create_agent`。这不是"因为已有设计"而拒绝，而是把它变成一个有明确通过标准的实验。

#### 3.16.3 端到端 RL 的 deep research agent —— 不做，改做小模型判别器

| 维度 | 端到端 RL（Tongyi / WebDancer 路线） | 小模型判别器 + 轨迹蒸馏（建议） |
|---|---|---|
| 收益 | 学会"何时继续查"，长程检索强 | 只学"够不够、停不停"，收益窄但直接 |
| 数据 | 需大规模高质量轨迹 + 开放环境 | 用我们自己的 trace，几千条即可起步 |
| 可审计 | 策略不可解释 | 二分类输出，可解释、可回放 |
| 成本 | RL 基建 + 训练 + 评测，重 | 一次 SFT，本地小模型可承担 |
| 与账本契约 | 容易冲突 | 只在 `ASSESS` 前做判定，不碰账本 |

结论：**不做端到端 RL**。先用 S2G-RAG 式确定性控制器 + prompt 拿到主要收益；同时用 `brain_evals/` 累积研究轨迹，P3 训练一个"gap/停止判别器"，只做二分类。等轨迹到 1-2 万条再评估 RL，而不是现在押注。

#### 3.16.4 异步子 agent —— 第一周不做，但现在留 seam

| 维度 | 同步（现状） | 异步 |
|---|---|---|
| 延迟 | 等最慢 probe，Anthropic 明确是瓶颈 | 更低，可动态补派 |
| 一致性 | 简单，轮内并行已足够 | 状态一致性、错误传播复杂 |
| 可复现 | 同一 snapshot 可重放 | 顺序不定，回放难 |
| 预算核算 | 简单 | 并发下难归因 |
| 调试 | 容易 | 明显更难 |

结论：**第一周不做，但不留死**。现在就必须满足三条：probe 无共享可变状态、预算与 `deadline` 随请求传递、probe 幂等。只要守住这三条，P2 把轮内 `Send` 换成异步调度即可，不改契约。触发条件写死：单轮 P95 超过 60s 才考虑，否则同步的确定性更值钱。

#### 3.16.5 顺带对比：单 agent 还是多 agent

| 维度 | 单 agent + 好工具 | 主控 + 并行 probe |
|---|---|---|
| token | 省 | 约 15x |
| 广度覆盖 | 易漏 | 强（Anthropic 内部评测 +90.2%） |
| 上下文 | 易爆 | 隔离 |
| 责任归属 | 清晰 | 需唯一主控 |
| 适合 | 窄问题、单事件、个股问答 | 大盘归因、风口扫描、跨板块 |

结论：**按档位选拓扑**，已写入 §4.2.1——breadth-first 用多 agent，narrow 用单 agent。统一上多 agent 是浪费，统一上单 agent 会漏。

### 3.17 审计分层与框架落位（v1.6）

#### 3.17.1 审计分三层，不是"全有或全无"

| 层 | 记什么 | 去掉的后果 | 策略 |
|---|---|---|---|
| L1 结果 | `run_id`、输入快照、输出、模型/prompt 版本、成本 | 无法复盘"当时输出了什么" | 全量 |
| L2 证据 | 每条 claim → `evidence_ids`、`snapshot_id` | 无法证明结论来源；无法评测、无法时点回放 | 对外结论强制 |
| L3 过程 | 研究树、每次 request/response、工具入参 | 多 agent 出错只能猜；无法去重/防环/算 stall | 采样：正常 10%，失败/冲突 100% |

原文不进 trace，只进 `evidence_id`，正文落 KB。这样存储和延迟可控，又保留"能评测、能回放、能解释"。

#### 3.17.2 为什么审计在这里是"运行态数据"

四个理由，前两个不是合规问题：

1. **时点正确性**：没有 `snapshot_id` 与 `as_of`，无法证明 14:30 的 run 没用 15:00 才发布的数据；A 股还有财务重述、成分调整，没有时点快照，回测和 A/B 的"更准"都不可信。
2. **循环本身依赖它**：`request_id / parent_request_id / round` 同时是去重键、环检测和 stall 计数的依据；去掉 L3，多轮 loop 会退化回"重复问同一个问题"。
3. **错误会复合**：Anthropic 明确说加全链路 tracing 才定位到失败原因；没有 trace，改 prompt 等于碰运气。
4. **合规与信任**：对外发布时引用是责任边界；具体监管要求需法务确认，不作法律判断。

#### 3.17.3 它们不是同一层的"两种方法"

| 层 | 代表 | 职责 | 与本项目关系 |
|---|---|---|---|
| 运行时 / 编排 | LangGraph | 状态图、checkpoint、持久执行 | 已用 |
| 单 agent 构建块 | LangChain `create_agent` | 一个 tool loop | 已用 |
| **Harness** | **Deep Agents** | 在 LangGraph 上预置 planning / subagent / context / filesystem | **可插拔，不换运行时** |
| 框架 | CrewAI | Crews（角色团队）+ Flows（事件编排）+ memory | 另一套运行时 |
| 框架 / 运行时 | AutoGen | AgentChat（对话团队）+ Core（actor 事件运行时） | 另一套运行时 |

类比：LangGraph 是发动机，`create_agent` 是方向盘，Deep Agents 是预装好的驾驶舱，CrewAI / AutoGen 是另一辆车（自带发动机）。所以"Deep Agents vs CrewAI"不是同级选择。

#### 3.17.4 Deep Agents 能用在哪些节点

| 节点 | 适配度 | 理由 |
|---|---|---|
| `AG-LEAD` | 高（主链） | planning + subagents + context offload 正好对应"列候选 → 派 probe → 归因" |
| `MT-EVOLVE` | 高（离线） | 长任务、批量错题、需要文件产物；§5.5 已列为可先试 |
| `MT-REFLECT` | 高（离线） | 夜间长上下文、跨案例归纳 |
| `EX-CHAT` | 中（P2 评估） | 多轮对话需要上下文管理；但必须拦住它写账本 |
| 5 个 probe | 低 | 2-4 步、一个明确 schema，`create_agent` / `StructuredTool` 足够 |
| `CA-TREND` / `CA-RHYTHM` | 无 | 纯计算，无 LLM |
| `MT-CHECK` / `DB-BULL` / `DB-BEAR` / `DB-JUDGE` / `DB-WRITE` | 低 | 单次 LLM、无工具、要严格结构化输出 |
| 规则层 / 渲染 | 无 | 确定性代码 |

一句话：**harness 适合"长、宽、乱"的节点，不适合"短、窄、严"的节点。**

#### 3.17.5 CrewAI 为什么放离线

1. 延迟不敏感：夜间跑，不受 P95 90s 约束，层级 manager 多一次 LLM 调用可接受；
2. 产物是 `proposed`，人工批准才生效，不进生产账本；
3. 形态匹配：错题分析、红队、假设生成天然是"多角色讨论 + 批量处理"；
4. 失败可重跑，不要求强时点复现（但仍保留输入快照）；
5. 放主链的代价是换运行时、丢 checkpointer、破坏 registry / 权限 / 账本，收益不抵成本。

落位：`MT-EVOLVE`（错题分析、红队补证）、`MT-REFLECT`（假设生成）；**不进主链**。

#### 3.17.6 引入 Deep Agents 的得失

**得到**：

- 计划/待办不用自己写，`write_todos` 直接对应 `ResearchPlan.questions`；
- 子 agent 天然隔离上下文，减少串味；
- 长文与产物落 filesystem，agent 之间只传引用，正好配合"只回 evidence_ids"；
- 摘要/压缩开箱，长上下文更稳。

**代价**：

- 多一层封装，出问题时定位更深；
- 工具权限、预算闸门、结构化输出要靠 middleware 兜，不能默认可用；
- 版本演进绑定比只用 LangGraph 快；
- **绝不能放开 filesystem 写账本**，账本仍由规则层单写。

**边界**：probe、`CA-*`、`DB-*`、规则层与渲染层都不用；D6 spike 三项（强制结构化输出、拒绝未授权工具、逐节点记账）任一不过，就退回 `create_agent`。

**引入范围定稿**：`AG-LEAD`（主链，spike 通过后）+ `MT-EVOLVE` / `MT-REFLECT`（离线）+ `EX-CHAT`（P2 评估）。

### 3.18 probe 的 agent 属性与"智能在哪"（v1.8）

#### 3.18.1 五个 probe 的准确定位

| 问题 | 答案 |
|---|---|
| 算不算 agent | 算，但是**受控 agent**：有 LLM + 工具循环，无持久记忆、无账本写权、不能直调同级 |
| 是不是 ReAct | 是单 agent ReAct（`create_agent`），不是自由 ReAct：`max_steps` 上限、工具白名单、结构化输出 |
| 用不用 tool | 用，只能经 `tools/` 统一客户端，禁止 probe 自己请求外部源 |
| 用不用 harness | 用轻 harness：`create_agent` + middleware + `TimeoutPolicy`；**不用 Deep Agents** |
| 是否多轮 LLM | 请求内可多步（tool → observe → 再判断），受 `max_steps` 限制；跨请求的多轮由 AG-LEAD 控制 |
| 能否同级协作 | 只能间接：`suggested_requests` → `OR-ROUTER` → 另一个 probe |

"Deep Agents 的子 agent"是**调用形态**，"probe"是**职责**。若 AG-LEAD 换成 Deep Agents，probe 可注册成 `task` 子 agent，契约仍是 `ResearchRequest → ResearchResponse`。

#### 3.18.2 两层多轮

| 层 | 谁控制 | 边界 | 例子 |
|---|---|---|---|
| probe 内部多步 | probe 自己 | `max_steps`、工具白名单 | 先搜事件，再读全文，再核对落地时间 |
| 研究循环多轮 | AG-LEAD + 确定性控制器 | `max_rounds=2`（硬上限 3）、预算、`Gap` 驱动 | 缺 exposure → 第二轮只派资金 probe |

#### 3.18.3 三张时序

1. **单个 probe**：`ResearchRequest → tool_call → observation → 够不够判断 →（补查）→ 写 evidence 正文 → 返回 claims/evidence_ids/gaps/suggested_requests`。
2. **同级补证**：A 返回 `suggested_requests` → `OR-ROUTER` 去重/防环/预算校验 → 转给 B → B 带 `evidence_ids` 返回 → AG-LEAD 更新冲突与置信。
3. **整个系统**：`调度 → OR-RUN（冻结 snapshot、出 RunBrief）→ AG-LEAD → probes（第一轮并行）→ ASSESS（+ RoundLedger）→（第二轮）→ ResearchResult → DB 多空/裁决/落账 → 出口`。

#### 3.18.4 为什么"受限"不等于"不智能"

智能没有集中在某一个 agent，而是分在四层：

| 层 | 承担什么智能 |
|---|---|
| 规则层 | 制度：时点、预算、档位、单写入口 |
| AG-LEAD | 研究策略：问题拆解、假设（含反方）、充分性判断、补查路由、收敛 |
| probes | 专业取证：只回答自己那一类问题，工具用得多深由 `max_steps` 定 |
| DB / KB / MT | 裁决与记忆：多空对抗、历史证据、方法沉淀 |

四条限制都有明确目的，不是"为了管住它"：

- **无持久记忆**：probe 每次拿 KB 投影，系统级记忆在 KB-EVIDENCE / KB-CLAIM / KB-METHOD，不在某个 agent 的上下文里；这样换模型、重跑、回放都不受影响。
- **无账本写权**：单写入口，避免五个 probe 并发覆盖同一结论；probe 仍可通过工具写 evidence 正文，只是不写 judgment。
- **不能直调同级**：防止重复取证、A→B→A 死循环、以及"同级结论互相污染"；请求统一走路由器，才可去重、计预算、留痕。
- **不自发起第二轮**：全局轮次、预算、收敛必须由一处掌握；否则每个 probe 都能加轮，成本失控且无法判断何时停。

反过来说：如果每个 probe 都有持久记忆、写账本、互调、自发起轮次，系统会得到"更多自主性"，但会换来重复劳动、结论互相污染、无限循环和无法复现——这正是单轮 ReAct 之外更严重的失败模式。

**所以 AG-LEAD 不是"唯一的大脑"，而是"研究策略的主控"**：它决定查什么、够不够、要不要再查；probe 决定怎么查；DB 决定信谁；KB/MT 记住发生过什么。智能在"循环 + 记忆 + 契约"，不在单个 agent 的自主度。

#### 3.18.5 两个档位的时序差异

| 维度 | 晨报 | 市场溯源 |
|---|---|---|
| 触发 | 定时 06:00，06:30 必须出 | 收盘后按需 |
| 目标 | 昨日复盘 + 今日关注 | 4 个候选 × 6 阶段因果链 |
| 轮次 | 最多 2 轮，缺数据可 `partial` | 最多 3 轮，允许 `insufficient` |
| 关键约束 | 时间死线优先 | 广度优先，反证必须保留 |
| 典型第二轮 | 补北向/两融 | 补 `transmission` / `exposure` |

### 3.19 让 probe 更聪明：四个杠杆与边界（v1.9）

目标不是给 probe 更多自主权，而是提高**单位 token 的有效证据产出**。

#### 3.19.1 工具更准

| 做法 | 机制 |
|---|---|
| 一工具一目的 | 每个 probe ≤7 个工具；高频链式调用合并成一个（如"板块 + 龙头 + 资金"一次返回） |
| 命名空间 | `wind_*` / `event_*` / `capital_*`，减少选错 |
| 返回有意义上下文 | 不只回数据，还带 `as_of / source / unit / missing_fields / reliability` |
| Token 效率 | 默认只回必要字段；长文用 `fetch_detail(evidence_id)` 二次取 |
| 错误可行动 | `no_data / stale / timeout / bad_arg` 分开，附建议 |
| 预算感知 | prompt 明说"最多 N 次调用，证据够就停"；单纯加预算不会更好 |
| 评测驱动 | 每个 probe 20–30 条真实任务，测工具选择、参数、调用数、token、错误率，留 held-out |

#### 3.19.2 KB 投影更全

按问题生成三块投影，而不是塞整个 KB：

| 块 | 内容 | 预算 |
|---|---|---|
| Fact | 当前标的/板块最新证据，按相关性、时效、可信度排序，带 `evidence_id` | ~2k tokens |
| Prior | 近 30 天相关 judgment（active / superseded）、置信、反证 | ~1k |
| Method | 检查清单 + 历史案例摘要 | ~1k |

规则：总投影 < 8k；**反证必进**，没有反证标 `one_sided`；投影只给摘要与索引，细节用 `kb_read(evidence_id)` 即时取；去重、带标签、不放大段自然语言。

#### 3.19.3 历史案例作为上下文

- 案例结构：`case_id / as_of / regime / subject / question / evidence_pattern / what_worked / what_failed / outcome / tags`。
- 检索：BM25 + embedding 混合，先按市场状态、板块、horizon 过滤，取 top 3–5，成功与失败各至少 1 条。
- 用法：写成"相似点 / 不同点 / 可借鉴动作 / 不要照搬"，**给方法，不给结论**。
- 防泄漏：案例 `outcome` 必须在当前 `as_of` 之前已知，否则不许进投影。
- 沉淀：`MT-EVOLVE` 从账本提炼，人工抽检后进 KB-METHOD；增量追加，禁止全量重写（避免 context collapse）。

#### 3.19.4 按 probe 调 max_steps

- 先测步数分布、每步新增证据数、边际收益曲线；
- 初始值：风口 6、事件 6、基本面 5、资金 5、宏观 4；硬上限 +2；
- 动态：只有命中关键 `Gap` 才加 1–2 步；连续两步无新增证据强制停；
- 监控：steps p50/p95、无效步占比、证据/步、超时率，按月调。

#### 3.19.5 三色区边界（负责人可改什么）

| 区 | 内容 | 谁定 |
|---|---|---|
| 红区 | 契约、state 通道、ID/账本、OR-ROUTER、预算/轮次、registry、权限 | 组长，改动需架构评审 |
| 黄区 | 工具白名单、prompt 结构、投影/检索策略、案例选择、`max_steps` 区间 | 负责人提 PR，组长 review |
| 绿区 | 实现细节、单测、日志、内部命名、缓存 | 负责人自主 |

**接口即边界**：probe ≤150 行；只返回 `ResearchResponse`；不请求外部源；不写账本；不直调同级；必须带 golden + 降级用例。

#### 3.19.6 Probe 记分卡与 DoD

每个 probe 一张卡：工具选择正确率、参数正确率、证据产出率、gap 闭合率、引用准确率、P95、token/条结论。

完成定义（DoD）：

1. 只改自己目录与 `registry.yaml` 一行；
2. 返回体符合 `ResearchResponse`，缺数据产出 `Gap` 而不是空；
3. 至少 10 条 golden（含 2 条降级）；
4. 工具调用有预算上限，连续无新增证据会停；
5. 记分卡数据可采集。

### 3.20 V3 的智能上限与学习闭环（v1.9）

#### 3.20.1 距离资深分析师还差什么

现有设计能回答"为什么涨跌、谁在买、有没有证据"，但资深分析师的结论还包含：

| 缺口 | 需要补的能力 |
|---|---|
| 预期差 | `KB-EXPECT`：市场一致预期、超预期/低预期 |
| 估值与空间 | `CA-VALUATION`：估值分位、目标价区间、风险收益比 |
| 横向比较 | 同业/板块内对照，而不是只看单标的 |
| 催化剂日历 | 财报、解禁、政策窗口、事件到期 |
| 反证与证伪 | 已有 DB-BEAR，但缺"什么条件下我错了"的显式记录 |
| 置信校准 | 预测分桶 vs 实际命中率，调整置信 |
| 方法沉淀 | 把反复有效的检查清单写回 KB-METHOD |
| 组合视角 | 仓位、相关性、流动性约束 |

结论：**当前层级合理，但只到"研究助理 + 初级分析师"**。要到资深，必须补"预期差、估值、横向比较、证伪"四类工具，而不是再加一个泛泛的 agent。

#### 3.20.2 层级是否合理

保留四层：规则层（制度）→ AG-LEAD（研究策略）→ probes（取证）→ DB（裁决/落账）。需要补两个**确定性**层，而不是新 agent：

- `CA-EXPECT`：一致预期与超预期计算；
- `CA-VALUATION`：估值分位、目标价区间、风险收益比。

它们走工具，不走 LLM；结论仍由 DB-JUDGE 裁决。

#### 3.20.3 哪些节点用什么 LangChain / LangGraph 形态

| 节点 | 形态 | 理由 |
|---|---|---|
| AG-LEAD | `create_agent` + middleware（或 D6 后 Deep Agents） | 需要动态选 probe、多步判断 |
| 5 个 probe | `create_agent` + `ToolStrategy` 结构化输出 | 有工具选择，但步骤有界 |
| 简单 probe（宏观） | LCEL / 单次结构化调用 | 不需要 ReAct，省一次循环 |
| `MT-CHECK` | 单次 LLM + 结构化输出 | 无工具 |
| `DB-BULL` / `DB-BEAR` | 单次 LLM + 结构化输出 | 读 claim，不取数 |
| `DB-JUDGE` | 确定性打分 + LLM 解释 | 分数可复现，解释可读 |
| `CA-*` | 纯 Python Tool | 数字必须可复现 |
| `OR-*` | 确定性代码 | 路由不能靠 LLM |
| `EX-*` | 渲染 / 模板 | 不参与推理 |

LangGraph 侧只用四件事：`StateGraph` 子图、`Send` 扇出、`Command` 路由、Postgres checkpointer；长期记忆用 Store 的 namespace，不塞进 state。

#### 3.20.4 越用越聪明的五个闭环

| 闭环 | 机制 | 频率 |
|---|---|---|
| 结果验证 | 每个 judgment 带 `horizon / due_at`，到期由 `MT-VERIFY` 打分 | 每日 |
| 错题归因 | `MT-EVOLVE` 按"方向错 / 幅度错 / 主因错 / 漏催化 / 数据错 / 时机错"分类 | 每周 |
| 方法沉淀 | 有效检查清单增量写入 KB-METHOD，带支持数与最后验证时间 | 每周 |
| 校准 | 置信分桶 vs 命中率，偏移则调阈值 | 每月 |
| 方法 A/B | 新方法/新 prompt 先离线回放，显著优于旧版才晋级 | 每次变更 |

关键：**学习发生在方法和阈值上，不训练基础模型**。每条方法必须可回滚、可 A/B、带证据；否则会"越学越自信"而不是"越学越准"。

#### 3.20.5 路线

- **P0（第一周）**：结果验证 + 错题分类字段 + 方法库只读。
- **P1（第二周）**：方法增量写入 + 置信校准 + 方法 A/B。
- **P2**：预期差、估值、横向比较三个工具；小模型判别器。

#### 3.20.6 学习闭环实施顺序（已定）

顺序不能颠倒：**没有结果标签，后面的验证、归因、方法沉淀全是空转**。

| 序 | 步骤 | 产出 | 前置 | 门禁 |
|---|---|---|---|---|
| 1 | 结果字段 | `Judgment` 增 `due_at / verify_status / outcome / error_tags` | 契约评审 | 字段可空、向后兼容 |
| 2 | 到期验证 | `MT-VERIFY` 每日扫描到期 judgment，写验证记录 | 步骤 1 | 到期未验证率 < 5% |
| 3 | 错误分类 | 六类标签：方向 / 幅度 / 主因 / 漏催化 / 数据 / 时机 | 步骤 2 有 ≥20 条样本 | 人工抽检一致率 ≥ 80% |
| 4 | 方法库版本化 | `KB-METHOD`：`method_id / version / support / last_validated / status` | 步骤 2 | 每条方法可追溯到案例 |
| 5 | 离线提炼 | `MT-EVOLVE` 每周产出 `proposed` 方法与案例 | 步骤 3、4 | 只提案，不自动生效 |
| 6 | 回放 A/B | 新方法在回放集对比旧版 | 步骤 5 | `n≥30`，显著优于旧版才晋级 |
| 7 | 置信校准 | 分桶命中率 vs 置信，偏移调阈值 | 步骤 2 有 ≥100 条 | 校准前后 Brier 分数下降 |
| 8 | 反馈投影 | 高价值案例/方法提高检索权重，写进 KB 投影 | 步骤 6、7 | 可回滚 |

硬规则：**前一步没有数据，后一步不许开工**；步骤 5 的产出永远先进 `proposed`，人工批准才进 `active`。

**P0 契约增量（已落 v1.14）**：`Judgment` 增 `due_at`；新增 append-only `VerificationRecord`（`verify_status / outcome / error_tags`），`verify_at = due_at + 3 个交易日`；Judgment 上的 `verify_status / verified_result` 只是投影。

### 4.2 绞杀榕：组长打样 + 五波接入

**统一六步**（每个功能都走）：

1. 建影子：新链路跑同一输入，只落影子表，不对外；
2. 同输入对照：同 `snapshot_id`，比账本完整性、时延、token；
3. 门禁：账本 100%、P95 与成本在预算内、方向抽检无显著退化；
4. 灰度：1% → 10% → 50% → 100%，按用户/时段/标的；
5. 老链路转只读：不再写库，不再被新入口调用；
6. 删除：停 cron、删入口、归档对照记录。

**组长打样选 `review`（大盘复盘/溯源）**：盘后、非实时、覆盖 5 个 probe + 6 阶段 + 冲突裁决。打样产出不是代码，而是**接入手册**：registry 示例、golden 模板、降级用例、PR checklist。若组长负责的不是 `review`，就选一个"覆盖 ≥3 个 probe、有裁决、非实时"的功能。

| 波次 | 现有功能（worker） | V3 落点 | 复用方式 | 关键风险 |
|---|---|---|---|---|
| 0 | `review` | `market_review` | 真做风口/事件，其余 stub | 无历史对照，只比工程指标 |
| 1 | `wind_leader` / `stock_trace` | `wind_board` / `stock_on_demand` | probe 复用 | 板块码与个股码命名空间 |
| 2 | `stock` / `sector` / `sector_trace` / `event` | `stock_on_demand` / `sector` / `event_driven` | probe + 临时 adapter | 单个 worker 里混了多段逻辑，需拆分 |
| 3 | `morning` / `midday` / `alert` | `morning_brief` / `intraday_brief` / `alert` | 依赖前两波结果 | 时间死线，不能拖 |
| 4 | `broadcast` / `midday_broadcast` / `hot_burst` | 出口渲染 / 报告 | 只做渲染，不进研究层 | 音频链路不在 Python |
| 5 | `trend_score` / `rhythm_master` / `iterate` | `CA-TREND` / `CA-RHYTHM` / `MT-EVOLVE` | 确定性工具或离线 | 不要为了统一而上 LLM |

每波切换门槛一致：影子 ≥3 个交易日、账本 100% 完整、P95 与成本在预算内、方向无显著退化、可一键回滚。**老链路先转只读，再删 cron**，不允许直接删。

> 已定：采用**混合迁移**——核心研究型 worker 先包 adapter 做影子对照，4 周内拆成“工具 + prompt + probe”；生产型与计算型不进研究层。`alert` 已定走秒级快路径；`hot_burst` 是否需要独立 `institutional` 能力仍待定。

### 4.3 Owner 与统一开发规范

| 角色 | 负责 | 不碰 |
|---|---|---|
| 组长 | 主图、contracts、state、OR-ROUTER、预算、registry、CI | 各 probe 内部实现 |
| 各功能负责人 | 自己的 `probes/<name>/`、工具白名单、prompt、golden、降级用例、registry 一行 | 主图、契约、其他 probe |

规范：

1. **契约先行**：先改 Pydantic，再生成 Schema/TS，CI 重新生成后 `git diff --exit-code`；
2. **单写入口**：只有 app-api 写账本，Python 与研究层不得写；
3. **分层单向**：`graph → nodes → probes → tools → contracts`，CI 用 import-linter；
4. **PR 三件套**：变更说明 + golden 结果 + 回滚方式；缺一不合并；
5. **三色区**：红区组长批，黄区组长 review，绿区负责人自主（见 §3.19.5）；
6. **一次只改一个维度**：prompt、工具、预算不同时改，否则无法归因。

### 4.4 A/B 测试约定

- **对象**：同一张图、同一 `snapshot_id`，只切 profile（旧链路 vs V3，或旧 prompt vs 新 prompt）。
- **样本**：配对样本，按交易日/标的配对；`n≥30` 才判定，`n=10` 只做冒烟，不宣布胜负。
- **指标**：结果（方向、主因、置信校准）+ 过程（gap 闭合率、无效补查率、工具效率、引用准确率）+ 工程（P95、token/条）。
- **判定**：配对 bootstrap 置信区间；区间跨 0 不判胜负；不 early stop；不按单日结果调整。
- **防污染**：A/B 期间不改 prompt/工具；两组用同一模型版本；隐藏组别给评审。
- **回滚**：profile 开关一键切回；影子表保留 30 天。

### 4.5 试点：先用自己负责的功能跑通

**选点原则**：非实时、输出可对比、覆盖 ≥3 个 probe、有冲突或降级场景。推荐从自己负责的 `wind_leader` + `stock_trace` 开始；如果负责 `review`，直接用它打样。

两周节奏：

| 阶段 | 做什么 | 出口 |
|---|---|---|
| 第 1 周 | 接 1 个真实 probe + 其余 stub；跑通两轮 loop；落影子表 | 账本完整、gap 可查、P95 可测 |
| 第 2 周 | 接第 2 个 probe；做 3 天影子对照；灰度 1% | 无显著退化、可回滚 |

试点必须记录的问题清单：数据缺口、快照时点、工具延迟、prompt 歧义、预算超限、降级路径、前端字段兼容。**试点目标是暴露问题，不是证明架构正确**；问题清单直接进 §4.3 的接入手册。

### 4.6 时间档位与共享资源隔离

不同功能跑在不同时间，统一架构必须先保证互不拖累。

| 档位 | 时间约束 | 轮次 | 策略 |
|---|---|---|---|
| 晨报 06:00 | 硬死线 06:30 | 最多 2 轮 | 缺数据标 `partial`，不拖 |
| 盘中告警 | 秒级 | **不跑 loop** | 确定性触发 + 单次 LLM 解释 |
| 盘后复盘/溯源 | 分钟级 | 2–3 轮 | 广度优先，允许 `insufficient` |
| 个股按需 | 十秒级 | 1–2 轮 | 只开 2–3 个 probe |

四个共享件的隔离方式：

| 共享件 | 隔离方式 |
|---|---|
| `snapshot` | 每个 run 独立生成，跨 run 不复用；缓存键含 `snapshot_id + 参数` |
| 账本 | owner 键含 `type / horizon / judgment_type`；app-api 单事务分版本，功能之间不会互相顶掉 |
| 路由与预算 | 按 profile 配置；晨报、盘中、盘后各自预算与超时 |
| 模型配额 | 按 profile 分队列与并发上限；盘中告警优先，盘后复盘可排队 |

三条硬规则：

1. **告警不套多轮 loop**：秒级场景只做确定性触发 + 单次解释，否则时延和成本失控；
2. **节点不得读系统时钟**：一律用 run 的 `as_of`，避免不同时段功能互相污染；
3. **幂等键**：`(profile, as_of, subject, snapshot)`，重复触发不重复记账。

## 6. 验收标准（第一周）

1. 一条真实 run 产出 judgment，含 `evidence_ids`、`confidence`、`invalidators`、`verify_at`。
2. 确定性与去重要分两个口径，不能混为一个"重复率"：
   - **同一 run 内**：`tools/` run 级 memo 生效，`duplicates / total < 5%`（即去重后唯一率 > 95%），由 memo 输出的 `{total, unique, duplicates}` 直接计算；
   - **跨 run 回放**：固定 `as_of` + 录制工具响应，两次 run 的 `evidence_id` 集合完全一致；
   - 实盘非回放模式允许数据更新导致差异，不纳入本门禁；两种口径都必须无两条 active。
3. 任一 probe 超时/空数据，run 仍产出结果：status 为 `partial`，且 `missing_probes` 含 `required=true` 项；若必查缺失导致无法出结论，则 status 为 `insufficient`。预算触顶记 `stop_reason=budget`，不改变 status 也不计入 partial。"出口不展示空结论"的判定层明确为 **app-api 的出口查询**（`status != 'ok'` 且无有效 evidence 时不返回），不是前端兜底。
4. Schema 连续生成两次 sha256 一致、CI diff 为 0、TS 类型可编译，且 TS 文件头有 `// generated, do not edit`。
5. 3 条影子 run 的 P95、token、partial 率、预算触顶率有记录，可与老链路并列；**不比较方向**。
6. registry 校验能分别拦住"未登记模块""空登记""`deps` 成环""指纹变化"四类。
7. 并行确定性单测通过：同一批输入以两种到达顺序合并，`evidence` / `claims` 结果完全相同。
8. import-linter 通过：`graph → nodes → probes → tools → contracts` 单向；`probes → adapters → 旧 workers` 单向，旧 workers/graph 禁止 import `brain_v3`；运行时无 `brain_evals` 依赖。

| **升级依赖炸影子基线** | `lock` 文件被单人改动 | lock 变更需两人 review + PR 模板勾选旧链路兼容评估（§3.8） |

| **旧基线被误当目标** | 拿"播报方向 4/5"当新链及格线 | 基线只作老链路水平参考，不设为目标（§1） |
| **并行 reducer 结果漂移** | 同输入两次 run 的 claims[0] 不同 | 按内容排序 + 禁止下标取值 + 确定性单测（§3.10） |
| **预算触顶被算作 partial** | B 组 token 更低但 partial 更高 | `stop_reason=budget` 独立统计，不进 partial 率（§3.6） |
