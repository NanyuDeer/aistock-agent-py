## 0. 一句话理解

**智慧大脑不是把各模块的报告收上来做二次总结，而是让所有功能跑在同一套 LangGraph 编排里：一张主图负责编排与共享状态，每个能力都有自己的子图，子图之间通过证据与论点互相影响。**

现在的系统是「每个功能一条竖井」：前端每张卡各自调接口拼结论，app-api 每个模块各抓各的数据，agent-py 由 supervisor 一次路由到单个 Agent、执行完即 END。功能之间没有共享状态，信息和分析逻辑互不影响。

目标是把这些竖井合成**一套作战图**：

- 同一份工作记忆（append-only 证据账本）；
- 同一套证据与论点契约；
- 同一条研判链（多方 → 反方 → 冲突 → 落账）；
- 同一份研判，多处渲染。

各功能不再是「各自出报告的科室」，而是这套图里的不同角色：**感知、研究、质疑、校准、表达**。它们通过共享证据互相影响，而不是在页面层被临时拼在一起。

**不要求物理上只有一张图**：主图（`run_orchestrator` 所在的 StateGraph）负责编排、共享 state 与研判；八个研究能力域各自是独立可编译的 LangGraph 子图，可以单独运行、单独测试、单独部署。运行时按 §1.1 收敛为「AG-LEAD 主控 + 5 个取证子 agent + 2 个计算工具」，能力域一个不少。它们之间的关联靠**同一套契约 + 同一个账本 + 显式的读写边**，而不是把所有节点硬塞进一个文件。

**仍然不做的事**：不新增对话 Tab、不做追问输入框、不把前端做成"会诊界面"。对话只作为只读账本的一个出口。

## 1. 定位与边界

| 维度 | 说明 |
|---|---|
| 是什么 | 一套**统一的 LangGraph 编排**：一张主图 + 多个功能子图；功能模块是图里的角色节点 / 子图 / LangChain 工具 |
| 不是什么 | 不是聊天机器人；不是"各模块出报告 → 大脑二次总结"；不是一个大模型从头写到尾 |
| 核心价值 | 让功能之间的信息与推理**互相影响**，形成单一研判，而不是多份互不相关的结论 |
| 成功标准 | 同一只票/板块/事件在全站只有一个结论；结论可解释、可验证、可复现；准确率可持续校准 |

**五条设计原则**

1. **单一数据源**：app-api 仍是数据 owner，Agent 通过工具取数，不直连外部源。
2. **单一研判账本**：一次研判只写一条 `judgment`，所有出口引用同一个 `judgment_id`。
3. **增量证据**：节点只 append 证据/论点，不覆盖别人的结论；下游按投影读取。
4. **冲突显式**：模块之间矛盾时不强行合并，输出分歧点并降档置信度。
5. **可验证**：每条研判必须带失效条件与验证时间，到期回填。

### 1.1 两层定位：规则层管「怎么跑」，研究层管「怎么想」

节点数量不等于智能程度。判断权集中在哪、能不能验伪、能不能并行、能不能复盘，才决定系统是否智能。因此全图按职责切成两层：

| | 规则层（确定性骨架） | 研究层（智能 agent） |
|---|---|---|
| 回答什么 | 什么时候跑、跑哪个档、必须查什么、花多少预算、写不写账、怎么验证 | 这次现象可能是什么原因、先查谁、证据够不够、要不要换假设 |
| 节点 | IN-TIME ~ IN-VERIFY、OR-RUN、**OR-PROFILE 档位模板**、OR-SCOPE 工具权限、KB-EVIDENCE ~ KB-GOV、DB-JUDGE 裁决、MT-CALIB 校准、MT-VERIFY 验证、EX-BRIEF ~ EX-PICK 渲染 | AG-LEAD 归因主控、AG-WIND / AG-EVENT / AG-FUND / AG-CAPITAL / AG-MACRO 子 agent、DB-BULL / DB-BEAR 辩论、EX-CHAT 对话、MT-EVOLVE 方法演化 |
| LLM 角色 | 分类、模板填充、规则计算；不做自由循环 | 自由循环、假设、验伪、换工具 |
| 出问题怎么查 | 查档位表、预算、工具权限 | 查 trace 里的工具调用与证据引用 |

研究层内部再分三种角色：

| 角色 | 节点 | 形态 | 是否 agent |
|---|---|---|---|
| 主控 | AG-LEAD 归因 | bounded ReAct，唯一 lead agent | 是 |
| 取证子 agent | AG-WIND 风口 / AG-EVENT 事件 / AG-FUND 基本面 / AG-CAPITAL 资金 / AG-MACRO 宏观 | 独立上下文、独立工具子集、2-4 步上限，只返回结构化 claim | 是，但不是主控 |
| 计算工具 | CA-TREND 趋势 / CA-RHYTHM 节奏 | 公式计算，LLM 只写解释 | 否 |

两层只通过两个结构交互：

- **RunBrief**（规则层 → 研究层）：`{ run_id, 档位, 标的, 必查清单, 可选清单, 步数预算, 时间截面, 可用工具, 输出 schema }`
- **ResearchResult**（研究层 → 规则层）：`{ claims[], evidence_ids[], confidence, partial, tool_calls }`

硬边界：研究层不直接写 KB-EVIDENCE/KB-CLAIM/KB-JUDGMENT；规则层负责校验、落账、渲染。研究层失败只能返回 `partial` 或 `insufficient`，不能绕过规则层编结论。

**为什么不是 8 个并列研究员**：8 个固定工位顺序全跑，没人判断「要不要查、查到什么程度算够」，本质是流水线。AG-LEAD 是唯一需要「多假设 + 反复验伪」的 agent；CA-TREND / CA-RHYTHM 是纯计算；其余 5 个是专项取证。收敛后主图研究节点从 8 个降到 1 个主控，能力域一个没少。

**为什么不是 1 个巨型 agent**：5 个领域的原始数据全进一个上下文会造成上下文污染；单 agent 拿 20+ 工具选择准确率明显下降；结论只有一段文本时，`modules` 字段与证据追责无从落地。Anthropic 的判据是：只有「上下文污染 / 可并行 / 专业化」三种情况才值得拆子 agent，我们三条都命中。

#### 层内再细分（避免「规则层」变成一个大筐）

规则层按职责再分四小类：

| 子类 | 节点 | 特征 | 代码落位 |
|---|---|---|---|
| 触发与编排 | IN-TIME ~ IN-VERIFY、OR-RUN、OR-PROFILE、OR-SCOPE | 决定跑不跑、跑哪档、给多少预算、能用什么工具 | agent-py `brain_v3/` 编排层（旧实现为 `graph/brain/`） |
| 计算与规则 | CA-TREND、CA-RHYTHM、DB-JUDGE、MT-CALIB、MT-VERIFY、MT-CHECK | 公式或规则表，可单测、无自由循环 | 重计算在 app-api，薄包装与规则在 agent-py |
| 账本与治理 | KB-EVIDENCE ~ KB-GOV | append-only、投影、检索排序、指标 | app-api 持久化 + agent-py state / reducer |
| 表达 | EX-BRIEF ~ EX-PICK | 模板渲染、推送、对话 | agent-py 出 payload，app-api / 前端渲染 |

研究层按角色再分三小类：

| 子类 | 节点 | 特征 |
|---|---|---|
| 主控 | AG-LEAD | 唯一有自由循环与判断权 |
| 取证子 agent | AG-WIND / AG-EVENT / AG-FUND / AG-CAPITAL / AG-MACRO | 2-4 步、独立上下文、只返回结构化 claim |
| 计算工具 | CA-TREND / CA-RHYTHM | 不跑 LLM 循环，返回确定性快照 |

**CA-TREND / CA-RHYTHM 不是「研究员」也不是「研究子图」，是计算工具**：CA-TREND 的趋势评分本身在 app-api 的 `TrendScoreService` 里算好（`trend_scores` 表 + `/internal/trend/score/:symbol`），agent-py 只做支撑压力的薄计算；CA-RHYTHM 的恐贪与仓位规则是纯公式，LLM 只写解释。把它们和研究 agent 混为一层，会让人误以为它们也需要「思考」。

### 1.2 代码落位：谁负责算，谁负责编排

| 职责 | 仓库 / 模块 | 现状 | 目标 |
|---|---|---|---|
| 行情 / K 线 / 资金 / 板块 / 财务 / 新闻取数 | app-api `core/routes` + `modules/*` | 已有 | 不变，仍是唯一数据 owner |
| 趋势评分（S/A/B/C/D） | app-api `modules/monitor/TrendScoreService` + `trend_scores` 表 | 已有 | CA-TREND 调 `/internal/trend/score/:symbol`，不重复实现 |
| 资金 / 筹码指标 | app-api 资金流、龙虎榜、两融模块 | 已有 | AG-CAPITAL 以工具调用，不在 agent-py 重算 |
| 板块强度 / 龙头 | app-api 板块接口 | 已有 | AG-WIND 子 agent 调用 |
| 情绪 / 恐贪、仓位规则 | agent-py `brain_v3/rules/rhythm.py`（新） | 现散在 `rhythm_master.py` | 抽成纯函数，CA-RHYTHM 直接调用 |
| 支撑 / 压力（20 日区间） | agent-py `graph/brain/nodes/trend.py`（旧） | 已有 | 保留为薄计算，不新增评分体系 |

| state / reducer / 投影 | agent-py `graph/brain/state.py`（旧） | 已有 | 加三因子检索排序 |
| MT-CHECK 元认知 | agent-py `brain_v3/nodes/metacognition.py`（新） | 无 | 新增 |

原则：**app-api 负责「数」和「重算」，agent-py 负责「编排、判断、账本投影」**。agent-py 不复制 app-api 已有的评分与指标实现；app-api 不引入 LLM 编排。

V3 按「谁负责」把节点分成九层、六个组；可交互图见 `docs/智慧大脑-V3-分层结构图.html`。

| ⑤ 研究 | AG / CA | 研究组 | ResearchResult |

## 2. 总体架构：主图 + 子图 + 一条记忆脊柱

```
触发层：时段 / 事件 / 用户 / 验证
                        ↓
              run_orchestrator（档位 · 预算 · 扇出）
                        ↓
              OR-PROFILE 档位模板（必查清单 · 预算 · 降级）──RunBrief──▶ 研究层
                        ↓
感知层：market / event / entity / user ──写──▶ KB-EVIDENCE 证据账本
                        ↓ 投影 / 增量                 │
研究层：AG-LEAD 归因主控（唯一 lead agent）◀─────────────┘
          ├─ 计算工具：trend_snapshot / rhythm_snapshot（CA-TREND / CA-RHYTHM，确定性）
          └─ 子 agent：wind_probe / event_probe / fundamental_probe / capital_probe / macro_probe
             （独立上下文，只返回结构化 claim；必查项由 OR-PROFILE 规定）
                        ↓ ResearchResult
研判层：bull → bear → conflict_resolver → judgment_writer ──▶ KB-JUDGMENT 研判账本
                        ▲                                  │
        MT-CALIB 校准先验 ────┘                                  ├──▶ 表达层：briefing / stock_view / push / chat
                                                           └──▶ MT-VERIFY 验证（due+3）→ KB-JUDGMENT / KB-METHOD → 研究先验
工具带：app-api 24 项能力 → LangChain StructuredTool（统一 provenance）
```

### 2.1 五个角色层

| 层 | 节点 | 做什么 | 相对现状的变化 |
|---|---|---|---|
| 触发（规则层） | 时段 / 事件 / 用户 / 验证 | 只产生统一的 run 触发，不直接调各 Agent 函数 | 调度与图解耦 |
| 编排（规则层） | `run_orchestrator` + **OR-PROFILE 档位模板** | 按触发源 + 标的 + 预算选档，发 RunBrief，规定必查与降级 | 替代 supervisor 的单次路由 |
| 感知（规则层） | `market_perception` / `event_perception` / `entity_perception` / `user_perception` | 取一次数、做一次实体链接，写成证据 | 消除各模块重复取数 |
| 研究（研究层） | **AG-LEAD 主控** + `wind_probe` / `event_probe` / `fundamental_probe` / `capital_probe` / `macro_probe` + `trend_snapshot` / `rhythm_snapshot` | AG-LEAD 按 RunBrief 调子 agent 取证并验伪；子 agent 独立上下文、只返回 claim；快照是确定性计算 | 从「8 个固定工位」到「1 个现场指挥 + 按需取证」 |
| 研判（混合） | `bull_advocate` / `bear_advocate`（研究层）；`conflict_resolver` / `judgment_writer`（规则层） | 多空辩论用 agent；冲突分级与落账用规则 | 从多份报告到一个 judgment |
| 校准（规则层） | `calibrator` / `verifier`（规则）；`method_evolver`（研究层，离线） | 置信度校准、到期验证、失败模式版本化 | 从复盘文件到自动回灌 |
| 表达（规则层） | `briefing_writer` / `stock_view_writer` / `push_dispatcher` / `pick_view_writer`（模板）；`chat_responder`（研究层，只读账本） | 同一研判多处渲染 | 前端不再拼结论 |

### 2.2 互相影响怎么发生（不是口号）

| 影响链 | 具体机制 |
|---|---|
| 市场 → 板块 | `market_perception` 写风险偏好 / 量能 / 风格证据；`wind_research` 用它区分「普涨型风口」与「结构性风口」，不是只看涨幅 |
| 板块 → 个股 | `wind_research` 写板块强度与龙头 claim；`insight_research` 据此判定个股异动是「板块共振 / 逆板块 / 个体事件」。**这就是洞见卡片主因的上游** |
| 个股 → 板块 | `insight_research` 的龙头 / 异动 claim 经 KB-CLAIM 反哺板块强度；**反哺发生在下一轮 run**（读上一轮 claim），同一 run 内不构成环 |
| 事件 → 风口 | `event_research` 写事件热度 claim；`wind_research` 读该 claim，板块强度不再只看涨幅 |
| 事件 → 实体 | `event_perception` 先产事件主记录，`entity_perception` 再做实体链接（SE-EVENT→SE-ENTITY），避免各模块各猜一套归属 |
| 风口 → 洞见 | `insight_research` 读板块强度与龙头 claim，判断个股异动是「板块共振」还是「个体事件」 |
| 趋势 → 洞见 | `insight_research` 读 `trend_research` 的支撑 / 压力 claim，判断异动是否有趋势背景 |
| 资金 → 板块 | `capital_research` 的资金流 / 主力行为 claim 进入 `wind_research`，板块强度不只看涨幅 |
| 资金 → 洞见 | `insight_research` 读资金筹码 claim，判断异动是主力行为、拥挤交易还是散户跟风 |
| 宏观 → 板块 | `macro_research` 的环境松紧 claim 进入 `wind_research`，高 β 板块与防御板块的强度随环境调整 |
| 宏观 → 洞见 | `insight_research` 读宏观政策 claim，排除「环境性下跌被误判为个股利空」 |
| 宏观 → 节奏 | `rhythm_research` 读宏观政策 claim，仓位建议不再只看恐贪读数 |
| 趋势 → 研判 | `trend_research` 的支撑/压力位直接成为研判的 `invalidators` |
| 基本面 → 洞见 | `fundamental_research` 的业绩/机构 claim 解释异动是否基本面驱动 |
| 研判 → 节奏 | `rhythm_research` 读 KB-JUDGMENT 中**最近一条同标的研判**（上一交易日 / 上一次 run）；本轮 judgment 尚未生成，不读，避免同 run 成环 |
| 验证 → 研究 | `verifier` 回填命中结果，`method_evolver` 生成方法版本，作为研究子图先验 |

关键点：这些不是「前端把两张卡放一起」，而是图里的**数据依赖与反馈边**。

洞见卡片是这条链的试金石：前端只调 `/api/cn/favorites/movements`，卡片上的 `primary_cause` 目前主要由个股自身证据归因（行情、该股新闻 / 公告，以及 2026-10-16 新增的板块消息证据）；目标是把市场基调与板块强弱作为上游 claim 注入同一条归因，**接口形状不变、前端不改**，但卡片主因能说清「是大盘带的、板块带的，还是个股自己的事」。

### 2.3 主图与子图：分层，而不是硬塞进一张图

| | 主图 `run_orchestrator` | 研究子图（8 个） |
|---|---|---|
| 职责 | 接收触发、选档位、扇出、研判、落账、分发给出口 | 完成一个能力域内的取数、计算、claim 生成 |
| state | 全图共享的 8 条通道（evidence / claims / conflicts / judgment / verification / method_prior / render_targets / trace） | 只声明自己需要的输入投影与输出 claim |
| 编译 | 一张可编译的 `StateGraph` | 每个子图可独立编译、单测、回放 |
| 互相影响 | 通过通道与 reducer | 只读其他子图的 claims / 工具，**禁止直接改对方 state** |
| 设计图 | 目标视图即主图 | 点击带 ⊞ 的研究节点展开 |

允许的物理形态：

1. **一个进程、一张主图 + 子图函数**（推荐起步）：子图作为 `StateGraph` 的 node 注册，代码分文件，状态同源。
2. **一个进程、多张可编译图**：每个研究子图有独立入口，主图通过 `invoke` 调用，共享同一套契约与账本。
3. **多个服务**：子图独立部署，通过工具/队列通信，账本仍是同一个。

三种形态的**契约不变**：证据结构、claim 结构、judgment 结构、通道 reducer 和 provenance 信封完全一致。差别只在进程边界，不影响「互相影响」的设计。

**两类链路模板（2026-11-26 新增）**：

| 模板 | 起点 | 典型功能 | 特征 |
|---|---|---|---|
| 数据先行 | SE 取数 → AG 归因 | morning、trend、review、sector | 先有数据再找原因；缓存可长；验证「结论对不对」 |
| 结论先行 | IN-EVENT 异动假设 → AG 取证 | alert、insight、hot_burst | 先有假设再补证据；缓存要短；必须标 `hypothesis=true`；先验「假设是否成立」 |

V3 目前只建模了数据先行，alert/insight 这类会被硬塞进不合适的模板，需要补第二套。

**交易日历统一**：交易日判断只允许通过统一服务，节点与 job 不得各自判断。现有 `event_calendar.py` 只服务事件窗口，需要扩展为通用日历；当前 25 个文件、162 处调用要逐步收敛。

**执行拓扑（2026-11-25 收敛）**：主图研究段只保留 AG-LEAD 主控；AG-WIND / AG-EVENT / AG-FUND / AG-CAPITAL / AG-MACRO 以 `StructuredTool` 形式挂在 AG-LEAD 上，内部仍是可独立编译、单测、回放的子图；CA-TREND / CA-RHYTHM 是确定性函数。主图与子图的契约不变，变的是挂载方式——从「8 个并列节点」变成「1 个主控 + 5 个子 agent 工具 + 2 个计算函数」。对应设计图「③ 执行：规则层 + 研究层」。

### 2.4 主图边契约（2026-11-25 校正）

设计图目标视图的连线曾出现 9 处不自洽（缺边、方向反、同 run 成环）。实现以本节为准，不以旧图连线为准。

| # | 原问题 | 校正后的契约 | 理由 |
|---|---|---|---|
| 1 | 工具带只连 6 个节点 | OR-SCOPE → SE-MARKET / SE-EVENT / SE-ENTITY / SE-USER、AG-LEAD / AG-WIND / AG-EVENT / AG-FUND / AG-CAPITAL / AG-MACRO / CA-TREND / CA-RHYTHM、MT-VERIFY、EX-BRIEF、EX-PUSH、EX-CHAT | 节点说明里声明要用工具的都必须有边；EX-CHAT 的实时数据只作上下文，不得直接下结论 |
| 2 | `CA-TREND→AG-WIND`「板块共振」方向反了 | `AG-WIND→CA-TREND`「板块强度」，执行顺序 wind 先于 trend | 趋势需要板块上下文；个股对板块的反向修正放到下一轮 |
| 3 | 洞见读趋势但无边 | `CA-TREND→AG-LEAD` | AG-LEAD 归因必须能回答「趋势是否支持」 |
| 4 | CA-RHYTHM 读「当日 judgment」成环 | CA-RHYTHM 读 KB-JUDGMENT **最近一条同标的研判**（上一交易日 / 上一次 run），主图补 `KB-JUDGMENT→CA-RHYTHM` | DB-WRITE 在同一 run 后段才生成 judgment，读本轮值会形成 `CA-RHYTHM→DB-WRITE→CA-RHYTHM` 环 |
| 5 | KB-METHOD 只连 CA-RHYTHM | `KB-METHOD→AG-LEAD / AG-WIND / AG-EVENT / AG-FUND / CA-TREND / CA-RHYTHM`；`KB-METHOD→MT-CALIB`（校准方法版本）、`KB-METHOD→MT-EVOLVE`（失败模式库） | KB-METHOD 是研究先验库，不只服务节奏 |
| 6 | KB-GRAPH 只连 AG-FUND | `KB-GRAPH→SE-EVENT`（事件实体）、`KB-GRAPH→SE-ENTITY`（实体归属）、`KB-GRAPH→AG-EVENT`（事件实体）、`KB-GRAPH→AG-FUND`（RAG） | 实体归属只维护一份，事件去重 / 链接 / 研究共用 |
| 7 | 对话回写、研判连贯无边 | `EX-CHAT→KB-JUDGMENT`「新结论回写」；`KB-JUDGMENT→DB-WRITE`「上一条研判」 | 没有回写就不是账本；没有上一条就无法产 `prev_judgment_id` / `relation` |
| 8 | 事件主记录到实体链接无边 | `SE-EVENT→SE-ENTITY`「事件主记录」 | 实体链接必须在事件去重之后 |
| 9 | 触发边没有 payload | IN-TIME 带 `window`、IN-EVENT 带 `event_id`、IN-USER 带 `subject`、IN-VERIFY 带 `judgment_id` | OR-RUN 需要 payload 才能选运行档位 |

补充规则：

- 同一 run 内只允许「前置依赖」方向；任何反向修正（个股→板块、judgment→节奏）都读上一轮账本，不画成同 run 环。
- EX-PUSH 的「只推变化」由 DB-WRITE 写入的 `prev_judgment_id` / `relation` 判定，不让推送层自己比较版本。

### 2.5 多 agent 协作模式：分场景使用

| 模式 | 用在哪 | 不用在哪 | 边界 |
|---|---|---|---|
| Supervisor / 层级 | 主链：AG-LEAD 派 probe；大盘 → 板块 → 个股按层级执行 | — | 主链必须有唯一责任人 |
| Blackboard | KB-EVIDENCE / KB-CLAIM：typed、versioned、只追加 | — | agent 不直接互调，只读写黑板 |
| Debate | DB-BULL / DB-BEAR / MT-CHECK | — | 必须有等强度反证 |
| Contract Net（有限招标） | 可选 probe：OR-PROFILE 发布缺口，probe 按能力标签投标，AG-LEAD 定标 | 固定必查 probe 不招标 | 投标与定标全程记 trace |
| Peer / Swarm | 仅 MT-REFLECT 离线反思、假设生成 | 主链判断、盘中结论 | 离线产物只能进假设池，不能直接写 judgment |

**为什么主链不用 Peer**：不是审计不了（trace 能记），而是责任不可归因、收敛不可控、同一标的两次 run 可能结论不同。**招标之所以能用**，是因为中标结果与理由可审计。

### 2.6 信号总线：三种连接里的「突触」

| 连接 | 机制 | 用途 |
|---|---|---|
| 数据连接 | claim 引用（KB-CLAIM） | 下游读到上游结论 |
| 事件连接 | Signal Bus（本节） | 跨 run / 跨功能的实时通知 |
| 反馈连接 | MT-VERIFY → MT-EVOLVE | 错题回灌 |

事件表：

| 事件 | 发布者 | 订阅者 | 触发动作 |
|---|---|---|---|
| `phenomenon.detected` | SE-EVENT | AG-LEAD | 新现象触发研究 |
| `phenomenon.linked` | SE-ENTITY | AG-LEAD | 父子现象建立（大盘 → 板块 → 个股） |
| `claim.published` | AG-WIND / AG-EVENT / … | AG-LEAD / DB-* | 论点可用，下游不必重查 |
| `claim.invalidated` | MT-VERIFY | AG-LEAD / EX-PUSH | 失效通知，立即降档 |
| `judgment.committed` | DB-WRITE | EX-* / MT-* | 渲染与验证的起点 |
| `verification.failed` | MT-VERIFY | MT-EVOLVE | 错题自动入池 |
| `step.failed` | 任一节点 | OR-RUN / MT-VERIFY | 失败分类（transient / permanent / degraded）与补偿 |

三条硬规则：

1. **总线只做通知，不决定主链顺序**——主链仍是 `StateGraph` 确定性边，总线不形成环；
2. 每个事件带 `trace_id / run_id / subject / evidence_ids`，落 PG `brain_signals` 表，可回放；
3. 跨 run 走总线，同 run 走黑板投影，避免盘中竞态。

**为什么不上 A2A**：A2A v1.0 是跨服务 agent 互操作标准（Agent Card + 任务委派 + 不暴露内部记忆），适合多团队、多框架的服务间协作。我们目前是 agent-py 一个进程 + app-api 一个数据服务，app-api 不是 agent，不需要 A2A 的传输层。但借鉴它三个设计：probe 注册能力卡、招标用固定消息格式、probe 只返回 claim。将来若 SE 层拆成独立服务，能力卡可直接升级为 Agent Card。

**与 EventBus 的分工**：EventBus 保留，负责晚间链路内部驱动（review → snapshot → iterate）；Signal Bus 只做跨 run / 跨功能通知；两者事件语义不重叠。

## 3. 研判契约（Analysis Contract）

所有模块与图之间、图与出口之间，只认这一份结构。

### 3.1 字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `judgment_id` | string | 是 | 唯一 ID，格式 `jdg_{YYYYMMDD}_{subjtype}_{code_ns}-{code}_{horizon}_{jtype}_v{n}`（如 `jdg_20261126_stk_ex-600519-SH_1d_forecast_v1`）；由 app-api 在分配 `version` 的同一事务生成并回传，Python 只提交 owner 键与草稿，不得自行拼最终 ID |
| `subject` | object | 是 | `{type: stock/sector/market, code_ns: ex/ths/em, code, name}`；`type` 与 `code_ns` 进 owner 键 |
| `horizon` | enum | 是 | `intraday / 1d / 3d / 1w` |
| `as_of` | datetime | 是 | 信息截面时间（决定"当时可得知的信息"） |
| `direction` | enum | 是 | `bullish / bearish / neutral / unclear` |
| `confidence` | number | 是 | 0~1，须经校准，不是模型自评原值 |
| `thesis` | string | 是 | 一句话核心结论（≤60 字） |
| `evidence` | array | 是 | 每条含 `evidence_id / claim / source / source_id / source_type / snapshot_id / event_time / published_at / as_of / weight`；身份为 `(source_type, source_id, snapshot_id)`，`subject` 可空、只作属性 |
| `counter_evidence` | array | 是 | 反方证据，允许为空数组但必须显式存在 |
| `conflicts` | array | 否 | 模块间分歧及处理方式 |
| `invalidators` | array | 是 | 失效条件（如"跌破 20 日线"） |
| `due_at` | datetime | 是 | 研判到期时间（horizon 结束，按交易日历计算）；到期才可评分 |
| `verify_at` | date | 是 | 验证执行日 = `due_at + 3 个交易日`（留数据结算）；**与 `due_at` 不同** |
| `verify_status` | enum | 是 | 投影字段：`pending / verified / missed / void`；事实源是 `verification` 记录 |
| `verified_result` | object | 否 | 投影字段：验证结果（见 §5.9），含 `hit / actual / error_tags`；事实源是 `verification` 记录 |
| `modules` | array | 是 | 参与的研究子图名与版本 |
| `render` | object | 是 | 允许渲染的出口：home/stock_page/event_page/broadcast/push/chat/pick_page |

```json
  "claim": "近 5 日北向净流入 12.3 亿",
  "source": "tushare",
  "source_id": "ts_flow_600519_20261120",

  "event_time": "2026-11-20",
  "published_at": "2026-11-20T15:31:00+08:00",
  "as_of": "2026-11-20T15:35:00+08:00",
  "fetched_at": "2026-11-20T15:36:12+08:00",

```

```json
{

  "subject": {"type": "stock", "code": "600519"},
  "kind": "trend|wind|event|fundamental|insight|rhythm",

  "confidence": 0.64,
  "invalidated_by": [],
  "produced_by": "trend_research@v1.0"

```

**证据身份与三时间**

- 证据唯一键为 `(source_type, source_id, snapshot_id)`，`subject` 不进唯一键、不进 `evidence_id`，可为空，只作属性与 claim 关联。
- `snapshot_id = snap_{YYYYMMDD}_{HHMM}`（Asia/Shanghai），由 OR-RUN 在 run 启动时生成、同 run 所有 probe 共用；`evidence_id = ev_{source_type}_{sha1(source_id|snapshot_id)[:12]}`，同一来源条目在同一 snapshot 下 ID 稳定，回放可复现。
- `event_time`（事发时间）/ `published_at`（发布时间）/ `as_of`（可知截面）三字段必须同时声明，禁止用 `as_of` 冒充 `published_at`。
- **多源校验改用 `claim.subject`**：`evidence.subject` 可空后，`judgment_writer` 校验"主体一致"时比对 `claim.subject` 与 `judgment.subject`；evidence 侧只校验 `source` / 时间（三字段）/ `quality`。

### 3.3 研判账本（Judgment Ledger）

每次研判写一条记录，验证后回填。这是准确率提升的**唯一事实源**。

| 字段 | 说明 |
|---|---|
| `judgment_id` / `subject` / `horizon` / `as_of` | 唯一 ID、owner 键与截面（owner 键见下方硬约束） |
| `direction` / `confidence` / `thesis` | 结论 |
| `evidence` / `counter_evidence` / `conflicts` | 依据 |
| `invalidators` / `due_at` / `verify_at` | 可验证性：到期时间与验证执行日 |
| `verify_status` / `verified_result` | 投影：验证状态与结果；事实源是 append-only 的 `verification` 记录 |
| `model_version` / `prompt_version` / `module_versions` | 复现与归因 |
| `cost_ms` / `tokens` | 成本与时延 |

**硬约束**

- 未写账本的研判不得对外渲染。
- **验证 append-only**：`MT-VERIFY` 只追加 `VerificationRecord`，不得更新或删除 judgment 行；`verify_status / verified_result` 是投影，可由记录重建。
- `due_at` 按交易日历计算；`verify_at = due_at + 3 个交易日`，不得提前验证。
- 高置信（≥0.7）必须至少 2 个独立来源一致，否则自动降档。
- 风险事件非对称权重：黑天鹅 / 流动性骤变 / 政策突变 / 单日跌停潮出现时，bear 证据权重 ×1.5，`confidence` 上限 0.5；该事件未被解释时禁止输出高置信。
- 等强度反证：看多结论必须由 DB-BEAR 生成与多头论证同等级的看空论证（预演失败法），只写一句敷衍反证视为未通过 DB-JUDGE。
- `verified_result` 到期未回填的，治理层告警。
- 同一 `judgment_id` 在所有出口的 `direction / confidence / thesis` 必须完全一致。
- **唯一 owner（版本链）**：owner 键是 `(type, code_ns, code, horizon, judgment_type) WHERE status='active'`（部分唯一索引；缺 `type` 时 `market` 与 `stock` 同码会互相顶掉），另有全表唯一索引 `judgment_id` 只防 ID 重复、不承担 owner 语义。`judgment_id` 由 app-api 在分配 `version` 的同一事务内生成并回传（锁 owner 键 → `version+1` → 旧版置 `superseded` → 插入新版）。`judgment_type` 分 `forecast`（预判）/ `attribution`（归因）/ `assessment`（评估）三类。同一键同一时刻只允许一条 `status=active`，历史版本全部保留。每条 judgment 带 `valid_from / valid_until / status / supersedes`；下游触发时先查覆盖当前时刻的 active，有则引用，没有才走 OR-RUN 新开。**版本链只在同一 type 内成立**：盘中 alert 的快速归因可被收盘 review 的完整归因 `supersedes`；morning 的 forecast 与 review 的 attribution 是**对照关系**，由 MT-VERIFY 负责，互不覆盖。详见 §9.4.3。

### 3.4 现象图与归因边（权重动态计算）

溯源不是一条链，是一张图。

```text
现象 P1：上证 -1.8%（根现象）
  ├─归因边──▶ 外围市场     evidence_ids=[...]
  ├─归因边──▶ 权重板块     evidence_ids=[...]
  └─归因边──▶ 情绪面       evidence_ids=[...]

现象 P2：半导体 -4.2%（parent=P1）
  ├─归因边──▶ 大盘拖累（指向 P1）
  ├─归因边──▶ 板块事件
  └─归因边──▶ 资金流出

现象 P3：某半导体个股 -7%（parent=P2）
  ├─归因边──▶ 板块拖累（指向 P2）
  ├─归因边──▶ 个股公告
  └─归因边──▶ 主力出货
```

结构：

```json
{
  "phenomenon_id": "ph_20261126_market_01",
  "subject": {"type": "market", "code": "000001.SH"},
  "change_pct": -1.8,
  "window": "1d",
  "parent_id": null
}
```

```json
{
  "edge_id": "ae_20261126_001",
  "from_phenomenon": "ph_20261126_market_01",
  "to_cause": {"kind": "external_market", "ref": "nasdaq_drop"},
  "evidence_ids": ["ev_20261126_011"],
  "weight": 0.41,
  "weight_algo": "evidence_weighted@v1",
  "computed_at": "2026-11-26T15:40:00+08:00"
}
```

**权重不写死。** 每次 run 由证据重算：

```text
weight = normalize(quality × recency × directness × consistency)
```

| 因子 | 含义 | 来源 |
|---|---|---|
| quality | 证据质量：直接观测 > 二手转述 | `evidence.quality` |
| recency | 时效衰减 | `published_at` |
| directness | 直接因果 vs 间接传导 | 因果类型 |
| consistency | 多来源方向是否一致 | 来源去重后的方向一致性 |

三阶段演进：

1. **P1 证据加权**：上式，可解释、可单测；先落地。
2. **P2 贝叶斯更新**：先验用同类归因的历史命中率，后验随本轮证据更新。
3. **P3 反事实归因**：关键边做干预式检验（拿掉这条证据，结论是否翻转）。

硬规则：

- 每条边必须带 `evidence_ids`，无证据的边权重为 0；
- 每次 run 的 `weight / weight_algo / computed_at` 全部落库，可复现；
- 不允许手工指定固定权重；人工只能调整因子系数，且必须版本化。

#### 3.4.1 市场溯源的 V3 映射：4 候选 × 同一条 6 阶段链（v1.3 新增）

**先纠正一个常见误解**：市场溯源不是"六条独立链"，而是 **4 个候选解释，各自走同一条 6 阶段因果链**。六阶段是表达与校验契约，不是六个 agent。

| 段 | 回答什么 | 典型证据 |
|---|---|---|
| `structural_root` | 慢变量/结构性背景 | 估值分位、盈利周期、政策周期 |
| `trigger` | 当日触发 | 事件、外围市场、数据发布 |
| `transmission` | 怎么传导 | 利率/汇率/风险偏好/产业链机制 |
| `exposure` | 谁在暴露 | 行业权重、外资/两融/ETF 持仓 |
| `repricing` | 价格怎么重估 | 板块与个股涨跌结构、成交 |
| `observable_result` | 可观察结果 | 指数、成交额、涨跌家数 |

V3 落地：

- 4 类候选沿用现有枚举：`global_risk_liquidity` / `domestic_macro_policy` / `industry_technology_supply` / `market_positioning_liquidity`；每个候选独立走完六段，最后由 DB-JUDGE 选主因/次因/被否，不合并成一条链。
- 研究员**按阶段供证**，裁决层**按阶段打分**；`CausalNode` 必须带 `stage` 与 `evidence_ids`，`validate_chain_stages` 仍强制按序恰好 6 段。
- 缺某一段时产出 `Gap(kind=missing_data, target_hint=<stage>)`，第二轮**定向补那一段**，而不是"再查一遍"；这是把原来的单轮生成改成目标驱动的主要收益。
- 硬规则：`stage` 必填；`evidence_ids` 为空的节点不得标 `supported`；候选之间可以共享 evidence，但不能把某个候选的结论当另一候选的证据。
- 待完善：`structural_root` 慢变量数据、`transmission` 机制库、`exposure` 持仓数据、`repricing` 与 `observable_result` 的边界、置信校准、前端加性字段与 10 日回放评测。

### 3.5 术语与 ID 规范

| 统一术语 | 禁用别名 | ID 规则 |
|---|---|---|
| 板块 | 风口、概念、tag_code（仅保留为外部字段名） | `sec_{code}` |
| 事件 | 新闻、资讯、电报 | `evt_{date}_{hash8}` |
| 论点 | 观点、结论片段 | `clm_{date}_{subject}_{seq}` |
| 研判 | 判断、结论 | `jdg_{YYYYMMDD}_{subjtype}_{code_ns}-{code}_{horizon}_{jtype}_v{n}` |

规则：

- **ID 只用于引用、展示与日志，禁止代码反向解析取字段**：查询 owner、horizon、judgment_type 一律走数据库列与 owner 键；`subjtype` 取 `mkt / sec / stk`（由 `type` 映射：`market→mkt` / `sector→sec` / `stock→stk`，不单独存储），`code_ns` 取 `ex / ths / em`，ID 的最终拼装权在 app-api。
- KB 内只允许统一术语；外部接口字段名可保留旧名，但必须映射；
- 同一实体只允许一个 ID，别名进 `entity_alias` 表；
- 新增术语必须先登记，禁止在代码里造新词。

## 4. LangGraph 设计

### 4.1 状态通道（channels + reducers）

| channel | 写入者 | 读取者 | reducer 规则 |
|---|---|---|---|
| `evidence` | 感知 / 研究 / 工具 | 所有研究节点 | 按 `evidence_id` append，去重，不覆盖 |
| `claims` | 研究子图 | 研判 / 洞见 / 节奏 / 风控 | 按 `claim_id` append；`invalidated_by` 只追加 |
| `conflicts` | 研究 / `conflict_resolver` | 研判 / 表达 | append，保留分歧，不强行合并 |
| `round_ledger` | `assess` | `lead` / `router` / 治理 | 按 `(run_id, round)` append，不覆盖；携带 `satisfied / in_loop / has_progress / next_target / next_instruction / stall_count / new_evidence_count` |
| `judgment` | `judgment_writer` | 表达 / 节奏 / 对话 / `judgment_writer`（读上一条） | 仅保留最新一次 `committed`；跨 run 读最近一条同标的研判 |
| `verification` | `verifier` | 校准 / 治理 | append，按 `judgment_id` 关联 |
| `method_prior` | `method_evolver` | 研究子图 | 按版本号保留最新 |
| `render_targets` | `judgment_writer` | 表达 | 集合并集 |
| `trace / cost` | 所有节点 | 治理 | append，按节点与版本聚合 |

**读取方式**：节点不读全量 state，只读 `projection(subject, sector, time_window)` 或上次 run 的 `delta`。这是控制 token 成本的关键——比现在每个 Agent 各自把一堆工具结果塞进上下文更低。

**写入规则（2026-11-26 新增，来自 16 项盘点）**：

1. **幂等键**：KB 写入统一用 `(source_type, source_id, snapshot_id)` 做幂等键，重复写入只更新 `fetched_at`，不新增记录；`snapshot_id = snap_{YYYYMMDD}_{HHMM}`（Asia/Shanghai）由 OR-RUN 在 run 启动时生成、同 run 所有 probe 共用，`evidence_id = ev_{source_type}_{sha1(source_id|snapshot_id)[:12]}`。`subject` 不进唯一键、不进 `evidence_id`，降为属性 / 由 claim 关联（可为空）。event 与 insight 的 revision 去重上收到 KB 层统一实现。
2. **降级隔离**：`quality=failed` 或降级产物只进 trace，不进 KB、不进缓存、不参与验证。避免"个股分析暂时不可用"这类文案被当成一次真实结论。
3. **时间三字段**：每条证据与 claim 必须区分 `event_time`（事发时间）、`published_at`（发布时间）、`as_of`（我们可知的截面）。回测与验证只用 `as_of` 之前可见的信息，防止未来函数。
4. **错误分类与降级权**：probe 只返回 `ok` 或抛可分类错误（`timeout` / `empty` / `schema_mismatch` / `not_implemented`），**不得自己声明 `partial` / `degraded` / `insufficient`**；主控把缺失项写入 `missing_probes`，按 `required` 决定 run status（口径见 §5.4）。错误分 `transient`（超时、限流）重试与 `permanent`（schema 不匹配、参数错）记 trace 不重试；禁止所有错误都走同一条"返回文案"路径。
5. **数据截面统一**：一次 run 只允许一个行情快照（由 SE-MARKET 产出），其他节点只读该快照的 `as_of`，不得各自再取价。同一只票在同一 run 内所有出口口径一致。
6. **TTL 按数据频率分档**：行情 60s、新闻 15min、研判 2h、方法 1d。TTL 由数据类型决定，不由调用方决定。

**检索排序（三因子，2026-11-25 新增）**：KB-JUDGMENT / KB-METHOD 取历史研判与方法先验时，不按时间倒序全取，按加权分数取前 K：

```text
score = 0.5 × relevance + 0.3 × recency + 0.2 × hit_rate
```

| 因子 | 含义 | 计算 |
|---|---|---|
| relevance | 与当前标的 / 板块 / 事件类型的相似度 | 向量相似度或标签匹配 |
| recency | 时间新鲜度 | 指数衰减，`0.995 ^ 距今天数`（Generative Agents 同款） |
| hit_rate | 这条历史判断 / 方法后来的命中率 | MT-VERIFY 回填结果聚合 |

只影响检索排序，**不删除任何账本记录**。账本是审计与复盘的事实源，遗忘只能体现为排序降权。

### 4.2 编排要求

- 用 `StateGraph` 显式建模，禁止"一个 prompt 跑到底"。
- **依赖图优先于串行链**：09:00 播报链（morning / wind_leader / hot_burst / trend_score → broadcast）改为四个源并行、broadcast 等齐即发；总时延取最慢一段，而不是四段相加。任一源失败按 OR-PROFILE 的 `fallback` 处理，不阻塞其他源。
- **成本强制可见**：每个节点必须记录 `llm_calls / tokens_in / tokens_out / tool_calls / cost_ms`，按 `run_id + 档位` 汇总。没有成本数据的 run 不得进入 A/B 评估。
- 一次 run 记录 `trigger / subject / as_of / budget`，全图共享。
- 触发必须携带 payload：`IN-TIME=window`、`IN-EVENT=event_id`、`IN-USER=subject`、`IN-VERIFY=judgment_id`；OR-RUN 据此选档位，禁止只传一个空触发。
- 同一 run 内禁止反向边成环：个股→板块、judgment→节奏一律读上一轮账本（KB-CLAIM / KB-JUDGMENT），不读本轮尚未产出的值。
- 档位模板（OR-PROFILE）必须声明必查 probe 与预算；研究层不得跳过必查项，规则层不得替 AG-LEAD 决定可选 probe。
- 超时与预算分层：节点级 `TimeoutPolicy` + 节点级 `error_handler`（可返回 `Command` 路由）是主要控制手段，`asyncio.wait_for` 只保留为外层保险；节点超时是上限、run 预算是硬上限，全链 P95（第一周 ≤ 90s）是性能目标，三者不得混用。预算触顶记 `stop_reason=budget`，**不改变 run status**，也不计入 `partial` 率。
- 开启 checkpointer（Postgres）：支持重放、对比、A/B。
- 关键节点（`bear_advocate`、`conflict_resolver`、`judgment_writer`、`verifier`）不可跳过。
- 研究层只能通过**只读工具 + claims + ResearchResult**互相影响，禁止直接改对方 state 或直接写 KB-EVIDENCE/KB-CLAIM/KB-JUDGMENT。
- 八个研究能力域各自可独立编译、独立运行、独立单测；主图只依赖它们的输入/输出契约，不依赖内部节点名；执行形态按 §1.1 收敛为主控 + 子 agent。
- 子图内部同样用 `StateGraph` 建模，不允许一个 prompt 从头写到尾；纯计算必须走 LangChain Tool。

#### 4.2.1 研究循环（v1.3 新增）

研究层不是"一次派发、一次生成"，而是显式状态机；**ASSESS 是唯一岔路口**，是否继续查由确定性的充分性检查决定，不由 LLM 自由决定。

```text
PLAN → DISPATCH → COLLECT → ASSESS
                              ├─ 判据满足            → JUDGE → WRITE
                              ├─ 有 Gap 且预算允许   → REPLAN → DISPATCH（下一轮）
                              ├─ 无新增证据/排序稳定 → JUDGE（partial）
                              └─ 轮次/预算耗尽       → JUDGE（insufficient / partial）
```

- **停止条件按优先级**：① `sufficiency_rules` 全部满足；② 预算或轮次耗尽（`stop_reason=budget`，不改变 status）；③ 连续两轮无新增证据或候选排序稳定（收敛）；④ 存在无法通过允许工具补齐的 `Gap`（直接 `insufficient`）。
- **进度账本**：每轮 `ASSESS` 额外写 `round_ledger`，记录 `satisfied / in_loop / has_progress / next_target / next_instruction / stall_count / new_evidence_count`。`stall_count` 连续递增到阈值（默认 3）时触发**重置计划**（`plan_reset`，默认上限 2 次），而不是继续在同一个坏计划上加轮次；这是"两轮无增量就判收敛"之外的硬兜底。
- **轮次自适应**：默认 `max_rounds=2`，硬上限 3。只有同时满足"候选排序分歧大、缺口属于关键段、预算充足"才升到第 3 轮；固定跑满 3 轮视为失败，因为多 agent 约 15x token、日内链路还要守 P95。
- **拓扑按档位选择**：breadth-first 档位（大盘归因、风口扫描）用"主控 + 并行 probe"；narrow 档位（个股问答、单事件解读）用单 agent + 工具即可，不为了形式统一而上多 agent。
- **闸门**：`max_rounds=2`（硬上限 3）、`max_depth=2`、总请求数上限、run 预算，四者同时生效；`recursion_limit` 与硬上限对齐。
- **回查只走请求队列**：probe 只能在 `ResearchResponse.suggested_requests` 里提请求，由确定性的 `OR-ROUTER` 按 `target + question + expected_evidence` 路由。**禁止 probe 直接函数调用另一个 probe**，也禁止自由发明工具。
- **路由目标三类**：上游节点重跑（如快照过期 → 重跑感知并重新冻结 `snapshot_id`）、同级 probe 补证（如缺外资暴露 → 请求资金 probe）、工具层换源或换日期（`GX`）。
- **去重与防环**：去重键 `(target, question, as_of, stage)`，重复请求复用已有响应；请求树出现 A→B→A 立即停止该分支并标 `circular_request`。
- **同级结论不是证据**：peer 返回必须带 `evidence_ids` 才能进 KB-EVIDENCE；没有证据链的结论只算 `claim`，不能单独支撑 `confirmed`。
- **研究树可追溯**：trace 记录 `request_id / parent_request_id / round / target / purpose`，前端能回答"第二轮为什么查、谁提的、补上了没有"。
- **第一周范围**：只做"受限两轮"——第二轮只能从档位已声明的 `optional_probes` 里选；同级 peer request 与上游重跑放 P1。
- **只回引用**：probe 返回 `evidence_ids + claim`，正文落 KB；`ResearchResponse` 内嵌原始正文设长度阈值，CI 校验超限即失败，避免把长文本在 agent 之间搬运（对应 Anthropic "output to filesystem, avoid game of telephone"）。
- **异步预留（不实现）**：probe 接口必须无共享可变状态，预算与 `deadline` 随 `ResearchRequest` 传递，而不是存在全局；第一周同步执行，P2 若要改异步只换调度，不改契约。

### 4.3 为什么不是「所有节点一个大上下文」

- 感知节点写证据，研究节点只取与自己相关的切片；
- 研究节点写 claims，研判节点读 claims 而不是原始工具输出；
- 表达节点读 judgment，不重新推理；
- 校准节点只读验证结果与方法版本。

这样「互相影响」发生在**结构和契约层**，不是把所有文本反复塞进模型。

## 5. LangChain 工具清单

工具统一用 `StructuredTool` + Pydantic schema 定义，返回体固定携带：

```json
{"data": {}, "provenance": {"source": "", "published_at": "", "fetched_at": "", "quality": "ok/partial/failed"}, "error": null}
```

| 工具组 | 工具 | 职责 |
|---|---|---|
| 行情 | `quote_snapshot` / `kline_query` / `money_flow` / `global_markets` | 实时/历史行情、资金、全球市场 |
| 板块 | `sector_rotation` / `wind_leaders` / `trend_scores` | 轮动、风口、趋势评分 |
| 事件 | `news_search` / `announcement_search` / `research_rag` / `event_entities` / `market_calendar` | 新闻、公告、研报、事件实体、日历 |
| 基本面 | `financial_report` / `profit_forecast` / `institution_research` | 财报、业绩预测、机构调研 |
| 情绪 | `fear_greed` / `stock_monitor` | 恐贪、异动 |
| 记忆 | `graph_query` / `stock_trace` / `prediction_records` / `user_profile` | 图谱、溯源、预测、画像 |
| 出口 | `push_send` / `audio_render` / `review_snapshot` / `iterate_apply` | 推送、音频、复盘、迭代 |

**工具规范**

1. 单一职责，命名动词开头，描述里写清"适用/不适用"边界。
2. 所有工具复用 app-api 现有数据接口，不新造第二套数据源。
3. 失败必须显式：空结果、字段缺失不得静默归零。
4. 每个工具有金标样本与失败率监控，纳入数据准确率任务。
5. 工具调用记录进 trace，供失败模式归因。
6. 工具返回的 `provenance` 必须能追溯到 `source / published_at / fetched_at`，否则不得进入高置信证据。

### 5.1 三层工具箱（公共箱 + 角色箱 + 借用条）

工具不再按“部门”切死，而是按权限分三层：

| 层 | 内容 | 授权规则 |
|---|---|---|
| 公共箱 | 行情、K 线、新闻、公告、日历、恐贪、通用检索 | 所有研究节点默认可用，只读 |
| 角色箱 | 风口（轮动/龙头）、事件（全文/产业链）、基本面（财报/预测/调研）、资金（龙虎榜/两融/北向/大宗/大单）、宏观（利率/CPI/PPI/PMI/汇率/政策） | 默认只给本职节点 |
| 借用条 | 节点在 harness 中显式声明要借的跨箱工具，例如 AG-LEAD 借 AG-WIND 的板块强度、AG-EVENT 的事件全文、AG-FUND 的盈利预测、AG-CAPITAL 的资金筹码、AG-MACRO 的宏观环境 | 声明后才可用；每次借用写 trace（谁借、为什么、花了几步） |
| 敏感箱 | 写研判账本、用户持仓/画像、推送、音频 | 只给 DB-WRITE / EX-PUSH / EX-BRIEF / EX-CHAT 等指定节点，写操作需确认 |

规则：

- 默认最小权限；未声明的工具调用直接拒绝，不静默降级。
- **一次定义，多处授权（2026-11-26 新增）**：工具只有一份实现，权限按角色声明。禁止像现状那样在同一文件里把 `get_quote` 重复注册 6 次、`get_capital_flow` 重复注册 6 次；`OR-SCOPE` 维护「工具 → 角色」授权表，改一处即全局生效。

#### RAG 用在哪（不要到处用）

现状只有一处真 RAG：`tools/industry_vector_search.py`，用 pgvector + `text-embedding-3-small` 做「关键词 → 行业」语义匹配，供 `event_graph_resolver` 的 fallback 使用。其余所谓「检索」都是关键词查询或图谱查询，不是 RAG。

V3 只在四处用 RAG：

| 位置 | 检索什么 | 现状 | 要求 |
|---|---|---|---|
| SE-ENTITY | 关键词 → 行业 | **已有** pgvector | 保留，作为实体链接 fallback |
| AG-EVENT | 历史相似事件 | 无 | 新增事件向量库 |
| AG-FUND | 研报原文 | 无（只有全文读取） | 新增研报向量库 |
| EX-CHAT / MT-REFLECT | 历史相似研判 | 无 | 复用 KB-JUDGMENT 案例库 |

硬规则：RAG 结果必须带原文引用与 `published_at`，否则只能作线索，不能进高置信证据。图谱查询（`graph_tools`）是结构化关系查询，不算 RAG，两者不要混用。
- 借用条不是永久授权，按 run 生效，进入 trace 供 KB-GOV 归因。
- 同一 run 内 GET 走 memo（阶段 2 已实现），同一证据不重复取。
- 工具返回 `quality=failed` 时，不得进入高置信 evidence。

**AG-CAPITAL/AG-MACRO 的工具组**：资金组接 app-api 现有的资金流/龙虎榜/两融/北向/大宗能力，缺的接口列入待接；宏观组接 EDB / 宏观日历 / 政策库，缺的同样显式标注，不用假数据补齐。

### 5.2 Agent Harness 契约（主控 + 子 agent）

每个节点在方法库里登记一份 harness，主图只认这份配置。研究层分两类 harness。

**probe 统一三段式（2026-11-26 新增，来自 16 项盘点）**：

1. **LLM 提议**：只输出候选结论与证据引用，不写 KB；
2. **规则校验**：schema、证据存在性、图谱事实、数值范围；
3. **兜底**：校验失败退回规则结果（如 insight 的 `rule_fallback_select`）。

禁止 probe 直接产出最终 judgment；judgment 只能由 DB-WRITE 写。event 的"chain 只能来自图谱证据"是这个契约的既有实现，应推广到全部 probe。

#### 5.2.1 主控 AG-LEAD（唯一 lead agent）

```json
{
  "agent_kind": "react",
  "role": "lead",
  "tool_scope": {
    "compute": ["trend_snapshot", "rhythm_snapshot"],
    "subagents": ["wind_probe", "event_probe", "fundamental_probe", "capital_probe", "macro_probe"]
  },
  "required_by_profile": ["capital_probe", "wind_probe"],
  "optional_probes": ["event_probe", "fundamental_probe", "macro_probe"],
  "max_probe_calls": 4,
  "max_steps": 6,
  "timeout_s": 90,
  "stop_when": ["hypotheses_settled", "no_new_evidence", "budget_exhausted"],
  "require_citations": true,
  "fallback": "partial | insufficient"
}
```

必查项由 OR-PROFILE 档位模板注入，AG-LEAD 不能跳过；可选 probe 由 AG-LEAD 按已有证据现场判断。`max_probe_calls` 是硬上限，超出强制停止并返回已有证据。

#### 5.2.2 子 agent probe

```json
{
  "agent_kind": "react",
  "role": "probe",
  "tool_scope": {"base": true, "role": ["wind"], "borrow": ["event.fulltext"]},
  "max_steps": 3,
  "timeout_s": 25,
  "output_schema": "SectorClaim",
  "return_only": true,
  "fallback": "raise classified error（timeout / empty / schema_mismatch / not_implemented），不自行降级"
}
```

`return_only=true`：子 agent 只返回 claim 与 evidence_ids，不写账本、不写报告、不直接对外渲染。原始数据不进主控上下文。

#### 5.2.3 全节点 harness 表

| 节点 | 角色 | agent_kind | 工具箱 | 步数 | 说明 |
|---|---|---|---|---|---|
| AG-LEAD 归因 | lead | react | 2 个计算 + 5 个子 agent | 6 | 多假设、验伪、按需调用 |
| CA-TREND 趋势 | compute | deterministic | 公共 + 趋势 | — | 公式计算，LLM 只写解释 |
| CA-RHYTHM 节奏 | compute | deterministic | 公共 + 情绪 | — | 公式计算，LLM 只写解释 |
| AG-WIND 风口 | probe | react | 公共 + 风口 + 借用事件/资金/宏观 | 3 | 只返回板块 / 龙头 claim |
| AG-EVENT 事件 | probe | react | 公共 + 事件 | 4 | 只返回事件 claim 与传导链 |
| AG-FUND 基本面 | probe | react | 公共 + 基本面 | 3 | 只返回基本面 claim |
| AG-CAPITAL 资金 | probe | react | 公共 + 资金 | 3 | 只返回资金筹码 claim |
| AG-MACRO 宏观 | probe | react | 公共 + 宏观 | 3 | 只返回宏观政策 claim |
| DB-BULL / DB-BEAR 辩论 | debater | react | KB-CLAIM 证据 + 1-2 个验证工具 | 2-3 | 选证据/反证，不重新做研究 |
| DB-JUDGE 裁决 | rule | deterministic | 无 | — | 冲突分级与降权 |
| DB-WRITE 主笔 | writer | llm | 无 | 1 | 只写结论，不调工具 |
| EX-CHAT 对话 | chat | react | 公共 + 账本检索 | 4 | 账本优先，实时数据只作上下文 |
| MT-EVOLVE 方法演化 | evolve | react | 离线样本 + 方法库 | 8 | 周期性运行，不阻塞主链 |
| MT-CHECK 元认知 | critic | llm | 无（只读 ResearchResult） | 1 | 检查证据-结论匹配、内部矛盾、反事实 |
| MT-REFLECT 离线反思 | reflect | react | KB-JUDGMENT / KB-METHOD 只读 + 语义库 | 8 | 非交易时段修正归因、蒸馏条目、生成假设 |

硬规则：

1. 只有 `role=lead | probe | debater | chat | evolve` 才允许循环；每步必须产生新 evidence，否则本步不增加预算。
2. 步数用完或超时：probe 抛可分类错误，由主控记入 `missing_probes`；主控与研判节点可返回 `partial`，只带已验证部分；禁止编造。
3. 所有结论必须引用 evidence_id；无引用只能输出 `insufficient`。
4. `tool_calls` 进 trace：工具名、参数摘要、耗时、状态、借用来源。
5. `role=probe` 不得写 KB-EVIDENCE/KB-CLAIM/KB-JUDGMENT，不得输出对外文案；越权调用直接拒绝。

### 5.3 LangChain 在 Harness 里提供什么

| 能力 | LangChain / LangGraph 组件 | 用在哪 |
|---|---|---|
| 图编排 | `langgraph.graph.StateGraph` | 主图与八个研究子图 |
| 有边界 ReAct | `langchain.agents.create_agent`（probe 只需一次结构化返回时用 `StructuredTool`）或 `ToolNode` + 条件边 | AG-LEAD / AG-WIND / AG-EVENT / AG-FUND / AG-CAPITAL / AG-MACRO/DB-BULL / DB-BEAR/EX-CHAT/MT-EVOLVE |
| 工具标准化 | `langchain_core.tools.StructuredTool` + Pydantic schema | 24 个工具与 provenance 信封 |
| 结构化输出 | `with_structured_output` | 候选原因、claim、judgment |
| 可观测 | `astream_events` / callbacks | 每一步工具调用与 token 成本 |
| 重试/超时 | 节点级 `TimeoutPolicy` + `error_handler`、`RetryPolicy`、`recursion_limit` + 自定义步数计数；`asyncio.wait_for` 只作外层保险 | 预算与降级 |
| 状态恢复 | LangGraph checkpointer | run 回放、失败续跑 |

**边界**：不用 `AgentExecutor` 作为主图；不允许无步数上限的自由循环；LangChain 只提供“能循环、能调工具、能结构化输出”的能力，**“聪明”来自候选原因清单 + 证据验伪 + 复盘回灌，不来自框架本身**。

### 5.4 两层交互契约：RunBrief / ResearchResult

规则层与研究层只通过这两个结构交互，避免 agent 直接改图状态。

**precheck（2026-11-26 新增）**：每个档位在调用 LLM 前必须先做数据可用性检查，声明：

```json
{"precheck": {"source": "/internal/wind-leaders", "min_count": 1, "on_empty": "skip"}}
```

- `on_empty=skip`：直接返回「暂无」，不调 LLM（wind_leader、trend_score 已有此行为）；
- `on_empty=partial`：用已有证据产出低置信结论并标 `partial`；
- `on_empty=fallback`：改用备用数据源（如事件库异常时降级触发抓取）。

没有 `precheck` 声明的档位不得上线。

#### RunBrief（规则层 → 研究层）

```json
{
  "run_id": "run_20261125_review",
  "profile": "market_review",
  "mode": "slow",
  "subject": {"type": "market", "code": "000001.SH"},
  "as_of": "2026-11-25T15:05:00+08:00",
  "snapshot_id": "snap_20261125_1505",
  "required_probes": ["capital_probe", "wind_probe"],
  "optional_probes": ["event_probe", "fundamental_probe", "macro_probe"],
  "compute_snapshots": ["trend_snapshot", "rhythm_snapshot"],
  "fast_rules": ["涨停开板", "放量突破20日线", "跌破止损位"],
  "fast_output": "signal_only",
  "escalate_when": ["fast_confidence < 0.6", "涉及仓位建议", "证据冲突"],
  "budget": {"max_probe_calls": 4, "max_steps_per_probe": 3, "timeout_s": 90},
  "tool_scope": {"base": true, "borrow": ["event.fulltext"]},
  "output_schema": "AttributionClaimSet",
  "fallback": "insufficient"
}
```

`mode` 三档：

| mode | 谁在跑 | 输出 | 升级条件 |
|---|---|---|---|
| `fast` | 规则引擎 / 统计指标 | 只出信号，不出口结论 | 命中 `escalate_when` 任一条 |
| `slow` | AG-LEAD + probe + DB-BULL / DB-BEAR | 完整 judgment | — |
| `escalate` | 由 fast 升级而来 | 同 slow | — |

`fast` 档不训练 RL 小模型，只用规则 + 统计（FrugalGPT 级联思路的金融版）；信号只用于提示与推送，不能直接写成 judgment。

#### ResearchResult（研究层 → 规则层）

```json
{
  "run_id": "run_20261125_review",
  "status": "ok | partial | insufficient",
  "stop_reason": "complete | budget | timeout | error",
  "missing_probes": [{"id": "capital_probe", "required": true, "reason": "timeout"}],
  "claims": [
    {
      "claim_id": "cl_20261125_market_attr_01",
      "kind": "insight",
      "statement": "缩量下跌主因是权重拖累，不是事件冲击",
      "evidence_ids": ["ev_20261125_001", "ev_20261125_017"],
      "confidence": 0.62,
      "produced_by": "AG-LEAD@v1.0",
      "probe_calls": ["capital_probe@v1.0", "wind_probe@v1.0"]
    }
  ],
  "tool_calls": [
    {"tool": "capital_probe", "args_digest": "sector=all;window=1d", "ms": 1830, "status": "ok"}
  ],
  "partial_reason": null
}
```

`status` 只表达结论完整性：`ok` = 必查 probe 全部成功（可选缺失只记录）；`partial` = 存在必查缺失但有结论；`insufficient` = 必查缺失且无结论。`stop_reason` 与 status 正交：预算触顶只记 `budget`、不改变 status；`timeout` / `error` 只指 run 级。可选 probe 缺失只进 `missing_probes`，不降 status；`partial_reason` 仅作文字说明。

规则层收到后做三件事：校验引用、写 KB-CLAIM、交给 DB-BULL / DB-BEAR。研究层没有写账本权限。

#### 多轮研究契约（v1.3 新增）

以下五个结构只在 Python 内部流转，不生成 TS；跨界仍只有 `Evidence` / `Judgment` / `ToolEnvelope` / `RunStatus`。字段口径**以本节为准**；《V3 架构改进方案》§3.12 只作背景与取舍说明，不作为规范来源。

```text
ResearchPlan {
  plan_id, decision_type,          // attribution / forecast / risk / selection / monitoring
  questions[], hypotheses[],       // 2-4 个问题；3-5 个候选，至少 1 个反方
  required_probes[], optional_probes[],
  sufficiency_rules[],             // 每个问题"什么算够"
  max_rounds: 2,                   // 默认 2；满足 escalate_when 才升到硬上限 3
  hard_cap_rounds: 3,
  escalate_when[],                 // 候选分歧大 + 关键缺口 + 预算充足
  max_depth: 2, budget
}

ResearchRequest {
  request_id, parent_request_id, round,
  requester, target,               // 上游节点 / 同级 probe / GX 工具
  objective,                       // 一句话目标，必填
  question, purpose,               // purpose 必填，禁止"随便再看看"
  output_format,                   // 期望的结构：claim 列表 / 单值 / 时间序列
  source_hint,                     // 优先数据源或接口，避免 probe 乱找
  boundaries,                      // 不做什么、时间窗、标的范围
  expected_evidence[], stage?,     // 归因绑定 6 阶段之一
  deadline, budget
}

ResearchResponse {
  request_id,
  status,                          // ok / partial / insufficient / rejected
  claims[], evidence[],            // 只回引用：evidence_ids + claim；正文落 KB
  gaps[],                          // 缺什么、为什么缺
  suggested_requests[]             // 仅建议，由 OR-ROUTER 决定是否执行
}

Gap {
  kind,                            // missing_data / missing_conclusion / conflict / low_confidence / stale_data
  detail, target_hint, expected_evidence[]
}

SufficiencyReport {
  question_id,
  status,                          // satisfied / gap / conflict
  gaps[], can_judge: bool
}

RoundLedger {
  round,
  satisfied: bool,                 // 本次请求是否已满足
  in_loop: bool,                   // 是否在重复同一请求
  has_progress: bool,              // 相比上一轮是否新增有效证据
  new_evidence_count,
  stall_count,                     // 连续无进展轮数
  next_target, next_instruction,
  plan_reset_count                 // 超过阈值触发重置计划
}
```

规则：

- probe 只返回 `ResearchResponse`，不直接写账本、不直接调用其他 probe；
- `ResearchPlan` 由 AG-LEAD 的 `plan_research` 产出；方向模板固定的档位可用确定性 `OR-PLAN` 生成骨架，AG-LEAD 只补充排序；
- 不同档位给不同方向，靠 `decision_type + sufficiency_rules` 表达，不加第二个 LLM 决策者；
- `ResearchPlan` 的 `max_rounds` 不得突破 `RunBrief.budget` 的上限，冲突时以规则层预算为准。
- `ResearchRequest` 的 `objective / output_format / boundaries` 必填；`source_hint` 可为空，但为空时必须在 `purpose` 里说明为什么没有偏好源。缺这四项的请求一律拒绝，避免子 agent 重复劳动或留下缺口。
- `round_ledger` 每轮必写；`stall_count` 达到 3 触发 `plan_reset`，`plan_reset_count` 达到 2 直接收敛。重置计划必须重新读 `ResearchPlan.sufficiency_rules`，不允许换汤不换药。
- **只回引用**：`ResearchResponse` 不内嵌长原文，正文由 probe 调工具写入 KB，响应里只给 `evidence_ids`。CI 设返回体长度阈值，超限失败。
- **轮次自适应**：`max_rounds=2` 是默认执行值，`hard_cap_rounds=3` 只在 `escalate_when` 命中且预算充足时使用；跑满硬上限仍不满足，按 `insufficient` 收口，不继续加轮。

#### OR-PROFILE 档位模板（规则层的作战计划）

| 档位 | 必查 probe（每档 2 个） | 确定性快照 | 可选 probe | 预算 |
|---|---|---|---|---|
| `market_review` 大盘溯源 | `capital_probe` + `wind_probe` | trend / rhythm | event / macro / fundamental | 4 次 probe，每次 3 步 |
| `stock_on_demand` 个股按需 | `wind_probe` + `event_probe` | trend / rhythm | fundamental / capital | 4 次 probe，每次 3 步 |
| `wind_board` 风口页 | `wind_probe` + `capital_probe` | trend | event / macro | 6 次 probe（多板块并行） |
| `event_driven` 事件触发 | `event_probe` + `wind_probe` | trend | fundamental / capital | 4 次 probe |
| `verify_backfill` 验证回填 | 无 | rhythm | 无 | 不回跑研究，只读行情 |

规则：

- 必查项没跑完，规则层直接判 run 失败，AG-LEAD 不能交差；
- 可选 probe 由 AG-LEAD 按已有证据判断，规则层只校验预算；
- 档位模板可版本化（KB-METHOD），改规则不动 agent 代码。

### 5.5 为什么暂不采用 Deep Agents（选型说明）

Deep Agents 是 LangChain 的现成 harness（planning / subagents / skills / filesystem / memory 开箱）。本项目暂不作为主链底座，原因是五个具体不匹配：

| # | 冲突点 | Deep Agents 默认 | 本项目要求 |
|---|---|---|---|
| 1 | 账本写入权 | filesystem / memory 由 agent 自主读写 | 研究层不得直接写 KB-EVIDENCE/KB-CLAIM/KB-JUDGMENT，规则层确定性落账 |
| 2 | 工具权限 | 子 agent 注册即可用 | 三层工具箱 + 借用条 + 未声明调用直接拒绝 |
| 3 | 输出契约 | 自然语言 / 文件产物 | 每条 claim 必须带 `evidence_ids` 与 `produced_by` |
| 4 | 预算粒度 | subagent 配置不含步数/超时闸门 | 按 probe 计步、按 run 计次、超时熔断 |
| 5 | 版本风险 | 快速演进 | 核心研判链不宜绑定高频变动包 |

**适合的位置**：

- **AG-LEAD 主控底座（阶段 2 之后评估）**：planning + subagents + skills 正好对应「列候选原因 → 调 probe → 归因方法手册」；
- **MT-EVOLVE 方法演化（可先试）**：离线长任务 + 文件系统，适合批量分析错误样本，不阻塞主链；
- **不适合 probe**：probe 只有 2-4 步、一个明确 schema，用 LangChain `create_agent` 足够。

**迁移路径**：阶段 1 用 LangGraph + `create_agent`，先把账本、证据、权限跑通；阶段 2 若 AG-LEAD 的上下文管理与计划能力成为瓶颈，再用 `create_deep_agent` 只替换 AG-LEAD 底座，probe 与 `RunBrief` / `ResearchResult` 契约不变。

### 5.6 元认知监督 MT-CHECK（对应前扣带回）

位置：AG-LEAD 输出 `ResearchResult` 之后、规则层写 KB-CLAIM 之前。单次 LLM，无工具，步数 1。

检查三件事：

| 检查 | 问题 | 不通过处理 |
|---|---|---|
| 证据-结论匹配 | 结论说「权重拖累」，引用的证据里有没有权重板块的资金数据？ | 打回 AG-LEAD 重跑一次（只补证据，不换结论） |
| 内部矛盾 | 有没有同时引用「北向流入」和「主力流出」却没有解释？ | 要求补一句冲突说明，否则标 `conflict_unresolved` |
| 反事实 | 如果最关键那条证据是错的，结论会不会翻转？ | 会翻转 → 置信度降 0.15，并写入 `invalidators` |

输出 `meta_check: {passed, failed_checks[], confidence_delta, retry_count}`，随 `ResearchResult` 一起进 KB-CLAIM。

硬规则：MT-CHECK 只做检查，不改写结论；最多打回 1 次，第二次仍不通过就按降置信处理，不允许无限循环。

主流依据：Reflexion 的自我反思、Constitutional AI 的 critique、Anthropic dreaming 中「修正当时记错的笔记」。

### 5.7 离线反思 MT-REFLECT（对应默认模式网络 / 睡眠重放）

位置：非交易时段运行，不阻塞主链。输入 KB-JUDGMENT 研判账本 + KB-METHOD 错题本 + MT-VERIFY 验证结果。

四个动作：

| 动作 | 做什么 | 写到哪 |
|---|---|---|
| 修正笔记 | 把当时归因错的案例补正确标签（「看对是因为政策，不是因为资金」） | KB-JUDGMENT 的 `verified_result.error_type`（只追加，不改原结论） |
| 蒸馏条目 | 反复验证的模式写成一条规则（「半导体在业绩兑现期前 5 日动量通常延续」） | KB-METHOD 语义条目，带 `support_cases` 与版本号 |
| 生成假设 | 从两条不相关经验里找连接，标记 `pending` | KB-METHOD 假设池，第二天由 AG-LEAD 优先验证 |
| 更新权重 | 按命中率调整方法先验的初始置信 | KB-METHOD `method_prior.hit_rate` |

硬规则：

1. MT-REFLECT 只写 KB-METHOD，不改 KB-JUDGMENT 的历史结论；KB-JUDGMENT 是事实，反思只能追加标注。
2. 每条蒸馏条目必须带 `support_cases >= 3`，否则只能留在假设池。
3. MT-REFLECT 产出的假设第二天最多占用 AG-LEAD 一次 probe 预算，不能挤掉必查项。
4. MT-REFLECT 失败不影响主链，只记 `reflection_failed`。

主流依据：Anthropic《The components of agent memory》的 dreaming（离线重读日志、修正错误笔记、蒸馏 wiki 记忆，350K 文档实测 25 题评测 13%→48%）、Letta + UC Berkeley 的 sleep-time compute、Generative Agents 的 reflection。

### 5.8 迭代链路：MT-REFLECT 与 MT-EVOLVE 分工

现状 iterate 是单条链路：跑 case → 产变体 → 回归闸门 → 人工审核 → 不自动覆盖。V3 拆成两段，并扩大迭代对象。

| | MT-REFLECT（每晚） | MT-EVOLVE（每周/每月） |
|---|---|---|
| 读什么 | 当日 KB-JUDGMENT + MT-VERIFY 结果 | 累积错题 + 回归结果 |
| 做什么 | 修归因标签、蒸语义条目、产假设 | 产方法变体（prompt / 阈值 / 规则 / 权重因子） |
| 写什么 | KB-METHOD 经验条目 | KB-METHOD 版本候选（`proposed`） |
| 过闸门 | 不需要 | 必须：自动回归 + 人工审核 |

三类迭代对象：

1. prompt 版本；
2. 阈值与规则表版本；
3. **现象图权重因子版本**（quality / recency / directness / consistency 的系数）——现状 iterate 没有这一类。

归因题库（待建）：

- 标注对象从「整条结论对不对」改为「这条归因边对不对」；
- 先人工确认 50~100 条边级样本，冻结为金标准；
- 分题库：预测题库（已有）、归因边题库（新建）；
- 归因题库建成前，归因不过自动闸门，只走人工审核。

**分层统计（2026-11-26 新增）**：MT-VERIFY 不只统计总准确率，必须按「市场状态（牛 / 熊 / 震荡）× 标的类型（market / sector / stock）」分层。任一层的命中率低于阈值就单列告警，不允许用整体数字掩盖局部退化。归因验证的粒度是**边级**：每条归因边单独判定是否成立，而不只判定整条 judgment。

硬规则：

- MT-EVOLVE 产物一律标 `proposed`，人工批准前不生效；
- 即使批准也不自动覆盖生产 prompt；
- 每次变体记录 `weight_algo` 版本，保证可回放。

### 5.9 结果验证契约（v1.14 草案）

验证不写回 judgment，而是追加一条 `VerificationRecord`；Judgment 上的 `verify_status / verified_result` 只是投影，可重建。

#### `VerificationRecord`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `verification_id` | string | 是 | `ver_{judgment_id}_{attempt}`，全局唯一 |
| `judgment_id` | string | 是 | 被验证的研判 |
| `due_at` | datetime | 是 | 到期时间，复制自 judgment，防口径漂移 |
| `verify_at` | date | 是 | 实际验证执行日 |
| `verify_status` | enum | 是 | `verified / missed / void`（`pending` 只存在于投影） |
| `outcome` | object | 否 | `verified` 时必填，见下 |
| `attempt` | int | 是 | 从 1 开始；`missed` 可重试，最多 3 次 |
| `reason` | string | 否 | `missed / void` 必填 |
| `created_at` | datetime | 是 | 记录写入时间 |

`outcome` 结构：

```json
{
  "hit": false,
  "actual_direction": "bearish",
  "actual_return": -0.021,
  "benchmark_return": -0.008,
  "excess_return": -0.013,
  "magnitude_error": 0.011,
  "primary_cause_match": false,
  "verified_at": "2026-11-27T15:30:00+08:00",
  "data_snapshot_id": "snap_20261127_1500",
  "error_tags": ["primary_cause", "missing_catalyst"]
}
```

`error_tags` 六类：`direction / magnitude / primary_cause / missing_catalyst / data / timing`；`hit=true` 时为空数组。

#### MT-VERIFY 流程

1. 每日扫描 `due_at <= now` 且无 `verified` 记录的 active judgment；
2. 取 `verify_at` 时点快照，计算实际方向、收益、超额、幅度误差；
3. 归因类额外判定 `primary_cause_match`；预测类允许 `unknown`；
4. 追加 `VerificationRecord`，按 `(judgment_id, attempt)` 幂等；
5. `missed` 重试最多 3 次；仍失败则保留 `missed` 并告警；
6. `void` 仅用于公司行为、契约变更等不可验证场景，必须写 `reason`；
7. 投影回 Judgment 的 `verify_status / verified_result`，投影失败不回滚记录。

硬规则：`due_at` 与 `verify_at` 不得合并；验证只能在 `due_at` 之后；记录禁止更新与删除。

## 6. 输出口设计

### 6.1 原则

- **一份研判，多处渲染**：所有出口引用同一 `judgment_id`，禁止各说各话。
- **前端只渲染**：页面不再调 3-6 个接口拼结论；原有卡片降级为证据附件。
- **不新增对话入口**：对话只作为只读账本出口，不做追问层、不做聊天 Tab。
- **播报可扩写不可新增**：叙述可以扩写，但不得引入研判之外的新结论。
- **对外发布 gate（2026-11-26 新增）**：面向全体用户的出口（EX-BRIEF / EX-PUSH / EX-PAGE 公开部分）发布前必须通过引用完整性检查——每条对外结论都带 `claim_id + evidence_id`，缺一项即降级为「仅内部」，不得对外。morning 与 broadcast 目前没有这道检查，属于现状缺口。

### 6.2 六个出口

| 出口 | 位置 | 内容 | 更新频率 |
|---|---|---|---|
| **首页** | App / Web 首页「今日结论」 | 大盘 + 持仓 + 异动的 3~5 条结论 | 开屏 / 收盘后 |
| **个股口** | 个股详情页「研判卡」 | 方向、依据、反方、失效条件、复查时间 | 每日 + 事件触发 |
| **事件口** | 事件详情页 | 事件研判 + 传导链 + 相关个股 | 事件触发 |
| **播报/推送** | 早 / 午 / 晚 / 收盘 + 异动 | 同一 briefing 出口的 4 个 slot；只推结论变化与失效 | 每日 4 次 + 事件 |
| **对话** | 现有 AI 对话 | 只读账本回答，必须引用 judgment/evidence | 用户触发 |
| **选股页** | 选股四个子 Tab（榜单 / 筛选 / 信号 / 推荐） | 每只入选股票带同一 `judgment_id`、入选理由与失效条件 | 每日 + 盘中刷新 |

### 6.3 渲染一致性

- 同一 `judgment_id` 在不同出口的 `direction / confidence / thesis` 必须完全一致。
- 出口文案由统一模板渲染，禁止各端自行拼接。
- 出口失败不影响账本记录；账本写入失败则不允许发布。

### 6.4 早/午/晚共用一个 briefing 出口

现状是「同一入口、三套实现」：早报/晚报走 `getBroadcast + getBrief`（晚报再加 `getMarketTraceReview`），午报走 `getReport('midday')`；前端分别用三套解析与三套卡片渲染。生成侧其实都已经输出 `display_report + podcast_brief + schema_version`，割裂点在**出口信封与渲染入口**，不在内容策略。

**统一边界**：统一「供数契约 + 可复用的卡片壳」，不统一「卡片长相」，也不合并三套提示词。晨报重隔夜与展望、午报重盘中校验、晚报重复盘验证，这些差异保留。

#### 6.4.1 信封 `briefing.v1`

| 字段 | 必填 | 说明 |
|---|---|---|
| `report_type` | 是 | `morning / midday / evening` |
| `slot` | 是 | `pre / mid / post`；调度与渲染只认 slot，不再按接口分支（`close` 等新时段后续按需追加） |
| `date` | 是 | 交易日 |
| `as_of` | 是 | 信息截面时间 |
| `schema_version` | 是 | 信封版本，与内容 schema 解耦 |
| `display_report` | 是 | `summary / highlight? / sections[] / risks[]` |
| `podcast_brief` | 否 | 播报扩写输入；有则可出音频 |
| `audio_path` | 否 | 音频地址；午报与晨/晚报统一放在同一位置 |
| `judgment_ids` | 是 | 本报告引用的研判；允许空数组，但不得缺省 |
| `evening_extras` | 否 | 仅晚报（`slot=post`）有值：异象判定、指数、涨跌家数、板块排行；晨/午报为 `null` |

`highlight` 是共享高亮卡的数据源：晨报填「今日头条」（`label=今日头条`，带 `title` 与标签），晚报填「大盘洞见 / 今日主因」；午报为 `null`，不渲染高亮卡。它只是 `sections[]` 第一段的投影，不新增内容。

`evening_extras` 由 `review` 报告只读投影（不新增生成链路）：

```json
{
  "has_anomaly": true,
  "anomaly_conclusion": "缩量整理为主因：量能不足导致高位股分化",
  "indexes": [{ "name": "上证指数", "close": 3421.32, "pct_change": 0.35 }],
  "breadth": { "advance_count": 2860, "decline_count": 1980, "flat_count": 210 },
  "sector_ranking": {
    "top_gainers": [{ "name": "储能", "pct_change": 3.42 }],
    "top_losers": [{ "name": "算力", "pct_change": -1.62 }]
  }
}
```

判定口径与前端 `eveningBriefCards` 一致：`brief.degraded=true` 或 review 未完成 → `has_anomaly=false`；结论含「证据不足 / 未确认主因」→ 无异象；其余（含 review 缺失）保守判定有异象。`anomaly_conclusion` 优先 `market_trace.trace.attribution_summary`，缺失时回退 brief 的「归因结论」条目。

#### 6.4.2 段落模型

```json
{
  "id": "sec_20261122_01",
  "title": "新能源",
  "conclusion": "政策催化叠加排产上修，板块强度继续抬升",
  "source": "wind_leader",
  "tags": [{ "text": "储能", "type": "sector" }],
  "claim_ids": ["cl_20261122_..._wind_01"],
  "judgment_id": "jdg_20261122_mkt_ex-000001-SH_1d_attribution_v1",
  "is_headline": false,
  "opportunities": ["储能", "快充"],
  "risks": ["高位股补跌"]
}
```

- `source`：来源 Agent（`morning / wind_leader / hot_burst / review / trend / event / midday`），驱动洞见行的图标与来源标签；缺失时前端降级为「简报」。
- `is_headline`：仅当段落在原报告中是头条时为 `true`；晨报据此把第一段投影到 `highlight`，洞见列表跳过它避免重复。
- `tags`：标的/板块标签，可为空数组。
- `opportunities / risks` 可选：午报「午后前瞻」填，晨/晚报不填就不渲染。
- 段落只引用 `claim_ids`，证据由 claim 的 `evidence_ids` 追溯，避免同一段重复挂证据。
- 晚报异象归因直接引用当天 `judgment_id`，前端不再自行拼结论。

#### 6.4.3 共享壳与时段专属卡

| 类型 | 组件（已落地） | 归属 |
|---|---|---|
| 音频条（播放状态 + 详情入口） | `BriefingAudioBar` | 共享 |
| 高亮卡外壳（白底 + 左侧主题条 + ★ 标签） | `BriefingHighlightCard` | 共享外壳；晨报头条（大结论 + 标签组）与晚报异象卡（今日主因 + 结论）内部层级不同 |
| 洞见列表（来源图标 + 情绪 + 结论 + 标签） | `BriefingSectionList` | 共享 |
| 数据胶囊（指数 / 板块涨跌 / 机会风险短词） | `BriefingChip`（`span=half/third/auto`） | 共享；大盘/板块两列，涨跌家数三列，短词流式 |
| 盘中研判 summary | `BriefingHighlightCard`（`variant="headline"` + `detailText`） | 共享外壳；午报仅多「查看完整报告」入口 |
| 机会 / 风险对位 | `BriefingView` 内 mid 模板 | 午报专属 |
| 异象判定 | `BriefingHighlightCard`（`variant="explain"`）+ `BriefingView` | 晚报专属 |
| 大盘行情（指数 + 涨跌家数） | `EveningMarketIndexCard` | 晚报专属 |
| 板块行情（领涨 / 领跌） | `EveningSectorsCard` | 晚报专属 |

**判定标准**：形态相同、数据来源不同 → 抽共享壳；只有某个时段才需要 → 保留专属卡，不强行抽象。

#### 6.4.4 非目标

- 不合并三个 writer 的提示词与取数策略，只共用编排入口、校验与落账。
- 不要求三份报告内容同构、段落数量一致。
- 不为了「统一」把午报机会/风险、晚报异象/行情塞进通用段落模型。

#### 6.4.5 迁移顺序与验收

1. 后端先双写 `briefing.v1` 信封，保留旧字段。
2. 前端收敛为一个解析入口，三套模板暂时不动。
3. 抽音频条、头条壳、洞见列表三个共享组件。
4. 时段专属卡原样迁移；新增时段只加 slot 配置，不改页面结构。

验收：同一事件在晨/午/晚引用同一 `claim_id`；新增一个 slot 时前端无需新增解析分支。

#### 6.4.6 统一读取接口与前端接入

**只读聚合接口**（app-api `publicRouter`，须在 `createAgentProxy` 之前挂载）：

| 接口 | 说明 |
|---|---|
| `GET /api/agent/briefing/:slot/:date` | `slot ∈ pre/mid/post`，`date=YYYY-MM-DD`；只读投影，不改数据库与生成链路 |

- `pre`：读 `brief_morning` + `broadcast_morning`，第一条洞见投影为 `highlight.label=今日头条`，`audio_path` 取广播报告。
- `mid`：读 `midday` 报告 `content.display_report`，机会/风险留在段落内，`audio_path` 可为 `null`。
- `post`：读 `brief_evening` + `broadcast_evening` + `review`；`summary` 优先取标题「收盘复盘」的结论；`evening_extras` 从 review 的 `market_trace` 投影异象结论、指数、涨跌家数与板块排行。
- 查无报告返回 `{ code: 0, data: null }`，前端渲染空态；读取异常才返回 500。

**前端接入**：

- 前端固定走真实接口 `/api/agent/briefing/:slot/:date`，无 mock 分支或本地 fixture。
- `pages-sub-app/briefing/prototype`（`pages.json` 已注册）：早/午/晚三 Tab + 日期切换，用于预览三套模板与共享壳，同样读真实接口。
- 正式页 `pages-sub-app/briefing/index` 已收敛为 `agentApi.getBriefing(slot, date)` + `BriefingView` 单入口；保留日期回退、Tab 切换、悬浮窗音频与详情跳转。晚报大盘/板块数据随信封 `evening_extras` 下发，不再单独请求 `getMarketTraceReview`。

**边界**：图只做融合与研判，不重复实现各模块的采集与计算；除校验目的外不直连原始数据源。

### 7.2 组长先行（样板链）

先由组长负责的链路跑通，作为其他模块的接入样板：

**数据平台 → 洞见 → 播报 → 市场**

- 数据平台：`market_perception` + 工具带，证明"取一次、全图共用"。
- 洞见：`insight_research` 读趋势/风口/事件 claims，证明"互相影响"确实改变结论。
- 播报：`briefing_writer` 渲染同一 judgment，证明"一份研判多处渲染"。
- 市场：首页切到 judgment 渲染，证明"前端不拼结论"。

样板链稳定后，其余模块按同一契约迁移；每个模块只需暴露工具 + 写 evidence/claims，不改前端。

### 7.3 代码里已有的三个雏形（复用，不重写）

合并进来的代码里，有三处已经长成了目标方向的形状：

| 已有 | 位置 | 对目标的用处 |
|---|---|---|
| Agent 注册表 | `agents/registry.py`：15 个 Agent 一处声明，11 个进图、4 个仅调度 | 对应主图的节点登记，避免「图、路由、升级表」三处手抄 |
| 统一任务执行 | `services/task_runner.py` + `task_store.py` | 接口可复用，接入 `brain_v3` 时包一层适配；任务执行记录是 `trace` 通道的雏形 |
| MCRE 事件→行业映射 | app-api `modules/causal` + agent `event_node_mapping.py` / `entity_recall.py` | 事件子图的传导链不必从零做，先把已有映射包装成 claim |

**边界**：这三处分别解决了「一处声明 / 一次执行 / 一条映射」，但都还没有共享证据与论点，所以仍需要主图与账本把它们串起来。

### 7.4 老 agent → 研究子图：打碎重组，不整块搬

老 agent 不是一一对应 AG-LEAD / AG-WIND / AG-EVENT / AG-FUND / AG-CAPITAL / AG-MACRO / CA-TREND / CA-RHYTHM，很多把「取数 + 研究 + 研判 + 写作」揉在一个循环里，必须按职责拆：

| 老 agent | 现在主要做什么 | 拆到哪 | 注意 |
|---|---|---|---|
| `morning` | 取数 + 大盘归因 + 写晨报 | SE-MARKET / SE-EVENT + AG-LEAD + EX-BRIEF | 不能整块搬，研究和写作分开 |
| `wind_leader` | 风口/龙头报告 | AG-WIND | 报告壳交给 EX-BRIEF/EX-PAGE |
| `event` | 事件理解 + 传导链 | AG-EVENT | 理解用单次 LLM，传导用 bounded ReAct |
| `stock` | 个股问答（基本面 + 异动） | AG-FUND + AG-LEAD | 基本面与归因拆开 |
| `sector` | 板块问答 | AG-WIND + AG-LEAD | 板块强度与个股归因拆开 |
| `trend_score` | 趋势评分 | CA-TREND | 保留计算，去掉自由循环 |
| `hot_burst` | 热点历史 | AG-WIND / AG-EVENT | 作为证据，不单独下结论 |
| `alert` | 异动监控 + 推送 | IN-EVENT / EX-PUSH | 只推变化与失效 |
| `review`（大盘溯源） | 快照 + 归因 + 预判 + 报告 | SE-MARKET / SE-EVENT / SE-ENTITY + AG-LEAD + DB-BULL ~ DB-WRITE + EX-BRIEF | 见 §7.5 |
| `rhythm_master` | 仓位/节奏 | CA-RHYTHM | 规则计算 + 单次 LLM 解释 |
| `general` | 通用问答 | EX-CHAT | 补账本引用与步数上限 |
| `broadcast` / `midday_broadcast` | 播报文案 | EX-BRIEF | 只渲染，不做研究 |
| `sector_trace` / `stock_trace` | 单次溯源 | AG-LEAD / AG-CAPITAL | 资金部分归 AG-CAPITAL |
| `advisor` 工具箱 | 没有对应 agent | 清理或并入 AG-LEAD | 当前是死映射 |

原则：**按「取数 / 研究 / 研判 / 表达」四件事拆，不按 agent 整块搬**；拆完的老 agent 只保留 prompt 资产与失败经验，循环和工具选择交给新 harness。

### 7.5 示例：大盘溯源定时 run 的改前 / 改后

**改前（15:05 定时）**：

```text
IN-TIME cron → review Agent
  → build_market_trace_snapshot（自己抓行情/板块/资金/新闻）
  → deep_think 单次 JSON 归因
  → validate + Redis 缓存 + 归档
  → predict_from_trace 写 prediction_records
  → 前端读 market_trace 报告
```

问题：快照私有、结论是文本、和早报/个股不共享证据；schema 不全时容易逼模型编主因。

**改后（15:05 定时）**：

```text
IN-TIME schedule(window=review) → OR-RUN 选 review 档位（run_id + 预算）
  → SE-MARKET 行情证据：指数 -1.2%，成交额 7800 亿，涨停 28 / 跌停 12
  → SE-EVENT 事件证据：消息面平稳，仅 2 条行业新闻
  → SE-ENTITY 实体证据：权重股与板块归属
  → KB-EVIDENCE（一次取数，全图共用）
  → AG-EVENT 事件（事件研究员）：无重大外部冲击
  → AG-WIND 风口（板块研究员）：权重板块拖累，热点散乱
  → CA-TREND 趋势（趋势研究员）：指数跌破 20 日线
  → AG-FUND 基本面（基本面研究员）：无业绩雷
  → AG-CAPITAL 资金（资金研究员）：北向 -60 亿，主力净流出，两融平稳
  → AG-MACRO 宏观（宏观研究员）：利率/汇率平稳
  → AG-LEAD 归因（洞见研究员，bounded ReAct）：
       候选 = 流动性收缩 / 权重拖累 / 情绪转弱 / 技术破位
       逐条验伪：事件排除；资金支持权重拖累；宏观排除环境冲击
  → CA-RHYTHM 节奏（仓位研究员）：仓位 60% → 50%，前提「成交额未回 9000 亿」
  → DB-BULL 多方（多方研究员） / DB-BEAR 反方（反方研究员）辩论
  → DB-JUDGE 裁决（裁判）：保留「缩量」与「权重拖累」两条主因，降权「情绪转弱」
  → DB-WRITE 主笔（主笔）：direction=偏弱，confidence=0.62，
       invalidator=成交额回到 9000 亿以上或权重止跌
  → KB-JUDGMENT 落账 + 阶段 3.1 归档
  → EX-BRIEF 渲染大盘溯源视图 → UI-HOME 首页下钻
  → MT-VERIFY 在 due+3 自动回填命中/错误类型
```

**共同点**：触发时间、页面结构（现象/主因/备选/被否/次日验证）、due+3 预判都保留。
**区别**：数据从私有快照变共享 KB-EVIDENCE；归因从单次 LLM 变「候选原因 + 工具验伪 + 多空辩论」；结论从报告文本变 judgment；失败允许写 `insufficient`，不再逼模型编主因。

### 7.6 示例：风口 agent 的改前 / 改后

场景：2026-11-25 收盘后，半导体涨 3.2%，系统需要判断「是风口启动，还是反弹一日游」。

**改前（wind_leader 单 agent）**：

```text
用户/定时 → supervisor 路由 wind_leader
  → deep_think ReAct（tools = get_wind_leaders）
      → 自己抓板块涨幅榜
      → 自己决定要不要再查资金、新闻
      → 一个上下文里同时做：板块强度 + 轮动阶段 + 龙头筛选 + 写 800 字报告
  → 前端渲染报告
```

问题：取数、研究、归因、写作揉在一个循环；数据不进共享账本；个股页再问同一板块要重跑；工具里没有的维度（拥挤度、第几天）不会主动补。

**改后（wind_probe 子 agent，由 AG-LEAD 按需调用）**：

```text
OR-RUN 选档（wind_board）
  → OR-PROFILE 发 RunBrief：必查 wind_probe + capital_probe；可选 event / macro；预算 6 次
  → SE-MARKET / SE-EVENT / SE-ENTITY → KB-EVIDENCE（市场基调：风险偏好、量能、风格）
  → AG-LEAD 主控：
      step1  trend_snapshot()  → 半导体指数站上 20 日线（确定性）
      step2  wind_probe("半导体")
               tools = 板块行情 / 资金流 / 龙头识别 / 事件热度 / 宏观 β
               max_steps = 3，独立上下文
               返回 claim:
               {
                 "sector": "半导体",
                 "strength": 0.78,            // 涨幅 + 广度 + 持续性
                 "rotation_stage": "day_2",   // 启动第 2 天
                 "leaders": ["中芯国际", "北方华创"],
                 "drivers": ["国产替代事件", "北向流入"],
                 "crowding": 0.61,
                 "evidence_ids": ["ev_20261125_041", "ev_20261125_058"],
                 "produced_by": "wind_probe@v1.0",
                 "confidence": 0.66
               }
      step3  capital_probe()  → 北向连续 3 日流入，主力净流入 42 亿
      step4  判断：事件催化已由 wind_probe 带回，不再调 event_probe（省一次）
  → AG-LEAD 汇总 ResearchResult：风口成立，第 2 天，拥挤度中等
  → DB-BULL 多方（产业催化 + 资金持续） / DB-BEAR 反方（涨幅透支 + 无业绩支撑）
  → DB-JUDGE 裁决 → DB-WRITE 写 judgment → KB-JUDGMENT 落账
  → 风口页 / 个股页 / 对话共用同一个 judgment_id
```

| | 改前 wind_leader | 改后 wind_probe |
|---|---|---|
| 形态 | 主图上的独立 agent | AG-LEAD 调用的子 agent（工具） |
| 上下文 | 取数 + 判断 + 写作混在一起 | 只做板块取证，返回 claim |
| 输出 | 800 字报告 | 结构化 claim + evidence_ids |
| 复用 | 每次问答重跑 | 风口页 / 个股页 / 对话共用 |
| 调用方 | supervisor | AG-LEAD、OR-RUN（风口页可并行 fan-out 多个板块） |
| 审计 | 只有文本 | `produced_by` + 证据链可追 |

**共同点**：板块涨幅、龙头、资金、事件这些事实口径不变；用户看到的风口页结构不变。
**区别**：从「一个 agent 干四件事」变成「主控判断 + 子 agent 取证」；同一份 claim 被三个入口复用；证据不足时 wind_probe 抛可分类错误（如 `empty`），由主控记入 `missing_probes` 并按是否必查判 `partial` / `insufficient`，AG-LEAD 不再硬编一个风口结论。

### 7.7 现有三个 agent 按 V2.1 跑一遍

现状里已有三个和研判直接相关的 agent：预判（`services/prediction_service.py`）、溯源（`review.py` / `stock_trace.py` / `sector_trace.py`）、迭代（`iterate.py` + `services/iterate_analyzer.py`）。它们在 V2.1 里不是被删掉，而是改变挂载位置。

#### 7.7.1 预判 agent：从独立 LLM 调用变成 DB-WRITE 的 `predictions` 字段

**现状**：输入溯源结果 + 快照 → 单次 LLM → `PredictionResult`（short / mid / long 三档 + 到期日），不调工具，和归因是两次独立推理。

**V2.1**：

```text
IN-TIME 收盘 / IN-USER 用户 → OR-RUN（market_review 或 stock_on_demand）→ OR-PROFILE → AG-LEAD
  → probe 取证 → MT-CHECK 检查 → DB-BULL / DB-BEAR → DB-JUDGE → DB-WRITE
  → DB-WRITE 写 judgment 时同时写 predictions[]：
      [{horizon: "short", direction: "bearish", confidence: 0.58, verify_at: "2026-12-02"},
       {horizon: "mid",   direction: "neutral", confidence: 0.51, verify_at: "2026-12-23"},
       {horizon: "long",  direction: "bullish", confidence: 0.55, verify_at: "2027-05-25"}]
  → MT-VERIFY 到期分别回填 judgment.verified_result 与 predictions[].verified_result
```

变化：

| | 现状 | V2.1 |
|---|---|---|
| 调用形态 | 独立 LLM，输入快照 | DB-WRITE 落账时生成，和归因同源 |
| 一致性 | 可能出现「归因看空、预判看多」 | 强制共用同一批 claims 与 confidence |
| 到期日 | `HORIZON_TRADING_DAY_OFFSETS` 确定性计算 | 保留，仍不让 LLM 算日期 |
| 验证 | 单独验证 | MT-VERIFY 同一次回填，归因与预判分别记命中 |

好处：不会再出现两份互相矛盾的结论；预判不再是「另一份报告」，而是 judgment 的前瞻部分。

#### 7.7.2 溯源 agent：三套溯源收敛成三个档位

**现状**：大盘 `review.py`（单次 LLM + `MarketTraceSnapshot`）、个股 `stock_trace.py`（Redis Stream consumer + 受限 LLM + schema 校验）、板块 `sector_trace.py`，三套各自构建快照、各自校验、各自落库。

**V2.1**：

```text
大盘：IN-TIME → OR-RUN(market_review) → OR-PROFILE 必查 capital + wind
        → AG-LEAD → capital_probe / wind_probe →（可选）event / macro
        → MT-CHECK → DB-BULL / DB-BEAR → DB-JUDGE → DB-WRITE → KB-JUDGMENT

个股：IN-EVENT（stock_trace consumer 只负责触发，不再直接调 LLM）→ OR-RUN(stock_on_demand)
        → OR-PROFILE 必查 wind + event
        → AG-LEAD → wind_probe / event_probe →（可选）fundamental / capital
        → MT-CHECK → DB-BULL / DB-BEAR → DB-JUDGE → DB-WRITE → KB-JUDGMENT

板块：IN-USER / IN-TIME → OR-RUN(wind_board) → OR-PROFILE 必查 wind + capital
        → AG-LEAD → wind_probe / capital_probe →（可选）event / macro
        → MT-CHECK → DB-BULL / DB-BEAR → DB-JUDGE → DB-WRITE → KB-JUDGMENT
```

变化：

| | 现状 | V2.1 |
|---|---|---|
| 快照 | 三套私有快照 | 统一 SE-MARKET / SE-EVENT / SE-ENTITY → KB-EVIDENCE |
| 推理 | 单次 LLM，无工具 | AG-LEAD + probe，有验伪 |
| 输出 | 三套 schema 的报告 | 统一 claim + judgment |
| 复用 | 三个入口各跑各的 | 同一批 probe，一份证据 |
| 触发 | consumer 直接调 worker | consumer 只产事件，触发 IN-EVENT |

`stock_trace` 的 Redis Stream consumer、幂等键、artifact 版本这些工程件全部保留，只把「消费后直接调 LLM」改成「消费后发 IN-EVENT 触发」。

#### 7.7.3 迭代 agent：从「偏差报告」升级为 MT-REFLECT 离线反思

**现状**：`iterate.py` 是纯流水线 + 阈值 + 按需 LLM，只读、只出建议，不改 prompt、不改代码、不改数据。

**V2.1**：

```text
IN-TIME 收盘后（非交易时段）→ MT-REFLECT 离线反思
  → 读 KB-JUDGMENT 昨日判断 + MT-VERIFY 验证结果 + KB-METHOD 错题本
  → 四个动作：
      1. 修正笔记：给错判案例补 error_type（只追加）
      2. 蒸馏条目：support_cases >= 3 的模式写成 KB-METHOD 语义条目
      3. 生成假设：跨案例联想，标 pending，第二天最多占 1 次 probe 预算
      4. 更新权重：按 hit_rate 调整方法先验初始置信
  → 写 KB-METHOD（版本号 + proposed 状态）
  → 人工批准后生效
```

变化：

| | 现状 | V2.1 |
|---|---|---|
| 定位 | 偏差分析报告 | 记忆巩固 + 方法演化 |
| 输入 | 快照文件 + 阈值 | KB-JUDGMENT / KB-METHOD / MT-VERIFY 三源 |
| 输出 | 建议文本 | KB-METHOD 版本化条目 + 假设池 |
| 写权限 | 只读 | 只写 KB-METHOD，append-only，需人工批准 |
| 对第二天的影响 | 无 | 假设池影响 AG-LEAD 的可选 probe 选择 |

`iterate_analyzer` 的阈值引擎保留，作为 MT-REFLECT 的「哪些案例值得反思」筛选器，不重写。

#### 7.7.4 三个 agent 跑完之后的整体结果

| 维度 | 现状 | V2.1 |
|---|---|---|
| 预判 | 独立报告，可能和归因矛盾 | judgment 的 `predictions` 字段，同源 |
| 溯源 | 三套快照、三套 schema | 三个档位、一套账本 |
| 迭代 | 一份建议报告，第二天不生效 | KB-METHOD 版本 + 假设池，第二天参与 AG-LEAD 决策 |
| 证据 | 各 agent 私有 | 全链路 `evidence_ids` 可追 |
| 验证 | 归因、预判分别验证 | MT-VERIFY 一次回填，分别记命中 |

逐项探查了 agent-py 与 app-api 的实际实现，结论如下。这张表是迁移的底稿，避免只凭图纸判断。

| stock | supervisor 路由到 `stock_analyst`，ReAct + 3 工具，**不落表**，只返 `final_response` | `stock_on_demand` 档，必查 AG-WIND + AG-EVENT | **强制写 KB-JUDGMENT** |
| sector | tag_code 输入，ReAct + 3 工具；`predict_sector_trend` 仅在问持续性时调 | `wind_board` 档 → AG-WIND + AG-CAPITAL | 板块预测并入 `judgment.predictions` |
| event | **5 次固定 LLM 调用**：Call 1 理解 + Call 2 传导；chain 只能来自图谱证据；STOCK 范围跳过传导 | SE-EVENT 去重 → fast 分级 → AG-EVENT | **保留两段式；同时做 bounded ReAct A/B 对比** |
| wind_leader | app-api 03:00 算好；09:00 链中 agent 预检后写报告 | `wind_board` 档 → AG-WIND | 与 sector 共用一个档 |
| hot_burst | 机构调研**四源共振**（财联社/格隆汇/同花顺/研报，≥2 源），09:00 ReAct | 规则先算共振，过线才 AG-EVENT | 共振规则留在数据层 |
| trend_score | app-api 四维打分写 `trend_scores`（技术 35/行业 25/消息 20/基本面 20）；agent 只写 `ai_conclusion` | CA-TREND 直接调接口 | 解释只在评分变化时写 |
| alert | 3 子 agent 并行 + Master 汇聚，SSE 流式；已有 `/api/agent/report/alert/:symbol/:date` | fast 规则 → AG-EVENT/CAPITAL → EX-PUSH | 保留 SSE |
| broadcast | 双人对话 LLM + 两个音频接口（briefing / midday），回填 `audio_path` | EX-BRIEF 读同一 judgment 写三时段 | 音频共用一条研判 |
| rhythm_master | **纯规则**：情绪 0.60 + 趋势 0.27 + 恐贪 0.13；四时点继承链 | CA-RHYTHM 纯函数 + 上一条研判 | 保留四时点 |
| chat | `qa_router` 短路闸门 + `skill_executor` + `synth_answer` 失败降级 | EX-CHAT 先读 KB-JUDGMENT，不命中才触发 AG-LEAD | 保留短路闸门 |
| insight | `classify_primary_cause` 阈值 3.0 / 1.0；LLM 选择 + 规则兜底；app-api 每 10 分钟 `runInsightCycle` | 现象图 + 贡献度分解 | 保留 10 分钟 cycle |
| APScheduler | agent-py 约 20 个 job + app-api 十几个 node-cron，两边各管一摊 | 四个 IN 入口只发 run | 两边 cron 不合并，统一登记 |

| 人工审核 | 双闸门任一层 `delta<0` 就 block；只有 prediction 变体 gate，归因分支不 gate | MT-EVOLVE/REFLECT 标 `proposed` | 归因分支也纳入 gate |
| 存储 | reports 表有 `expires_at`，每天 03:00 清理；Redis 两套 TTL（briefing 24h / event 30min）；归档 `open("x")` 不可覆盖；`podcast_cache` 也清理 | reports 降为渲染产物，KB 为事实源 | 历史回看接口形状不变 |

**盘点纠正的 6 个错误认知**：

1. 晚间闭环不是「一周只成功 2 条」——EventBus 链已建好，有重试与降级；旧数字来自历史统计。
2. `event` 不是 ReAct，是 5 次固定 LLM 调用，传导链受图谱证据强约束。
3. `stock` 不落表，个股分析没有历史可回看，这是真缺陷（已确认改为强制写 KB-JUDGMENT）。
4. `trend_score` 是两处：app-api 算分，agent 写 AI 结论；「不重复计算」还要覆盖结论。
5. `hot_burst` 是机构调研四源共振，不是涨幅榜；规则必须保留。
6. `rhythm_master` 几乎没有 LLM，归为计算工具是正确的。

**确认结论（2026-11-26 逐项确认）**：16 行取舍已全部确认，可直接作为实现依据。

| 功能 | 已确认结论 |

| stock | 强制写 KB-JUDGMENT |
| sector | 板块预测并入 `judgment.predictions` |

| broadcast | 保留早 / 中 / 晚三条音频 |
| rhythm_master | 保留四时点继承链 |

## 8. 准确率闭环

### 8.1 三层指标

| 层级 | 指标 | 验收方式 |
|---|---|---|
| 数据准确率 | 字段完整率、个股归属准确率、抓取成功率 | 自动化 + 抽样复核 |
| 结论准确率 | 方向一致率、事后命中率 | `verifier` 回填统计 |
| 推理质量 | 证据链、引用、逻辑、风险披露 | 盲评 rubric |

**推理质量 rubric**：数据/事实正确 30% · 证据链与来源可追溯 25% · 逻辑一致性 20% · 可执行性 15% · 风险披露与反例 10%。双人盲评 + LLM 初评，分歧人工裁决。

### 8.2 验证与校准

- 所有研判按 `verify_at = due + 3 个交易日` 回填结果。
- 计算**校准度**：高置信组命中率必须显著高于低置信组，否则置信度视为无效。
- 校准结果回灌到 `calibrator` 的先验，不直接改模型 prompt。

### 8.3 失败模式库

分类：数据缺失 / 事实错误 / 逻辑跳跃 / 时效滞后 / 过度保守 / 过度激进。
按模块统计 Top3，`method_evolver` 转成方法版本，每周复盘只讨论失败模式与改进项。

### 8.4 与权威分析师对比规则

- **时间截面冻结**：只使用 `as_of` 当时可得的信息，禁止事后视角。
- **区分错误与分歧**：结论不同不等于错，最终以事后走势与官方数据为裁判。
- 分析师观点只作参考基线与评审素材，**不照搬结论**（合规与依赖风险）。

### 8.5 执行拓扑 A/B 评估

目的：验证「只跑档位声明的必查 / 可选 probe」（`required_scope`）相对「强制全跑」（`all_probes`）在结论质量不降的前提下 token / 时延更低。完整设计见《智慧大脑-V3-架构改进方案》§3.7、§3.7.1、§3.7.2；本节只保留契约层口径。

**24 题降级为规则回归集**：`tests/fixtures/brain_eval_cases.json` 改名 `rules_cause_cases.json` 并移入规则层单测，只校验 `classify_primary_cause` 阈值，**不再作为 A/B 判据**。

| 维度 | 口径 |
|---|---|
| 拓扑 A / B | 同一张图的两个 profile：A = `all_probes`（强制全跑）；B = `required_scope`（只跑 `needs` / `optional` 声明的 probe，确定性选择，不含 LLM 自主加查） |
| 样本 | `brain_evals/cases/` 录制集，按 `published_at <= as_of` 冻结；第一周只做 `market_review` 10 条 |
| 判定门槛 | 配对比较仅 `n≥30` 执行；`n=10` 只记录方向性观察，不判定 |
| 指标 | 方向命中（T+3 客观）、主因一致（双人盲评）、证据引用率、token、P95、`partial` / `insufficient` 率、`stop_reason` 分布（budget/timeout/error）与 `degraded` 率，分别统计不混算 |
| 判定 | B 的方向命中比 A 少不超过 2 条；主因盲评不劣；token 或 P95 至少一项降 20%；`partial` 率不高于 A+5pp；预算触顶率不高于 A+5pp |
| 时间线 | 方向命中依赖 T+3 客观结果，最早 D10 才有判定；D7 只定 A/B 时间与样本 |
| 记录 | 结果写 KB-GOV 治理看板，按 `registry.lock` 拓扑指纹归因 |

硬规则：

- A/B 必须用同一批样本、同一时间截面、同一模型版本；模型升级或 `registry.lock` 指纹变化后需重跑。
- 作废「24 题 + 差值 ≤ 3pp」：每类 8 题时 3pp 不足 0.25 题，统计上不可判定。
- token 统计口径按 `BrainRunResult.tool_stats` + LLM usage 汇总，不估算。
- 评估未通过前，不允许把拓扑 B 设为默认档位。

### 8.6 审计留痕分层（v1.12 新增）

审计不是"全有或全无"。分三层，按需留，避免为了合规牺牲 agent 自由度。

| 层 | 记什么 | 去掉的后果 | 策略 |
|---|---|---|---|
| L1 结果 | `run_id`、输入快照、输出、模型 / prompt 版本、成本 | 无法复盘"当时输出了什么" | 全量 |
| L2 证据 | 每条对外 claim → `evidence_ids`、`snapshot_id` | 无法证明来源；无法评测、无法时点回放 | 对外结论强制 |
| L3 过程 | 研究树、每次 request / response、工具入参 | 多 agent 出错只能猜；无法去重 / 防环 / 算 stall | 正常 10%，失败与含 conflict 的 run 100% |

规则：

- **L1 全量**：任何 run 都必须有；没有 L1 的 run 不得进入评测与 A/B。
- **L2 只对用户可见结论强制**：中间推理不强制逐条引用；对外 judgment 缺 `evidence_ids` 直接拒绝发布。
- **L3 采样**：`trace` 只存 `evidence_id` 与引用关系，不存证据原文；原文留 KB，按权限读。
- **审计字段同时是运行态数据**：`request_id / parent_request_id / round` 承担请求去重、环检测与 `stall_count`；删除 L3 会让多轮 loop 退化成"重复问同一个问题"。
- **时点不可省**：`snapshot_id` 与 `as_of` 是回测与 A/B 的前提，不属于"可选留痕"。
- 具体监管要求以法务意见为准；本节只定工程口径。

**框架落位**（与改进方案 §3.17 一致）：

- Deep Agents：仅 `AG-LEAD`（主链，D6 spike 三项通过后）+ `MT-EVOLVE` / `MT-REFLECT`（离线）+ `EX-CHAT`（P2 评估）；
- CrewAI：仅离线（`MT-EVOLVE` / `MT-REFLECT`），不进主链；AutoGen 不引入；
- 共同前提：无论用哪个 harness，KB 仍由规则层单写，agent 不得直接写账本。

### 9.1 迁移方式：Strangler Fig（绞杀榕）

对应 AWS / 微软的 strangler fig pattern，三阶段：

| 阶段 | 做什么 | 退出条件 |
|---|---|---|
| Transform | 新链路并行建设，老链路不动；新链路写**独立影子表**（同结构不同表名，行带 `is_shadow=true`，永不进任何出口查询） | 新链路能跑通同一批评测集，且 baseline manifest 已冻结 |
| Coexist | 双跑对比，feature flag 控流量（1% → 10% → 50%）；老链路保留回滚 | 连续 7 天工程指标不劣于老链路 |
| Eliminate | 逐步退役老组件，只保留 adapter | 流量 100% 切换且稳定 2 周 |

灰度顺序：影子（0%）→ 10% → 50% → 100%。三阶段与影子 / 灰度 / promote 一一对应：Transform = 影子表，Coexist = feature flag 灰度，Eliminate = 正式账本 100%。

**影子阶段的三条硬要求（对应方案 §3.8）**：

| 要求 | 口径 |
|---|---|
| 物理隔离 | 影子表与正式表同结构不同表名，影子行 `is_shadow=true`，永不进任何出口查询；影子行保留 30 天后清理 |
| baseline manifest 冻结 | 对照前冻结代码 / 契约版本与 `registry.lock` 指纹；样本集 sha256 写入 `brain_evals/cases/index.json`，运行前校验，防基线漂移 |
| promote 门槛 | promote 不是改表名：灰度 run 重新写正式表并重新分配 `version`（app-api 单事务），旧 active 置 `superseded`；门槛 = 准确率不降（方向走盲评）**且** token 或 P95 降 20% |

影子阶段**只比工程指标**（P50/P95、token、成本、`partial` 率、预算触顶率、run 内去重率、回放一致性）；方向与主因一律走人工盲评，用旧链路方向作基线等于拿错误答案校准新链路。

硬规则：

1. 不删老代码，先用 adapter 包一层；老 agent 的 prompt 与失败经验标注原作者，作为资产保留。
2. 每次只迁一个功能，不批量切换。
3. 对比指标至少包含：方向准确率、主因命中率、token、P95 时延、`partial` 率；影子阶段方向 / 主因走人工盲评，不与旧链路比方向。
4. 任一指标劣化超过阈值就回滚，不做例外解释。

### 9.2 代码归属：CODEOWNERS

仓库根目录 `CODEOWNERS` 声明每个文件的评审人。示例（owner 待各负责人确认后填入）：

```text
# 智慧大脑 V3（brain_v3/）
/aistock-agent-py/brain_v3/probes/wind/        @风口负责人
/aistock-agent-py/brain_v3/probes/event/       @事件负责人
/aistock-agent-py/brain_v3/nodes/              @研判负责人
/aistock-agent-py/brain_v3/graph/              @编排负责人
/aistock-agent-py/brain_v3/tools/              @数据组
/aistock-agent-py/brain_v3/registry.yaml       @编排负责人
/aistock-agent-py/brain_v3/contracts/          @契约负责人
```

规则：

- `registry.yaml` 的 `owner` 是唯一事实源，CODEOWNERS 由它生成或校验，禁止两处手维护；
- 改别人的文件必须经过 owner review，不能悄悄改；
- 接口层（claim / ResearchResult / judgment schema）由契约 owner 统一评审；
- owner 是评审责任，不是行政权力；原作者保留署名。

### 9.3 配置单一来源

现状：cron 在 `config.py`、app-api cron 在 `index.ts`、prompt 在 `prompts/`、阈值散在各 worker。

规则：

- 所有 cron、阈值、prompt 版本号登记到一张 `brain_config` 表（或 YAML），代码只读，不写死；
- 每次 run 记录 `config_version`，回归与回放按版本锁定；
- 改配置走 PR + 回归闸门，不在线上直接改。

### 9.4 四个隐藏问题的修法

这四个问题不是 V3 新造的，是把现状里被「每处各写一份」掩盖的问题照出来的。修复顺序：**能复现 → 有证据 → 不偷看 → 口径一致**。

#### 9.4.1 传导边没有证据

**病根**：event 的传导链由 LLM 生成，每跳的 `reason` 是自然语言，没有强制绑定 `evidence_id`；图谱只约束候选，不约束落地。

| 层 | 动作 |
|---|---|
| 数据结构 | `AttributionEdge.evidence_ids` 改为非空 |
| probe 三段式 | 逐边校验，无证据的边降级为 `hypothesis=true`，不参与权重计算 |
| MT-CHECK | hypothesis 边权重之和 > 30% 时强制降置信并标注「部分为假设」 |
| DB-WRITE | 有证据的边进 KB；假设边单独存，供次日验证 |

**迁移**：历史传导能回填的补证据；补不上的标 `hypothesis=true`，不删，但不计入准确率。

#### 9.4.2 as_of 与未来函数

**病根**：新闻表有 `fetched_at`，但很多源没有准确 `published_at`；快照按「最新 N 条」取，不是按「as_of 之前可见」取；部分新闻是事后补录，回测会被误当成当时已知。

| 层 | 动作 |
|---|---|
| 数据结构 | 每条证据三时间：`event_time / published_at / as_of` |
| SE | 取数按 `published_at <= as_of` 过滤；无 `published_at` 的源标 `time_confidence=low` |
| 下游 | 不得自行取数或修改 `as_of`；同 run 只认 SE 产出的快照 |
| MT-VERIFY | 只用 `as_of` 之前可见的证据重放，checkpointer 提供快照 |

**迁移**：旧报告没有真实 `as_of`，标 `as_of_confidence=low`，不用于回测得分，只作叙事参考。

#### 9.4.3 同一票多处结论不一致

**病根**：五处触发时间不同、判断类型不同，各自生成结论，没有 owner。按 `as_of` 做唯一键是错的——08:50 和 09:00 的截面不同，会生成两条 1d 结论；把 review 当成 morning 的 v2 也是错的——预测与归因是两个不同命题。

**修法：按判断类型分 owner + 版本链 + 有效期。**

`judgment_type` 分三类：

| 类型 | 含义 | 谁产 |
|---|---|---|
| `forecast` | 对未来走势的预判 | morning、wind_leader、hot_burst |
| `attribution` | 对已发生事实的归因 | alert、insight、review |
| `assessment` | 对当前状态的评估（阶段、强弱） | sector 分析 |

```
judgment:
  subject: {type: stock, code_ns: ex, code: 600519-SH, name: 贵州茅台}
  horizon: 1d
  judgment_type: forecast | attribution | assessment
  valid_from: 08:50
  valid_until: 15:00
  status: active | invalidated | superseded
  supersedes: jdg_20261126_stk_ex-600519-SH_1d_forecast_v1
```

规则：

1. owner 键是 `(type, code_ns, code, horizon, judgment_type) WHERE status='active'`，同一键同时只有一条 `active`；
2. 下游触发时先查「是否有覆盖当前时刻的 active」，有则引用，不新生成；
3. 09:00 broadcast 查到 08:50 的 `forecast` 仍有效，直接引用；
4. **版本链只在同一类型内成立**：盘中 alert 的快速归因（`attribution`，partial）可被收盘 review 的完整归因（`attribution`，full）`supersedes`；
5. **morning 的 `forecast` 与 review 的 `attribution` 互不覆盖**，两者是**对照关系**，由 MT-VERIFY 判定「预判 vs 实际」是否命中；
6. 盘中跌停触发 `claim.invalidated`，`forecast` 提前标 `invalidated`，alert 新开 `attribution` run；
7. `intraday` 与 `1d` 是不同 horizon，互不冲突，但 intraday 必须引用同标的 1d judgment 作为背景。

| 出口 | 触发时间 | horizon | judgment_type | 与其他出口的关系 |
|---|---|---|---|---|
| trend_score | 02:00 + 08:30 | — | claim | 不算 judgment，只产 claim |
| wind_leader | 03:00 + 09:00 | 3d | forecast | 独立 owner |
| morning | 08:50 | 1d | forecast | 当日 forecast 的 v1 |
| broadcast | 09:00 | — | 引用 | 只引用，不产 judgment |
| hot_burst | 09:00 | 1d | forecast | 与 morning 同 type，可复用或修正 |
| alert | 盘中 | intraday | attribution | 快速归因 v1（partial） |
| insight | 每 10 分钟 | intraday | attribution | 采集 + 触发，不直接产 |
| review | 16:00 | 1d / 3d | attribution | 完整归因，supersedes 盘中 partial 归因；与 morning 的 forecast 对照 |

**迁移（Strangler Fig 三阶段）**：

1. 五处先写 `judgment_id` 字段（可为空），建立归属意识；
2. 有 judgment 的引用，没有的标 `standalone=true`；
3. 禁止 `standalone`，必须走 run。

#### 9.4.4 无法复现当时的 prompt / 阈值

**病根**：prompt 靠 git 版本，阈值散在 `config.py` 和各 worker，run 记录没有版本号。

| 层 | 动作 |
|---|---|
| 配置 | §9.3：cron、阈值、prompt 版本号登记到 `brain_config` |
| 归档 | `brain_run_archives` 增加 `config_version`、`prompt_versions`（JSONB）、`model_version` |
| 回放 | checkpointer + `config_version` 锁定，完整重建当时环境 |
| 闸门 | 变体必须带 `config_version`；只对比同配置下的新旧 prompt |

**迁移**：旧 archive 行统一补 `config_version='legacy'`，明确「这批无法精确复现」。

#### 9.4.5 修复顺序

| 顺序 | 问题 | 理由 | 工作量 |
|---|---|---|---|
| 1 | 9.4.4 配置版本 | 是其他三个的前提；没有它，闸门锁不住变量，A/B 也做不了 | 最小 |
| 2 | 9.4.1 边证据 | schema 升级独立可做，不依赖其他改造 | 中 |
| 3 | 9.4.2 as_of | 新数据强制，历史只标 low，不阻塞 | 中 |
| 4 | 9.4.3 唯一 owner | 涉及五个出口，只能 Strangler Fig 分三阶段 | 最大 |

## 10. 风险与边界

| 风险 | 应对 |
|---|---|
| 数据源不稳定，图里无米下锅 | 先完成数据准确率专项；工具层显式失败 |
| 多模块口径冲突 | 冲突显式化 + 置信度降档，不强行统一 |
| 成本与时延上升 | 分级触发 + 投影读取；主口全量、个股口按需、推送只推变化 |
| 单点故障 | 图不可用时各模块卡片保持可用，标注"研判暂不可用" |
| 观点合规 | 输出风险提示；不复制分析师原文结论 |
| 评测失真 | 时间截面冻结 + 固定评测集 + 人工裁决 |
| 迁移期双轨 | 旧接口保留只读兜底，观察两周再下线 |

## 附录：术语

- **证据（evidence）**：带来源、时间戳、质量标记的事实片段。
- **论点（claim）**：研究子图基于证据得出的结构化判断，可被反证失效。
- **研判（judgment）**：多方、反方、冲突消解后形成的唯一方向性结论。
- **研判账本**：所有研判与验证结果的持久化记录，是全站唯一结论源。
- **投影（projection）**：按标的/板块/时间窗从证据账本中取出的相关切片。
- **校准度**：置信度与实际命中率的一致性程度。

## 子图接入规范（`brain_v3/` 口径）

> 适用版本：2026-11-26 起（`brain_v3/` 第一周）。接入前先读 4 条规则与自检清单；
> 旧实现参考（仅作历史）：`aistock-agent-py/src/aistock_agent/graph/brain/nodes/research.py`。

主图装配只有固定节点是写死的：入口 `market_perception`、`event_perception`，裁决与出口
`conflict_resolver → judgment_writer → briefing_writer`（固定节点不登记，使用保留 ID）。中间环节是 probe，
必须在 `brain_v3/registry.yaml` 手动登记，主图按 `deps` 拓扑分层并行，不靠 import 顺序。

### 4 条插槽规则

1. **只读 evidence / claims，只写白名单通道。**
   子图允许写：`evidence`、`claims`、`conflicts`、`method_prior`、`render_targets`、`trace`、`cost`
   （与主图装配的通道白名单 `_SUBGRAPH_OUTPUT_KEYS` 一致；白名单外的键不会回写主图）。
   `judgment`、`brief`、`verified_result` 是出口/校准专用，子图**禁止**写入（`verified_result`
   只能由 SE-ENTITY 的 `verifier` 回填）；`method_prior` 只允许按 `method_prior["<子图名>"]["<字段>"]`
   新增自己的命名空间，禁止改 `default` 命名空间。
2. **必须能独立编译、独立单测，并在 `registry.yaml` 手动登记。**
   暴露 `build_<name>_subgraph()`（可独立编译、可单测）；在 `brain_v3/registry.yaml` 写
   `id / module / deps / required_for / owner` 五项，**不再要求改 `builder.py` 顶部 import**：
   注册只由 YAML 决定，扫描到但未登记的模块主图不加载。
   提交前跑 `python -m brain_v3.registry --check`：未登记 / 空登记 / `deps` 成环 / 指纹与
   `registry.lock` 不一致，四类都直接失败（指纹 = `id + deps + required_for + profiles.needs|optional` 的 sha256）。
3. **证据必须带溯源信封。**
   用 `brain_v3/tools/provenance.py` 的 `ok_envelope()` / `degraded_envelope()` 构造信封，
   再用 `envelope_to_evidence()` 落成 `brain_v3/contracts/` 的 `Evidence`；
   禁止手搓 evidence 字面量（缺 `source` / `published_at` / `fetched_at` 会被 `judgment_writer`
   的多源校验判死；`subject` 可为空，主体一致性校验改用 `claim.subject`）。
4. **失败必须可分类，不得抛出中断主图。**
   probe 只返回 `ok` 或抛可分类错误（`timeout` / `empty` / `schema_mismatch` / `not_implemented`），
   由主控写入 `missing_probes`（含 `required` 与 `reason`），不自行声明 `partial` / `degraded` / `insufficient`；
   节点级超时与错误路由由 `TimeoutPolicy` + `error_handler` 负责，`asyncio.wait_for` 只保留为外层保险；probe 不自己 sleep 重试。

### 最小注册示例

```python
# brain_v3/probes/sector/（module: brain_v3.probes.sector）
from langgraph.graph import END, START, StateGraph
from langgraph.graph.state import CompiledStateGraph

from brain_v3.contracts.judgment import JudgmentClaim
from brain_v3.graph.state import BrainState
from brain_v3.tools.provenance import envelope_to_evidence, ok_envelope


async def sector_research(state: BrainState) -> dict[str, object]:
    # 真实接入时换成对应领域工具取数；取数失败抛可分类错误（timeout/empty/schema_mismatch/not_implemented）。
    envelope = ok_envelope(
        {"pct": 2.1},
        source="ths_daily",
        source_type="market_data",
        event_time="2026-11-26T15:00:00+08:00",
        published_at="2026-11-26T15:00:00+08:00",  # 真实发布时间；禁止 published_at=state["as_of"]
        as_of=state["as_of"],                       # 可知截面，与上两者分离
    )
    evidence = envelope_to_evidence(
        envelope,
        # = ev_{source_type}_{sha1(source_id|snapshot_id)[:12]}，不含 subject
        evidence_id="ev_market_data_9f2c1ab34d07",
        kind="sector",
        subject=state["subject"],
        claim="板块指数当日上涨 2.1%",
        value=2.1,
        unit="%",
    )
    claim = JudgmentClaim(
        claim_id=f"clm_sector_{evidence.evidence_id}",
        subject=state["subject"],
        kind="sector",
        statement=evidence.claim,
        evidence_ids=[evidence.evidence_id],
        confidence=0.6,
        invalidated_by=["板块指数收盘跌破 20 日线"],
        produced_by="sector_research",
    )
    return {
        "evidence": [evidence],
        "claims": [claim],
        "trace": [{"node": "sector_research", "status": "ok"}],
    }


def build_sector_research_subgraph() -> CompiledStateGraph[BrainState, None, BrainState, BrainState]:
    graph: StateGraph[BrainState, None, BrainState, BrainState] = StateGraph(BrainState)
    graph.add_node("sector_research", sector_research)
    graph.add_edge(START, "sector_research")
    graph.add_edge("sector_research", END)
    return graph.compile()


# 登记在 brain_v3/registry.yaml（id / module / deps / required_for / owner），不在代码里注册。
```
