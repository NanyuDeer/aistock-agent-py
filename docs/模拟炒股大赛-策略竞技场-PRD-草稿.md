## 1. 背景与目标

### 1.1 观察到的问题

团队要做一个吸引用户的比赛，但**模拟炒股本身是反人性的**：没有真实盈亏，却要用户花时间看盘、分析、下单。所以"缩小版实盘"这条路走不通——投入高、门槛高、留存低。

同时，App 目前存在一个结构性问题（走查报告结论）：**"看市场"一侧已经相当完整（晨报/午报/晚报、风口/消息/事件/恐贪/节奏、复盘归因、预测验证），"看自己"一侧完全空白**——持仓陪伴 / 交易复盘 / 动态估值三个页面是空壳，全 App 没有任何下单、持仓、收益记录能力。
> 证据：`docs/洞见App使用体验报告-完整交易日全流程模拟.md`（§2.6、P0-4）

并且，系统里已上线的大量 AI 能力（消息洞见、事件传导、风口龙头、趋势评分、恐贪、机构调研等）**只给结论、从不被验证**；目前只有"预判环"和"节奏分支验证"两条具备可验证结果。

### 1.2 产品决策

把大赛重新定位为 **「AI 陪跑的策略竞技场」**，而不是"模拟炒股盘"：

> 用户选一种打法（= 一组 AI 能力），系统按打法推荐标的，用户虚拟买卖、可全程放手给 AI，平台用统一内核记账，产出**战绩海报 + 功能贡献度**，局内日榜竞技、胜者得奖励。

一句话：**模拟盘只是外壳，核心是游戏化地验证产品功能。**

### 1.3 期望达成的可观测效果

| 层面 | 效果（可被检验） |
| --- | --- |
| 用户侧 | 一局内用户只在 3 个决策点（盘前/盘中/盘后）做选择，不必每天盯盘；一局结束能看到"我赚/亏了多少、凭什么、哪个功能帮了我" |
| 系统侧 | 局内所有收益数字出自**同一个结算内核**，口径唯一、可核验、可回算；T+1 与涨跌停规则与实盘一致 |
| 平台侧 | 每个被验证的挑战产出一句可用的结论："X 功能在本局对收益的贡献是 Y"，用于后续产品迭代 |

> **合规底线【已定】**：严格虚拟模拟，不接实盘、不涉真实资金；不给投资建议、不预测涨跌。奖励形态需另行合规确认（见 §9）。

## 2. 范围

### 2.1 最小完整闭环（P0）

**入口 → 选打法 → 推荐池 → 虚拟买卖 → 收盘结算 → 战报与排名**

1. 用户从首页入口 / 新建「模拟」Tab 进入
2. 选择一种**挑战模式**（= 选定本局只能用哪一类 AI 能力）
3. 系统按该模式产出**推荐池**（带推荐理由与出处）
4. 用户在池内**虚拟买入 / 卖出**（T+1、涨跌停不可成交、无手续费）
5. 每个交易日收盘，**统一结算内核**记账
6. 局末产出**战报**（收益拆解 + 功能贡献度）与**排行榜**
7. 全程由**时段动态推送**在盘前/盘中/盘后各给一次决策入口

**完成证据（用户可见）**：战报页展示本局收益、排名、每一笔成交依据，以及"哪个功能贡献了多少"。

**最重要失败路径的恢复**：成交被涨跌停拒绝 → 明确告知原因并允许改价/改量重提；结算数据缺失 → 该标的当日标记为未结算并顺延，不写入错误数字。

### 2.2 P1（本期内可选）

- 更多挑战模式（消息洞见 / 事件洞见 / 恐贪 / 趋势评分 / 风口龙头 / 机构热门股 / 业绩预测）
- 成就与奖励体系（权益型）
- 战绩分享海报
- 功能贡献度的完整统计口径（依赖 P0 埋点数据积累后开放）

### 2.3 明确不做（避免歧义）

| 不做 | 原因 |
| --- | --- |
| 实盘、真实资金、真实账户 | 合规底线【已定】 |
| 全 App 收益口径统一 | 组长已确认：本次只服务模拟炒股大赛【已定】 |
| 与「择时镜子」项目复用同一套内核 | 择时镜子是另一个比赛项目，本期不做复用假设【已定】 |
| 好友对战 / 战队 / 实时多人对战 | 纯新增范围，本期社交仅到"分享海报"【建议·待确认】 |
| 基于用户数据自动调权 / 自动优化算法 | 本期只采集，不反哺【已定】 |
| 手续费与印花税 | 组长确认不影响模拟性质，不做【已定】 |

## 3. 核心产品模型

### 3.1 角色

| 角色 | 定义 |
| --- | --- |
| 参赛用户 | 洞见 App 已登录用户（现有统一账户：手机号 / 微信 / 邮箱 / 密码，含账户合并） |
| 平台（系统） | 产出推荐池、执行结算、生成战报与榜单；同时是反哺数据的消费方 |

### 3.2 核心对象

| 对象 | 说明 |
| --- | --- |
| **挑战模式** | 本局的"打法"，决定推荐池来自哪一类 AI 能力。一个挑战模式 = 一个功能的验证实验 |
| **局** | 一次完整的参赛周期，有明确开始与结束 |
| **推荐池** | 本局允许买入的标的集合，由挑战模式决定；每只标的带**出处标签**与推荐理由 |
| **虚拟账户** | 用户在某局内的资金与持仓容器 |
| **虚拟订单 / 成交** | 买入/卖出委托与成交记录 |
| **结算记录** | 每个交易日的持仓市值与日收益（由统一结算内核产出） |
| **战报** | 局末产出物：收益拆解 + 功能贡献度 + 可分享战绩 |
| **排行榜** | 按挑战模式分榜的排名 |

### 3.3 状态与生命周期

```
局：  未开始 → 进行中 → 已结算 → 已归档
订单：待成交 → 已成交 / 已拒绝(涨跌停·T+1·资金不足·非交易日)
             → 已撤销(仅限未成交)
持仓：持有 → 可卖(次日) → 已清仓
```

## 4. 功能需求

### FR-01 入口与「模拟」Tab

- **目的**：让用户零成本找到并进入比赛。
- **入口**（三处，本期至少做前两处）：
  1. 首页新增「模拟」入口（会上决议）
  2. 新建独立「模拟」Tab（会上决议）
  3. 【建议·待确认】复用全局对话栏「报告」按钮位——该位置源码注释已写明是"交易功能未接入前的占位去向"，改成模拟盘入口最省导航成本
  4. 【建议·待确认】三个空壳页（持仓陪伴 / 交易复盘 / 动态估值）由模拟盘接管，分别承载 **持仓页 / 战报页 / 资金与结算页**
- **触发**：登录用户可进入；未登录用户看到入口但进入时引导登录。
- **结果**：进入模拟 Tab 后默认落在"当前局"，无进行中局时落在"发起新局"。

### FR-02 挑战模式（局）

- **目的**：把"用户选股"改为"用户选 AI 能力"，同时让每一局成为一次功能验证实验。
- **产品规则**：
  - 一个挑战模式**只允许使用一类 AI 能力**对应的信号/标的作为买入依据
  - 每局必须提供**对照组模式**（全功能自由使用），用于与单功能模式对比
  - 模式与推荐池的来源一一对应，用户在同一局内不可切换模式
- **首期模式【建议·待确认】**：

| 挑战模式 | 对应 AI 能力 | 选择理由 |
| --- | --- | --- |
| AI 帮我选（主推） | `ai_stock_selection_runs / _candidates / _results` 三表 + `/api/ai-stock-selection/latest` | 已有真实接口与数据模型，推荐池可直接复用 |
| 节奏大师 | 节奏卡（stage/score/`position_band`/branches）+ 5 交易日分支验证 | 已有"5 日分支命中"验证口径，一局长度可直接对齐 |
| 全功能自由（对照组） | 以上全部 | 提供对照基线 |

> **与会上"选交易风格"的关系【待确认】**：会上决议是"用户先选**交易风格**（短线打板 / 中长线）→ 系统按风格推荐股票"，本文档把这条收敛为"选**挑战模式**"（一个模式 = 一类 AI 能力）。
> - 方案 A（推荐）：对外仍叫「风格」，用户看到的是"短线打板 / 价值投资"这类**玩法名**，内部映射到挑战模式与对应能力组。既满足会上口径，又保住"一局验证一个功能"的实验结构。
> - 方案 B：风格与挑战模式并存为两个维度（风格定玩法、模式定能力），表达力更强但数据模型与推荐池口径复杂一倍。

- **局的状态**：用户发起 →「进行中」→ 到局末自动「已结算」→ 展示战报 →「已归档」（可回看）
- **【TBD】一局长度**：待定。候选见 §9。倾向"短局制"以匹配"快反馈"。
- **【TBD】同时可参与的局数**：是否允许用户并行多局（分别体验不同挑战模式）待定。

### FR-03 推荐池

- **目的**：给出本局可交易的标的，且**每个标的都能回答"为什么推它、来自哪个功能"**。
- **规则**：
  - 推荐池由挑战模式决定来源，一经开局**固定**（局内不追加、不替换），保证榜单可比
  - 每只标的必须携带：出处标签（来自哪个功能）、推荐理由、生成时点
  - 池内数量【建议·待确认】（建议 10 只，与现有 `ai-stock-selection` Top10 对齐）
  - 用户**只能在池内买入**（会上决议：半自动赛制）
- **空态**：某模式当日无候选 → 明确提示"该模式今日无推荐，可改用对照组模式或等待下一局"，不允许静默给空池。

### FR-04 虚拟交易

- **目的**：让用户用最低成本表达"买 / 不买 / 卖"。
- **规则【已定 + 建议】**：

| 项 | 规则 | 来源 |
| --- | --- | --- |
| 手续费 / 印花税 | 不计 | 【已定】组长确认 |
| T+1 | 当日买入次日可卖 | 【已定】参照实盘 |
| 涨跌停 | 触及涨/跌停不可成交 | 【已定】参照实盘 |
| 最小交易单位 | 100 股（1 手） | 【建议·待确认】 |
| 成交价 | 下单时刻最新可成交价 | 【建议·待确认】 |
| 记账价 | 每个交易日收盘价 | 【建议·待确认】 |
| 交易时段 | 仅交易日的交易时段可下单 | 【建议·待确认】复用 `trading_calendar` |
| 买入范围 | 仅限本局推荐池 | 【已定】 |

- **交互要求（对应"轻量"定位）**：
  - 每只标的提供 **「跟 AI 的建议」** 一键操作（按预置比例下单），用户不必自己算仓位
  - 提供 **「忽略」** 出口，忽略不产生任何惩罚
  - 允许缺席：可设置 **自动跟随 AI**（该模式下 AI 建议自动转化为虚拟委托），用户整局不操作也能完赛
- **结果**：生成虚拟订单与成交记录；持仓页即时更新（盘中为估值，非记账值）。

### FR-05 统一结算内核

- **目的（本文档最重要的约束）**：**局内所有收益数字只由这一个内核产出**，保证同一数字在任何页面同值、可核验、可回算。
- **三层时钟【建议·待确认】**：

| 层 | 频率 | 作用 | 是否记账 |
| --- | --- | --- | --- |
| L1 盘中实时估值 | 盘中 60s 级刷新 | 只看涨跌，制造快反馈 | 否 |
| **L2 交易日收盘结算** | 每交易日收盘后 | **唯一记账口径**，产出日收益 | **是** |
| L3 局末结算 | 局结束时 | 用已结算的日收益复利，定榜与战报 | 是（汇总） |

- **口径纪律**：
  - 结算必须按 `trading_calendar` 唯一事实源判定交易日；非交易日不结算
  - 计算口径带**版本号**，口径变更需留痕且历史可回算（参照现有预判验证口径的管理方式）
  - 每个展示数字都可**指回原始成交明细与行情**
  - 关键常量（如基准、阈值）**只允许一个来源**，禁止多处内联
- **复用范式**：现有 `wind_leader_push_history`（`push_price` / `latest_price` / `realtime_return_pct`）已经确立了"收益率仅由后端按结算后价格计算、前端只展示"的做法，本内核沿用同一范式。
- **边界**：本期**不承担**全 App 收益口径统一（见 §2.3）。

### FR-06 持仓与战报

- **持仓页**：当前持仓、成本、浮动盈亏、可用资金、今日已结算收益；数据全部来自结算内核。
- **战报页（局末产出，竞技场的核心产物）**：
  1. 本局收益（含与对照基准的差异）
  2. 收益拆解：每一笔成交的时间、依据、盈亏
  3. **功能贡献度**：本局收益中归因于各功能的比例（例如"节奏大师在 3 次调仓中贡献 X"）
  4. 与本人历史局的对比
- **【TBD】功能贡献度的归因算法**：待定，需与数据采集（FR-11）一并设计。

### FR-07 排行榜

- **规则**：
  - **按挑战模式分榜**（不与对照组混排）
  - 榜单维度【建议·待确认】：收益、胜率、最大回撤、功能贡献度；避免单一"收益榜"逼迫所有人打板
  - 局榜 + 总榜（【TBD】总榜周期见 §9）
- **可解释性**：榜首应能点开看到其打法与依据摘要。

### FR-08 时段动态推送

- **目的**：按盘前/盘中/盘后把功能**在正确的时间推给用户**，既支撑实时决策，也提高功能使用率。
- **为什么用时段而不是风格作为推送轴【建议·待确认】**：时段是确定性的、无需用户画像、与产品既有节律（盘前读懂 / 盘中盯自选 / 盘后复盘）及引擎已有时段钩子（`morning_briefing`、`midday_briefing 12:05`、`rhythm_master` 的 morning/midday/after_close）天然对齐。
- **推送内容**：

| 时段 | 该段决策 | 推送项 |
| --- | --- | --- |
| 盘前 08:00–09:25 | 今天打什么 | 早点听摘要、风口龙头、消息洞见/事件洞见、AI 帮我选 Top10、节奏大师（盘前仓位） |
| 盘中 09:30–15:00 | 跟不跟 / 调不调 | 异动提醒（悬浮卡）、个股异动溯源解读、午间报、节奏大师（午间）、消息洞见（实时） |
| 盘后 15:00–次日 | 复盘 / 明天仓位 | 本局战报、预测验证、大盘溯源/市场洞见、节奏大师（收盘仓位） |

- **推送纪律（三条硬规则）**：
  1. **有增量才推**：对应功能无新内容时不推送，禁止按时间表机械弹窗
  2. **必须与用户相关**：推送必须说明"与你本局持仓/推荐池的关系"，否则不得推送
  3. **推送不等于要求在场**：每条推送必须同时提供「忽略（无惩罚）」与「交给 AI」两个出口
- **每段数量上限**：1–2 条【建议·待确认】
- **异常**：非交易日不推送交易类内容。

### FR-11 反哺数据采集（本期只采集，不做分析）

**目的**：为下期的"冠军模式分析 → 算法迭代"预留可用数据。**本期不实现任何分析或调权。**

| 采集对象 | 最小字段 | 留给下期做什么 |
| --- | --- | --- |
| 推荐曝光 | 推荐批次、标的、理由类型、出处功能 | 推荐采纳率 / 理由有效性 |
| 虚拟成交 | 下单时间（分钟级）、成交价、来源标签、数量 | 交易行为画像 |
| 虚拟卖出 | 卖出时间、持仓天数、已实现盈亏 | 胜率 / 持有时长分析 |
| 用户选择 | 挑战模式选择与变更记录 | 模式偏好与收益相关性 |

**硬要求**：以上记录必须带 `user_id` + 挑战模式 + 局标识，否则下期无法分析。

## 5. 共享规则与异常

### 5.1 单一事实源

| 事实 | 唯一来源 |
| --- | --- |
| 交易日判定 | `trading_calendar` 表（现有，禁止第二套日历） |
| 局内收益数字 | FR-05 统一结算内核 |
| 推荐池来源 | 挑战模式定义 |
| 计算口径 | 带版本号的口径定义（唯一入口，禁止内联常量） |

### 5.2 口径一致性要求

同一数字在不同页面（持仓页、战报页、排行榜）必须同值；若出现差异，以结算内核为准并记录异常。

### 5.3 异常处理

| 场景 | 处理 |
| --- | --- |
| 标的触及涨跌停 | 拒绝成交并说明原因，允许改价重提 |
| 非交易日下单/结算 | 拒绝，明确提示 |
| 资金不足 | 拒绝并提示可用资金 |
| 推荐池为空 | 明示空态与替代路径，不静默 |
| 结算数据缺失 | 该标的该日标记未结算并顺延，禁止写入推测值 |
| 用户中途退出 | 局继续，持仓保留；可随时回来看 |

## 6. 与现有系统的复用关系（诊断结论）

> 结论：竞技场的**原料基本齐备**，缺的是"交易与竞技"这块骨架。

| 档 | 可用的现有资产 | 竞技场对应模块 |
| --- | --- | --- |
| **直接接** | `ai_stock_selection_*` 三表（推荐池数据模型）；`wind_leader_push_history`（后端按结算价算收益的范式）；`rhythm_verification` 的 5 交易日验证窗口；`trading_calendar` | 推荐池、统一结算内核 |
| **加壳改造** | 10+ 个已上线的 AI 能力（AI 帮我选、节奏大师、消息洞见、事件洞见、恐贪、趋势评分、风口龙头、机构热门股、业绩预测等）——**均只出结论、无收益口径** | 挑战模式（一个能力 = 一个挑战）、功能贡献度 |
| **从零新建** | 前端三个空壳页（持仓/复盘/估值）+ 全局对话栏预留位 + Tab 徽章能力 | 虚拟账户·订单·成交·持仓、排行榜、奖励、分享、模拟 Tab 与页面 |

**额外价值判断**：现有 10+ 个能力中只有"预判环"和"节奏分支验证"具备可验证结果，其余**从未被验证**。竞技场是给这一批功能补上验证闭环的成本最低的方式——用户免费跑前向测试，平台获得"哪个功能真能提升收益"的结论。
